# 6-1 Web Workers

> 學習目標：能把 CPU 任務安全移到 Worker，並處理取消、錯誤與過期結果。

**核心觀念：** Worker 在另一執行緒執行可隔離的計算，透過 postMessage 交換資料，不能直接碰 DOM。結構化複製和啟動有成本，transferable 可處理大 ArrayBuffer。

**實作與驗證：** 選一個可重現的長任務，先量 UI 卡頓，再移到 Worker。加入任務 ID、錯誤回報、取消與資源回收；比較總完成時間與 INP／主執行緒阻塞。

**常見誤區：** 小型計算可能直接執行或切片更簡單；Worker 不保證總耗時縮短。

### 完整 Worker 任務還需處理什麼

除了 `postMessage` 與 `onmessage`，實務上還要有任務 ID 防止舊結果覆蓋新結果、錯誤傳遞、進度、取消與元件卸載後 `terminate()`。大量二進位資料可用 transferable 移交所有權，避免完整複製，但移交後原執行緒不能再使用該 buffer。

練習：讓使用者連續搜尋兩次，第二次先完成。確認 UI 只顯示最新任務結果；再測 Worker 失敗和頁面離開時的清理。比較的是 UI 是否流暢及總延遲，而不只是 Worker 中計算的秒數。

## 原理拆解

Worker 讓純計算不佔用 UI 主執行緒，但資料需要透過訊息傳送。一般物件常經結構化複製，輸入越大成本可能越高；可轉移的 ArrayBuffer 能避免完整複製，但所有權會移交。Worker 的回傳順序也可能與使用者最新輸入不同，因此結果需帶任務 ID，不能讓舊任務覆蓋新頁面狀態。取消、錯誤與卸載清理是完整實作的一部分。

## 從頭做一次

1. 先用 Performance trace 證明純計算長任務造成互動卡頓，再將核心計算抽成不依賴 DOM 的函式。
2. 建立 Worker 訊息協定，至少包含任務 ID、輸入、結果、錯誤；頁面離開時終止 Worker，連續任務時忽略過期結果。大 ArrayBuffer 可評估 transferable。
3. 比較主執行緒長任務、使用者互動延遲與總完成時間。若總完成時間變慢但 UI 明顯流暢，也要記下這個取捨。

## 如何判斷做對了

Worker 啟動與資料傳輸有成本；小型計算未必值得。

## 書籍逐頁核對｜紙本頁 6-2～6-10

書中先釐清：JavaScript 在頁面主執行緒上一次執行一件事，事件迴圈可讓 I/O 等待不長時間占住執行緒，卻不能把 CPU 密集的同步計算自動變成平行工作。若在主執行緒直接跑遞迴斐波那契一類重計算，頁面可能卡到無法操作。Web Worker 提供另一個執行環境，主執行緒可把資料送去計算，再接收結果並更新 DOM。

頁 6-4～6-7 用兩個檔案做最小範例：`worker.js` 接收數字、計算斐波那契、`postMessage` 傳回結果；頁面腳本建立 `Worker`，在按鈕事件送入數字、接收結果與錯誤。Worker 自己不能直接操作頁面 DOM；資料通常透過 `postMessage` 傳遞，這也表示通訊、資料複製與啟動都有成本。開多個 Worker 也會消耗 CPU 和記憶體，不代表越多越快。

頁 6-7～6-8 討論大量資料的傳輸：一般訊息使用結構化複製，可能造成時間和記憶體成本；`ArrayBuffer` 等可轉移物件可以把所有權交給另一端，避免整份資料複製，但原端就不能再照原本方式使用該 buffer。書中另外點到 SharedArrayBuffer 與 Atomics 的共用記憶體與同步議題；這涉及現行瀏覽器安全條件，應查最新支援要求，不能直接照舊範例使用。

頁 6-9～6-10 列適用場景，如大型排序、機器學習、加密解密、圖片處理、長輪詢等。選擇標準是「工作是否真的在主執行緒上阻塞互動，以及移轉後節省的時間是否大於通訊成本」。書中最後介紹 Comlink，讓 Worker 端函式可用較接近一般方法呼叫的形式操作，降低手寫 `postMessage` 協定的負擔。

## 問題與解答：何時使用 Web Worker

**問題 1：Worker 能解決什麼卡頓？** 純計算長任務若佔住主執行緒，按鈕、捲動和畫面更新會等它結束。把可隔離的計算移到 Worker，可讓主執行緒繼續處理 UI；但總計算時間未必縮短。

**問題 2：為什麼 Worker 不能直接更新 DOM？** Worker 運行在不同執行環境，通常沒有頁面的 DOM API。它以 `postMessage` 傳結果回主執行緒，再由主執行緒更新畫面。任務設計需包括 ID、錯誤、取消和元件卸載後不再套用過期結果。

**問題 3：傳大型資料給 Worker 會有什麼成本？** 結構化複製可能花時間與記憶體；`ArrayBuffer` 等可轉移物件可移交所有權，減少複製。若工作很短，啟動和傳輸成本可能大於計算本身，先量測再決定。

**問題 4：怎麼驗證收益？** 保留同一輸入資料和相同操作，量主執行緒長任務、互動延遲、整體任務完成時間及記憶體。理想結果是 UI 更可回應，且總耗時和資源成本可接受；若只是把資料來回傳送造成更慢，需調整邊界。
