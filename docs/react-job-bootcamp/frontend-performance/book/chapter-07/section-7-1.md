# 7-1 JavaScript 記憶體管理機制

> 學習目標：能用多輪操作和 retaining path 判斷記憶體洩漏。

**核心觀念：** 垃圾回收只能回收不可達物件；已不需要但仍被 closure、事件監聽、timer 或無上限 cache 持有的物件會留在記憶體。

**實作與驗證：** 重複執行同一開關頁流程，強制 GC 後比較 heap snapshot 與 retained size；沿 retaining path 找保留者，清理後重測。

**常見誤區：** 單次 heap 高不等於洩漏，須看多輪後持續成長與可重現的保留路徑。

### 如何分辨洩漏與正常成長

設計「打開彈窗 → 關閉 → 重複十次」的固定流程，每幾輪強制 GC 並拍 heap snapshot。若可達的 detached DOM node、監聽器或某個 Map 持續增加，沿 retaining path 找到保留者；若 GC 後回到接近原本水平，未必是洩漏。

修正時在元件卸載清理訂閱、timer、observer 和事件監聽，為 cache 設大小／生命週期上限。最後用同樣十輪流程重測，不要只靠『關掉一個 listener』就宣稱已解決。

## 原理拆解

垃圾回收只關心物件是否仍可從根參照到達，不知道產品功能是否已不需要它。關閉彈窗後，若監聽器閉包仍持有 DOM 節點，節點仍可達，就不會回收。記憶體洩漏分析因此要找「誰還持有它」，而不是只看某次記憶體峰值。多輪操作、強制 GC、比較 retained size 和 retaining path，才能把正常暫時分配與持續洩漏分開。

## 從頭做一次

1. 建立固定操作，例如反覆開關彈窗十次。每輪回到相同 UI 狀態，強制 GC 並拍 Heap Snapshot。
2. 比較 retained size、detached DOM node 與特定集合是否持續成長。沿 retaining path 找到保留引用的事件監聽器、timer、closure 或 cache。
3. 修正後用相同流程重測，並檢查功能沒有因過早清理而失效。

## 如何判斷做對了

單次 heap 高點不一定是洩漏；看的是 GC 後仍持續上升的可達物件。

## 書籍逐頁核對｜紙本頁 7-2～7-18

### 7-2～7-6：記憶體生命週期與 Stack／Heap 模型

書中用「分配、使用、釋放」三步驟說明記憶體生命週期。JavaScript 自動執行垃圾回收，但自動回收只會處理**不再可達**的資料；仍被程式保留引用的資料不會因「使用者看不到」就自動消失。書中用 Stack 與 Heap 的簡化模型畫出函式執行環境、基本值和物件參照，並明確提醒這只是教學模型，V8 的實際儲存方式會依最佳化和型別而不同，不能把「所有基本值都在 Stack、所有物件都在 Heap」當作規格。

### 7-6～7-11：GC 為何仍可能影響流暢度

書中先對比手動管理記憶體的語言與 JavaScript 的 Garbage Collector，再以 V8 的新生代／老生代概念介紹：年輕物件常較快回收，存活較久的物件進入老生代；書中示意 Scavenge 的複製、Mark-Sweep 的可達性掃描，以及 Mark-Compact 的整理。這些是理解「大量短命物件會增加 GC 工作、長壽物件若一直保留會讓記憶體膨脹」的模型，不是可以直接手動控制的 JS API。書中也談 GC 造成的執行暫停與增量標記，提醒長時間停頓會影響頁面反應。

### 7-12～7-14：常見記憶體洩漏來源

書中把洩漏定義為已不再需要但仍被保留、無法回收的記憶體。具體來源包括：事件監聽器在元件卸載後未移除；全域陣列不斷累積請求資料；從 DOM 移除節點後，JavaScript 的 Map／物件仍保留其引用。React 範例用 `useEffect` 的 cleanup 對應 `addEventListener`／`removeEventListener`。其他長期存活的 timer、observer 和訂閱也可依同樣思路檢查。

### 7-15～7-18：區分 CPU 成本與記憶體成本

作者做了一個大量物件的 demo，比較在原物件上重複改值與每次建立新物件。Performance trace 可看 CPU 忙碌程度，Memory heap snapshot 可看保留量。書中例子顯示不斷複製大量物件會讓 heap 瞬間上升，之後 GC 再清理；這不等於每次看到 heap 上升就是「洩漏」。真正的洩漏要看多次操作與 GC 後的基線是否持續增長，以及哪些物件仍被引用。書中最後提醒 immutable 風格有優點，但對巨大資料結構做頻繁完整複製可能成本高；應依實際資料規模與 profiler 決定做法。

## 問題與解答：記憶體上升是不是洩漏

**問題 1：JavaScript 有 GC，為何還會洩漏？** GC 判斷物件是否仍可從根參照到達，不知道產品已不需要它。事件監聽、閉包、全域陣列或 Map 若仍持有被移除的 DOM，物件仍可達，就不會回收。

**問題 2：Heap 曲線上升就能說有洩漏嗎？** 不行。大量短命物件可能讓 heap 暫時上升，GC 後再下降。用固定流程反覆操作，多輪後回到相同 UI 狀態並比較 GC 後基線；若基線持續升高，再追 retaining path。

**問題 3：怎麼找出誰保留了物件？** 對同一流程取多份 Heap Snapshot，找持續增加的類型或 detached DOM，沿 retaining path 追到事件監聽器、closure、timer 或 cache。修正保留者後，再用相同輪數重測。

**問題 4：Immutable 寫法是否一定更安全又更快？** 它有利於狀態推理，但頻繁完整複製巨大資料會產生大量短命物件，增加配置與 GC 工作。書中的大量物件 demo 正是提醒要把 CPU 與記憶體成本分開量，不能只用風格推定效能。
