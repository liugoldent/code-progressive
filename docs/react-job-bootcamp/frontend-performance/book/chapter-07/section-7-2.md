# 7-2 前端應用的各種渲染架構

> 學習目標：能按頁面需求比較 CSR、SSR、SSG 的首屏、互動與維護成本。

**核心觀念：** CSR、SSR、SSG 在首屏 HTML、資料新鮮度、伺服器負擔與 hydration 成本上各有取捨。個別頁面可選不同模式，並非整站只能採一種。

**實作與驗證：** 比較首頁、文章、個人化頁面的 TTFB、LCP、JS bytes、hydration 和快取策略。先以實際使用者路徑決定架構，再重測。

**常見誤區：** SSR 送出 HTML 後仍可能因巨大 hydration 工作而無法及時互動。

### 以頁面類型選渲染方式

公開文章頁內容穩定、需要搜尋與快取，可先評估 SSG；個人化但要求首屏 HTML 的頁面可評估 SSR；登入後高度互動的內部工具可評估 CSR。這只是起點，還要測資料更新頻率、伺服器成本和 hydration 所需 JS。

比較同一頁的 TTFB、LCP、可互動時間、首屏 JS bytes，以及後續導覽速度。SSR 若 TTFB 太慢或 hydration 太重，可能只改善了『看到 HTML』，沒有改善實際操作。

## 原理拆解

CSR、SSR、SSG 不是品質高低排序，而是計算發生在哪裡、何時產生 HTML 的選擇。CSR 把組裝畫面的責任較多放在瀏覽器；SSR 在請求時由伺服器產生 HTML；SSG 在建置時產生。SSR／SSG 可以讓內容較早出現在 HTML，卻不保證互動立即可用，因為 JS 與 hydration 仍可能很重。選型要同時看資料新鮮度、快取、伺服器成本及使用者主要任務。

## 從頭做一次

1. 選公開文章、個人化詳情、登入後內部工具三種頁面，列出 SEO、資料新鮮度、快取、首屏與互動要求。
2. 對每種架構比較 TTFB、LCP、JS bytes、hydration 成本，以及站內導覽。避免只看 HTML 先出現就認定較快。
3. 若採 SSR，測伺服器負載高時的 TTFB；若採 SSG，測內容更新與重新生成策略；若採 CSR，測低階裝置下載並執行 JS 的時間。

## 如何判斷做對了

同一產品可混用多種渲染方式；決策單位通常是頁面或路由。

## 書籍逐頁核對｜紙本頁 7-19～7-34

### 7-19～7-22：CSR 的兩個等待階段

書中先以 Client Side Rendering（CSR）說明：伺服器可先送出內容很少的 HTML，瀏覽器下載、解析並執行 JavaScript，才組出主要畫面。這讓後續互動與局部更新能由前端處理，但初次進站可能先等程式下載，再等程式執行。行動裝置 CPU 較弱時，光減少傳輸位元組不夠；書中把 Code Splitting、Dynamic Import 當作縮小初始 bundle 的辦法，同時提醒它們無法消除所有執行成本。

另一個問題是搜尋引擎取得的初始 HTML 可能缺少主要內容。書中提到 Google 可能在後續階段執行 JavaScript 來建立索引，但不能因此推定所有爬蟲都會正確、及時取得 CSR 內容。決定公開頁面的渲染方式時，應實際檢查伺服器回傳的 HTML、搜尋服務看到的內容，以及登入限制。

### 7-22～7-24：SSR 與 Hydration

傳統伺服器渲染會在收到請求後組好 HTML 再回傳；使用者較早看見內容，但每次請求都要在伺服器做工作。書中重點討論同構／混合式 SSR：同一應用可在伺服器產生首屏 HTML，再由瀏覽器載入 JavaScript，對既有 DOM 做 Hydration，綁定事件並使頁面能互動。**「畫面已出現」與「按鈕已能回應」是兩個時間點**，不可把 SSR 的可見速度直接當成可互動速度。

SSR 有利於把主要內容放入初始 HTML，也可能改善首屏體感；代價包括伺服器運算、維護同構程式，以及處理只存在於瀏覽器的 API。書中也提醒：若伺服器在尖峰時渲染不及，TTFB 會拉長。評估 SSR 時應同時量伺服器回應與 Hydration 的主執行緒工作。

### 7-24～7-26：SSG 與 ISR

Static Site Generation（SSG）在建置階段預先產生 HTML，請求到來時可直接透過靜態託管或 CDN 回傳。適合更新頻率低、內容可共用的頁面；若資料頻繁變動，必須考慮重新建置、部署和快取失效。當頁面數極大時，建置時間也會成為成本。

Incremental Site Rendering（ISR）是書中介紹的 Next.js 範例：先提供已有的靜態結果，到達指定重新驗證間隔後，再在背景產生新版本並更新快取。書中以 `getStaticProps` 的 `revalidate: 60` 示意「資料可短時間沿用，再逐步更新」，並非承諾所有請求剛好每 60 秒取得新資料。這類機制需另外設計失敗時的舊內容、快取鍵、更新時機與資料一致性；實際 API 隨框架版本可能改變，應查當前框架文件。

### 7-27～7-28：串流 SSR 與選擇性 Hydration

一般 SSR 若等所有資料和元件完成後才送出完整 HTML，最慢的部分可能拖住整頁。書中以 Streaming SSR 說明把已完成的 HTML 分批送出，讓使用者先看到可用區塊；以 Selective Hydration 說明不必等待全頁 JavaScript 與所有元件完成 Hydration，部分區塊可先具備互動能力。書中提到 React 18 的 Suspense SSR 作為實作方向。要注意串流較早顯示內容，仍須檢查網路、伺服器等待、JavaScript 執行與各區塊真正可操作的時間。

### 7-29～7-34：指標比較與選型

書中依次定義 TTFB、FP、FCP、TTI，然後用時間線對照傳統 SSR、CSR、SSG 與同構 SSR：

| 架構 | 內容何時產生 | 可能的優勢 | 要特別量的成本 |
| --- | --- | --- | --- |
| CSR | 瀏覽器執行 JS 後 | 豐富的用戶端互動、路由切換 | 初始 JS 的傳輸與執行、首屏空白 |
| 傳統 SSR | 每次請求時由伺服器完成 HTML | HTML 到達即可閱讀 | 伺服器運算與 TTFB |
| 同構 SSR | 伺服器先產 HTML，瀏覽器再 Hydration | 首屏內容與後續互動兼顧 | 伺服器運算、JS 下載、Hydration 長任務 |
| SSG | 建置時預產 HTML | 易快取與 CDN 配送 | 重建時間、資料新鮮度、動態資料接法 |
| ISR | 先使用靜態結果，再按策略重新生成 | 在快取與更新之間折衷 | 版本交替、一致性與失敗處理 |

書中的選型結論是 **it depends**：公開且少變動的內容適合先評估 SSG；常變動且需要首屏內容的頁面可評估 SSR 或 ISR；高度個人化或登入後工具可評估 CSR。真正的取捨要根據頁面、資料更新頻率、爬蟲需求、尖峰流量與使用者裝置測量；同一網站可以按路由混用。書中使用的 TTI 是當時常見指標，閱讀時應把它當成互動延遲的診斷概念，現行正式指標與工具介面需再按官方文件核對。

## 問題與解答：CSR、SSR、SSG 到底怎麼選

**問題 1：SSR 已回傳完整 HTML，為何點按鈕仍沒反應？** 瀏覽器還要下載並執行 JS，完成 Hydration 才能綁定事件。首屏可見與可互動是兩件事。量 TTFB、FCP／LCP，也要看 Hydration 期間的主執行緒長任務與實際點擊延遲。

**問題 2：公開文章與登入後工具，是否必須用同一架構？** 不必。公開且少變的文章可先評估 SSG；資料常變而要求首屏 HTML 可評估 SSR／ISR；高度互動的內部工具可評估 CSR。同一網站按路由混用，取決於 SEO、更新頻率、快取和伺服器負擔。

**問題 3：SSG 很快，為何還需要 ISR？** SSG 的 HTML 在 build 時產生，內容變動通常要重新生成；頁面數多或更新頻繁時成本上升。ISR 讓既有靜態頁繼續服務，按策略背景生成新版本，折衷快取與新鮮度，但必須接受短暫舊內容並設計失敗處理。

**問題 4：Streaming SSR 與 Selective Hydration 各解決什麼等待？** 串流讓伺服器分段送出已完成 HTML，不必整頁等最慢區塊；選擇性 Hydration 讓部分元件先變得可互動，不必等全頁完成。兩者都應以實際區塊可見、可操作時間驗證。

**問題 5：選型時哪個單一數字最重要？** 沒有單一答案。CSR 可能有較低伺服器負擔卻較重的初始 JS；SSR 可能改善首屏卻拉長 TTFB 或 Hydration；SSG 需要管理新鮮度。按頁面任務同時比較 TTFB、LCP、互動、JS bytes、快取和尖峰負載。
