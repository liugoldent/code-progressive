# 1-1 前端效能優化為什麼如此重要？

> 學習目標：能分辨「內容晚出現」與「內容已出現但操作卡住」，並選對診斷工具。

**核心觀念：** 慢不只發生在下載。使用者從點連結到看到內容，再到能順利操作，會經過網路、伺服器、瀏覽器解析與主執行緒執行。低階設備上的 JS 執行成本可能比高階桌機高得多。

**實作與驗證：** 選一條產品主流程，明確寫出頁面、操作、裝置、網路與地區。記錄冷快取和熱快取的結果，觀察等待是否造成重複提交或跳出。

**常見誤區：** 不要以開發機和單一網速代表所有使用者。

### 案例推演

商品頁打開後立刻出現標題，但主圖三秒後才出現：應先看主圖是否被 HTML 及早發現、請求何時開始，以及伺服器 TTFB。另一種情況是畫面已可見，但按「加入購物車」兩秒才有反應：此時要錄製點擊事件與下一次繪製，排查主執行緒工作，而非繼續壓縮主圖。

### 本節交付物

建立一張表，至少有「頁面／操作、使用者設備與網路、目前指標、目標、量測來源、最大瓶頸」六欄。沒有量測來源的目標無法驗收。

## 原理拆解

效能是一段時間線上的等待，而不是一個單一數字。使用者點擊連結後，可能先等待 DNS／連線與伺服器回應，接著瀏覽器解析 HTML、載入阻塞資源、執行 JavaScript，最後才繪製內容。首屏出現之後仍可能有 hydration、大量資料處理或第三方腳本讓操作卡住。因此先定義「使用者何時認為任務開始、何時認為任務完成」，再對應指標。若任務是加入購物車，單看首頁 LCP 不能代表這項任務的體驗。

## 書籍逐頁核對｜紙本頁 1-1～1-5

- **1-1～1-3：使用者體驗。** 作者先用「朋友開啟社群動態卻一直等待」的情境說明：介面看得見，不代表操作流程順暢。這個情境可以拆成畫面開始呈現、主要內容載入與操作得到回饋三個等待點；筆記應分別量測，不能只記總載入秒數。
- **1-2～1-3：營收。** 書中引用企業案例說明等待時間可能影響轉換與營收。這些是當年引用的案例，不應直接套成自己網站的轉換率預測。實務上應先以產品漏斗、使用者分群與效能資料驗證是否有關聯。
- **1-4～1-5：搜尋能見度。** 作者引用 Google 早期談頁面速度與搜尋排名的資料，並提醒搜尋排名仍由多種訊號共同決定。記錄成「效能是可能影響搜尋體驗的因素之一」較準確，不能推論改善 LCP 必然提升名次。
- **1-5：優化取捨。** 這一節最後強調，效能優化有時會變成過度追求速度；真正該處理的是使用者遇到的障礙。優先順序應由可觀察的任務困難與實測瓶頸決定。

**對應練習：** 選一個使用者會放棄的流程，分別寫下「內容何時可見、何時可操作、何時完成任務」。接著找一個相符的量測方法，避免把歷史案例當成自己的成果數字。

## 從頭做一次

1. 建立導覽時間線：從開始導覽、收到 HTML、發現主圖、完成 LCP，到第一次可用互動。Network 顯示請求階段，Performance 顯示主執行緒與繪製階段。
2. 選一個真實任務，例如「打開商品 → 看圖 → 加入購物車」。分別記錄首次進站和站內導覽，避免把兩種路徑混成同一個數字。
3. 寫下最慢環節及證據：若主圖請求直到 JS 執行完才開始，優先處理資源發現；若點擊事件後有長任務，優先處理計算與渲染。

## 如何判斷做對了

成功標準：能指出「哪個使用者動作、在哪種裝置、等待哪一段」，並用同樣條件重測。只說網站變快或變慢，仍無法指導優化。

## 自我檢查

- 我是否保存相同條件下的改動前後證據，並檢查副作用？

## 問題與解答：從「慢」找到可改的環節

**問題 1：使用者說「網站很慢」，為什麼不能直接先壓縮圖片？** 速度包含伺服器等待、資源下載、JavaScript 執行、畫面繪製及點擊回應。圖片只可能解決其中一段。先記錄「哪個頁面、哪一步操作、哪種裝置、何時開始與結束」，再用 Network 和 Performance 把等待拆開。例如列表已顯示卻點不動，優先查主執行緒長任務，而非圖片大小。

**問題 2：為什麼自己的電腦很快，使用者仍覺得卡？** 開發機可能有較快 CPU、穩定網路、熱快取與較少第三方阻礙。相同 JS 在低階手機上的解析、執行可能明顯變長。應分開測冷／熱快取、桌機／手機、良好／受限網路，並看真實使用者分布，不能用單次本機測試代替。

**問題 3：要先優化哪個頁面？** 先挑使用者常走、直接影響任務完成的流程，例如首頁進入商品頁再送出表單。記錄每一步的流失、重複點擊或等待，再找最慢且最常被碰到的環節。改善少見頁面的漂亮分數，未必比改善核心流程有價值。

**問題 4：怎麼證明優化真的有效？** 在相同裝置、網路、資料量和快取狀態下保留修改前後紀錄，同時檢查主要操作是否更快完成、錯誤或跳出是否下降。若只看到某次 Lighthouse 分數上升，還不能推論所有使用者受益。
