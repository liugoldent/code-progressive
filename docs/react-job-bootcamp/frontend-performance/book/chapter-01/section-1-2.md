# 1-2 效能的監控工具 Performance Analyzers

> 學習目標：把 Lighthouse、Network、Performance 和真實使用者資料放在同一條診斷流程。

**核心觀念：** 實驗室資料適合穩定重現與找原因；真實使用者資料反映裝置、網路、地區及第三方內容的分布。Lighthouse、DevTools Performance、Network、CrUX 或自建 RUM 各有用途。

**實作與驗證：** 先保存 Lighthouse 報告與 Performance trace，再以 RUM 分頁面、設備與版本觀察 p75。比較同一頁面的多次測量與波動範圍，避免被一次分數誤導。

**常見誤區：** Lighthouse 的 TBT 是實驗室阻塞訊號，不能直接當成真實使用者的 INP。

### 工具怎麼分工

Network 面板回答「哪個請求開始得晚、等了多久、載入多少位元組」；Performance 面板回答「主執行緒在忙什麼、哪一幀卡住」；Lighthouse 提供可重複的診斷提示；RUM 回答「真實使用者是否真的改善」。一次實驗至少保留一份原始 trace 或報告，方便回頭比較。

### 判讀範例

若同一頁 Lighthouse 分數從 78 到 86，但行動版 p75 LCP 不變，先檢查測試波動、正式環境快取與 LCP 元素是否相同。不要只憑總分宣稱使用者體驗已改善。

## 原理拆解

實驗室資料與真實使用者資料的抽樣方式不同。實驗室每次可以固定設備與網路，適合比較一個修改是否使同一場景改善；真實使用者資料混合不同裝置、地區和操作，適合判斷改善是否真的惠及受眾。Performance trace 的時間軸能告訴你「工作發生的順序」，Network waterfall 告訴你「請求間的依賴」。兩者要一起看：請求晚開始，可能是資源未被發現；請求早已完成但元素仍不出現，可能是渲染被 JS 或 CSS 擋住。

## 書籍逐頁核對｜紙本頁 1-6～1-19

這一節不是只有列工具名稱，而是把「找到問題」和「在提交程式碼時防止退化」串起來：

1. **1-6～1-8：PageSpeed Insights。** 書中示範輸入 URL 後查看速度分數、指標與資源統計。閱讀報告時要把指標值與診斷建議分開：分數只是摘要，建議項目提示可能的原因，仍需回到頁面量測確認。
2. **1-8～1-10：WebPageTest。** 書中展示可調整測試地點、瀏覽器與條件。這適合比較地理距離或網路條件造成的差異；報告若比 PageSpeed 慢，也可能只是設定不同，不能直接說哪個工具「比較準」。
3. **1-10～1-12：Lighthouse。** 作者展示 Chrome 擴充與 DevTools 入口，以及效能、無障礙、最佳實務等面向和改善建議。書中畫面屬出版當時的工具介面；實際操作以目前 DevTools 顯示的欄位為準。
4. **1-13～1-19：Lighthouse CI。** 書中把 GitHub App、repository secret、Actions 工作流程、門檻設定與 Pull Request status check 串成一套流程。門檻未達時可以標記警告或錯誤，使退化在合併前被看見。範例使用的 Action 版本與設定是歷史版本，實作時需查目前官方文件。

**關鍵判讀：** CI 門檻若設得過緊，波動會讓每次提交都失敗；設得過鬆則失去守門效果。先固定測試環境、選代表頁面，觀察數次基準值，再為真正重要的指標或資源大小設定預算。

## 從頭做一次

1. 先固定 URL、登入狀態、設備、網路、快取狀態及測試版本。Lighthouse 連續跑數次，保存結果；波動大時先找第三方腳本、廣告或伺服器回應差異。
2. 在 Network 依 Size 和 Waterfall 找最大資源與串行依賴；在 Performance 錄製同一操作，查看 LCP element、Interaction、Layout shifts、Main thread。
3. 正式環境再看真實使用者的 p75，依行動版／桌面版、地區和頁面分組。若實驗室改善但 RUM 沒變，先檢查實驗室場景是否代表使用者。

## 如何判斷做對了

驗證輸出：保留前後報告、版本、測試條件與判讀理由，讓下一次效能退化能追到變更。

## 問題與解答：工具怎麼搭配

**問題 1：Lighthouse、Network、Performance 分別回答什麼？** Lighthouse 用固定條件找可疑項目與建立基準；Network 瀑布圖顯示資源何時發現、等待與下載；Performance trace 顯示主執行緒何時執行 Script、Layout、Paint。看到圖片晚出現，先用 Network 查發現／下載，再用 Performance 查下載後是否還被渲染工作拖住。

**問題 2：實驗室分數很好，真實使用者指標卻差，誰錯了？** 兩者測的是不同樣本。實驗室測量通常可重現，但無法完整代表各地區、裝置、登入狀態和第三方內容。先將 RUM 按頁面、裝置、網路及版本分群，再在相近條件重現；不要把兩種數字硬當同一實驗。

**問題 3：報告應該保存哪些條件，才可比較？** 至少寫 URL／路由、操作步驟、測試時間、瀏覽器和裝置、網路限速、CPU 限速、快取狀態、資料量及程式版本。若修改前測冷快取、修改後測熱快取，速度差可能只是快取造成。

**問題 4：TBT 高可以直接說使用者的 INP 一定差嗎？** 不行。TBT 是實驗室載入期間的主執行緒阻塞線索；INP 觀察真實互動到下一次畫面更新的延遲。TBT 高值得追查長任務，但要用互動 trace 或真實使用者資料確認實際影響。
