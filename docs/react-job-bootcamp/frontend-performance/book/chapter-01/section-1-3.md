# 1-3 衡量前端效能的重要指標：Core Web Vitals

> 學習目標：能把 LCP、INP、CLS 拆成可行動的根因，而非只記門檻。

**核心觀念：** 現行核心三項是 LCP、INP、CLS。LCP 的良好門檻是 2.5 秒內，INP 是 200 毫秒內，CLS 是 0.1 以下；官方以真實使用者第 75 百分位判定。2021 年資料若寫 FID，需以現行 INP 概念重新理解互動延遲。

**實作與驗證：** LCP 慢時拆 TTFB、資源發現、下載與渲染；INP 慢時拆輸入延遲、處理時間和呈現延遲；CLS 高時找出位移元素及未預留空間的內容。

**常見誤區：** 指標是診斷入口，不是只追求總分的遊戲。

### 指標拆解

LCP 可拆為 TTFB、資源載入延遲、資源下載時間和元素渲染延遲。即使把圖檔縮小，若節省的時間全被 JavaScript 渲染等待吃掉，LCP 仍可能沒有改善。INP 涵蓋輸入到事件處理開始、事件處理，以及處理後到下一次繪製；CLS 則要找出造成位移的元素與觸發時間。

### 練習

在 Performance 面板開啟即時指標，點擊頁面上的一個常用按鈕，記錄 INP 與互動階段；再找一個最主要的 CLS 來源。比起只抄良好門檻，能說出延遲在哪一段更重要。

## 原理拆解

三項指標分別問三個問題：主要內容何時可見、互動後多久看到回應、畫面是否意外移動。LCP 不是「所有資料都下載完」，INP 也不是「事件函式跑多久」，CLS 更不是「所有動畫都算位移」。把指標分解才能找到根因。舉例：圖片只花 200 毫秒下載，但它在導航後第 2 秒才開始請求，優先修正的是資源發現延遲；若點擊 handler 只花 10 毫秒，但主執行緒先被其他 400 毫秒任務占住，INP 仍會差。

## 書籍逐頁核對｜紙本頁 1-20～1-27

- **1-20～1-22：LCP。** 書中用一個逐步載入的頁面說明：當最大可見元素從文字變成圖片，LCP 候選元素也可能改變。它列舉圖片、影片、背景圖片與文字區塊等候選；排查時要先從工具確認「這次測量的最大元素是誰」，不要預設永遠是主圖。
- **1-22～1-23：LCP 改善方向。** 作者依伺服器回應、阻塞時間、資源載入與 CSR 造成的等待分類。現在仍可當作排查地圖，但實際瓶頸要靠 waterfall 和 Performance trace 定位。圖片壓縮只有在下載時間真是主要原因時才會顯著改善 LCP。
- **1-23～1-24：書中使用 FID。** FID 衡量第一次輸入到事件開始處理的延遲；它不涵蓋完整事件處理與呈現。**現行 Core Web Vitals 已使用 INP 取代 FID**，因此書中 FID 門檻、`getFID` 程式碼與優化建議應當作歷史背景；今天要記錄互動的輸入延遲、處理時間與呈現延遲。
- **1-24～1-27：CLS。** 書中以突然插入區塊使按鈕下移的例子，介紹位移分數由影響範圍與移動距離相乘。列出的常見來源包括缺少圖片／iframe 尺寸、動態插入內容、字型載入與等待網路後才更新 DOM。修正時應先找出發生位移的元素並預留空間。

**版本提醒：** 書中圖片與工具列表反映出版時的 FID 時代。現行 LCP、INP、CLS 的定義與良好門檻，請以 [web.dev Core Web Vitals](https://web.dev/articles/vitals) 為準。

## 從頭做一次

1. 對 LCP，先確認最大內容元素究竟是哪張圖或哪段文字，再查 TTFB、資源發現、下載及渲染等待。若文字成為 LCP，字型與 render blocking CSS 也可能是關鍵。
2. 對 INP，錄製最慢的互動，拆開輸入延遲、事件處理及呈現延遲。若事件函式很短卻仍慢，可能是點擊前已有長任務或點擊後的大量 layout。
3. 對 CLS，找出位移時間與來源，檢查圖片尺寸、廣告占位、晚到字型和在既有內容上方插入的新區塊。排除使用者主動觸發、符合規範的位移情境。

## 如何判斷做對了

達標應看真實使用者第 75 百分位的設備分組；單次本機結果只適合診斷，不代表整站通過。

## 問題與解答：從指標找到原因

**問題 1：LCP 慢，要從哪裡拆？** 先確認 LCP 元素究竟是主圖還是文字，再依序看 TTFB、資源被發現的時間、下載時間及下載後的渲染延遲。若圖片直到 JS 執行後才出現在 DOM，單純換格式仍可能不夠；若主要瓶頸是圖片傳輸，再處理尺寸、格式與優先級。

**問題 2：點按鈕卡住，為什麼現在要看 INP 而非只看書中的 FID？** FID 只涵蓋首次輸入開始被處理前的等待；INP 更接近整次互動直到下一次畫面更新的感受。拆成輸入延遲、事件處理、呈現延遲，才能區分主執行緒被別的任務佔住、handler 太重，或畫面更新太慢。

**問題 3：CLS 高一定是圖片沒寫尺寸嗎？** 不是。未預留尺寸的圖片是常見原因，字型替換、廣告、非同步插入的區塊也會推動既有內容。用 DevTools 的位移紀錄找出移動的元素，追查是哪個新內容或尺寸變化造成，再為它預留空間。

**問題 4：三個指標怎麼判定是否達標？** 以現行 LCP、INP、CLS 在真實使用者第 75 百分位觀察；常用良好門檻分別是 2.5 秒、200 毫秒、0.1。分數不是根因。若 p75 不好，先按頁面與裝置切分，再針對較差群體錄製 trace。
