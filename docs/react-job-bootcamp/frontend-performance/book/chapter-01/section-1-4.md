# 1-4 從使用者角度出發：RAIL Model

> 學習目標：依使用者任務分配主執行緒時間，知道哪些工作應立即做、延後做或移出。

**核心觀念：** RAIL 將工作分成 Response、Animation、Idle、Load。它提醒我們在點擊回應、逐幀動畫、閒置工作與載入期間分配主執行緒時間；實際預算要依裝置與任務量測。

**實作與驗證：** 挑一個卡頓互動，錄製事件到下一次 paint 的過程；對動畫觀察 frame time；把非立即必要的工作延到空閒或分片執行。

**常見誤區：** RAIL 是思考模型，不等同於 Core Web Vitals 的評分公式。

### 把模型用在頁面上

Response：點擊後儘早顯示可辨識的回應，例如按鈕禁用或進度狀態。Animation：每幀盡量只做必要的視覺更新。Idle：將分析、預取與非必要整理工作安排到不妨礙主要操作的時段。Load：優先交付使用者此刻需要的內容。這些是工作安排原則，仍應以實測決定是否有效。

### 練習

把一個長事件處理拆成「立即回應、必要計算、可延後工作」。錄製拆分前後的互動 trace，確認下一次繪製更早出現，且後續工作沒有造成新的卡頓。

## 原理拆解

RAIL 的核心是從人的操作節奏安排工作。按下按鈕時，先讓使用者看見系統已收到指令；動畫期間，避免在每幀做大量同步 layout；閒置時再做預取或整理；載入時則先交付最有價值的內容。這不表示所有工作都可以任意延後：資料一致性、提交結果與錯誤回饋仍需要可靠地完成。將一個大任務分片之後，若每片之間沒有讓瀏覽器繪製的機會，體感仍可能沒有改善。

## 書籍逐頁核對｜紙本頁 1-28～1-32

書中以 RAIL 四個字母安排預算：

| 階段 | 書中的思考方向 | 今天怎麼使用 |
| --- | --- | --- |
| Response | 讓使用者在約 100 ms 內感到操作有回應，事件處理工作盡量留出餘裕 | 找輸入延遲與處理時間，先顯示有效回饋，再把非必要計算移出關鍵路徑 |
| Animation | 以 60 FPS 的約 16.7 ms 幀間隔思考，為瀏覽器自身工作預留時間 | 用 Performance 的 frame time 驗證；不把書中 10 ms 工作預算當成每台裝置都相同的硬性規範 |
| Idle | 利用空檔執行非立即必要的工作，避免阻礙下一次輸入 | 分片或延後預取、分析等工作，仍要保證重要任務有完成機會 |
| Load | 讓頁面盡快呈現主要內容並可互動 | 以目前的 LCP、INP、CLS 與產品任務判斷；書中約五秒的示意目標不能取代現行指標 |

**書中圖解重點：** 若主執行緒正執行長任務，使用者輸入會先排隊；即使事件處理本身不長，也會感到延遲。這與前一節的互動指標相連：排查時不能只計算 handler 自己花的時間。

## 從頭做一次

1. 把一次點擊的工作列出：更新按鈕狀態、驗證、資料轉換、發送請求、動畫、分析事件。找出使用者立即需要的最小回應，其餘工作評估延後或分片。
2. 錄製動畫，確認每幀是否有大量 layout、paint 或 JS。若 UI 在請求期間沒有反應，先提供準確的 loading 狀態與防重提交，再處理整體延遲。
3. 把延後工作放到合適時機，但不要假設 idle 一定會發生；重要任務需有可靠的完成路徑。改動後比較回應時間與總完成時間。

## 如何判斷做對了

取捨：過度切片會增加程式複雜度。只有當 trace 顯示任務確實妨礙互動時，才把它改造成排程問題。

## 問題與解答：RAIL 怎麼用

**問題 1：RAIL 的四個字母如何對應真實工作？** Response 看點擊與輸入後是否迅速回應；Animation 看每一幀能否準時產生；Idle 把非立即必要工作安排在空檔；Load 看首屏內容何時可見且可用。它是分配時間的思考模型，不是另一組評分指標。

**問題 2：動畫有 60 FPS 目標，是否代表 JS 可用滿 16.7 ms？** 不能。每幀還需要樣式、排版、繪製、合成與瀏覽器其他工作，JS 必須留出餘裕。先在慢裝置錄製 Frames 和 Main，找出超時幀及其中的工作，再決定減少計算或改動畫屬性。

**問題 3：點擊後要做大量計算，如何維持回應？** 先給必要的視覺回饋，把非關鍵工作分片或安排到空閒時段；純計算且量大時可評估 Worker。不能只把 spinner 顯示出來，卻在同一個長任務裡阻塞主執行緒，因為 spinner 也無法順利繪製。

**問題 4：如何用 RAIL 做一次檢查？** 選一個卡頓操作，標出事件開始、handler、下一次 paint；再看動畫掉幀與載入期間主執行緒是否被非必要任務占用。提出一個調整，重新錄製同一操作比較，而不是只說「感覺順了」。
