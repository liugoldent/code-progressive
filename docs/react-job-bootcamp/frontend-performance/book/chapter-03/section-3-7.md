# 3-7 寫出高效能的 CSS

> 學習目標：能從 trace 分辨樣式重算、強制同步 layout 與 DOM 更新成本。

**核心觀念：** CSS 成本主要來自受影響元素範圍、DOM 數量、頻繁樣式重算和 layout，而不只是 selector 長度。動畫可先考慮 transform／opacity，再用 trace 驗證。

**實作與驗證：** 錄製互動，找 Forced reflow 和過長的 style/layout。合併同一輪事件的讀取與寫入，減少大範圍 class 切換。

**常見誤區：** 只微調 selector 卻忽略反覆讀寫 DOM，通常無法解決卡頓。

### 找出真正昂貴的 CSS 更新

一個聊天列表每收到訊息就讀取捲動高度、寫入 DOM、再讀取高度，可能在同一幀重複觸發 layout。先錄製並確認 Forced reflow，再把幾何讀取集中、減少更新範圍，必要時以 requestAnimationFrame 合併視覺更新。

若時間主要花在 JavaScript 運算，改 selector 或使用 `contain` 也不會解決根因。優化前後比較的是實際 frame time、style/layout 時間和使用者可見的卡頓。

## 原理拆解

CSS 效能常被誤解成 selector 越短越好。實際瓶頸更可能是每次互動都讓大範圍 DOM 重新計算樣式、反覆量測布局或觸發昂貴 paint。你需要知道哪些元素被影響、每秒更新幾次，以及每次更新是否迫使瀏覽器同步取得布局結果。`contain` 等技術可以縮小某些影響範圍，但有語意與布局副作用，應在量測後局部採用。

## 從頭做一次

1. 重現一個卡頓場景，例如輸入搜尋時列表每字都重繪。在 Performance 看 Recalculate Style、Layout 和 Paint 是否隨輸入重複出現。
2. 找出在事件處理內交錯的幾何讀取和 DOM 寫入；先收集所需尺寸，再批次更新 class 或 style。必要時縮小選擇器影響範圍與 DOM 子樹。
3. 重測每次輸入的處理時間及下一次繪製。若成本仍在 JS 過濾演算法，繼續改 CSS 不會解決。

## 如何判斷做對了

不要迷信「selector 越短越快」；真實頁面中 DOM 量、更新頻率與 layout 範圍通常更關鍵。

## 書籍逐頁核對｜紙本頁 3-63～3-72

### 3-63～3-67：選擇器成本與可維護性

書中說明 CSS 選擇器匹配常從右邊的關鍵選擇器往左確認祖先關係，因此 `#ironman .article h2` 需要從候選 `h2` 往上檢查。它列出 ID、class、元素、兄弟、子代、後代、屬性與偽類等選擇器的相對成本；但也提醒 ID 與 class 的速度差通常很小。不要為了微小的匹配速度把所有元素改成 ID。書中主張避免不必要的通用選擇器、避免在已明確的 ID/class 前再加元素類型；有精確父子關係時，子選擇器比任意深度的後代選擇器更具體。

頁 3-67 也提醒 CSS 屬性會被後代繼承，無須在每層都重複宣告。同頁列 `:nth-child`、`filter`、陰影等可能較昂貴的選擇器或視覺屬性；這不能當作一律禁用清單，需先在真實頁面量測 Style／Paint 是否確實成為瓶頸。

### 3-68～3-70：動畫與 Reflow／Repaint

書中用 hover 的 `scale` 動畫說明 `transition: all` 可能讓非預期屬性也參與動畫；已知要動的屬性時，可明確指定它。接著把 CSS 變動連回前節渲染管線：改 margin、padding、width、height、位置、字體相關值或視窗大小可能觸發 Layout；若只想讓物件移動，`transform` 在適當情況下可減少 Layout。書中也示範在滾動期間暫時關閉 hover 效果，避免大量滑過元素時觸發額外繪製。這招有互動體驗成本，應僅在實測有問題的頁面使用。

### 3-71～3-72：Critical CSS 與預載的界線

外部 CSS 會影響首次繪製，書中介紹把首屏真正需要的少量 Critical CSS 內嵌在 HTML，讓瀏覽器不用等整份外部樣式表就能繪製首屏。代價是 HTML 變大，而且內嵌 CSS 不能像獨立檔案那樣方便快取；若抽取過多，可能拖慢 HTML 傳輸。對 CSS 中才會被發現的關鍵背景圖，可以考慮在 HTML 中提早 preload；非關鍵 CSS 可另安排載入時機。應先看 Network waterfall、LCP 與 CSS 覆蓋率，再決定抽取範圍。

## 問題與解答：CSS 效能要看哪裡

**問題 1：選擇器很長就是主要瓶頸嗎？** 不一定。實際成本還取決於受影響的 DOM 範圍、變更頻率，以及是否引起 style recalculation 和 layout。先用 Performance trace 看樣式計算是否真佔時間，再決定是否修改選擇器。

**問題 2：點一下 class 就卡，如何查？** 看該 class 是否影響大量子孫元素、改變幾何尺寸或讓 JS 立即讀取 layout。比較變更前後的 Recalculate Style、Layout 和 Paint；必要時縮小樣式作用範圍、批次讀寫 DOM。

**問題 3：Critical CSS 為何不把整份 CSS 全內嵌？** 只把首屏必需的樣式提早提供，可減少阻塞；把所有樣式塞進 HTML 則讓文件變大、失去獨立快取，還可能拖慢後續頁面。要測首屏所需樣式、HTML 大小與重複導覽的快取效果。

**問題 4：動畫改用 `transform` 是否一定更快？** 它通常可避開反覆 layout，但若元素很大、需要重新繪製或產生過多圖層，仍可能掉幀。用 Frames 與 Paint 紀錄驗證，而非只依 CSS 屬性名稱下結論。
