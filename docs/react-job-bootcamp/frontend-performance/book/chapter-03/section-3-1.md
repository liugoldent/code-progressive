# 3-1 瀏覽器的架構演進史

> 學習目標：理解主執行緒、Worker 與網路程序的分工，避免用錯優化手段。

**核心觀念：** 現代瀏覽器將網路、渲染、GPU 等工作分工處理；頁面的 JavaScript、樣式計算與 layout 仍可能在主執行緒競爭時間。理解進程與執行緒是為了判斷哪種工作能移走，哪些 DOM 操作不能。

**實作與驗證：** 在 Performance trace 標出網路等待、主執行緒長任務及合成階段。先確定瓶頸在哪一段，再選擇 Worker、快取或 DOM 變更。

**常見誤區：** 多進程架構不代表頁面 JS 自動平行；DOM 不是 Worker 可直接操作的物件。

### 用架構知識判斷優化方向

假設 Performance trace 顯示點擊後有 400 毫秒 JSON 解析與排序：這類純計算可考慮切片或 Worker。若 trace 顯示主要時間是 Layout：把排序搬到 Worker 可能幫助有限，應先減少 DOM 更新與強制同步量測。網路等待、計算與渲染要分開處理。

### 練習

在一份 trace 中標註三段：等待網路、執行 JS、style/layout/paint。指出最長的一段及下一步假設，避免看到「主執行緒」就直接引入 Worker。

## 原理拆解

瀏覽器把工作分配到不同程序或執行緒，但網頁仍有競爭同一主執行緒的工作，例如事件處理、樣式計算及布局。這能解釋為何下載已完成後，頁面仍可能因 JS 執行而白屏或無回應。Worker 適合移走可隔離的純計算；它不能直接讀寫 DOM。因此遇到卡頓先問「卡在網路、計算，還是布局繪製」，再決定改請求、演算法或 DOM。

## 從頭做一次

1. 在 trace 中圈出網路等待、JS 執行、style/layout/paint。把問題分類：等待資料、CPU 純計算、DOM 更新或繪製；每類對應不同工具。
2. 如果是大型資料排序造成長任務，先考慮減少資料、分片或 Worker；如果是布局重算，先減少讀寫交錯與 DOM 變更範圍。
3. 改動前寫出「若假設正確，trace 哪一段會縮短」。改動後檢查該段是否真的縮短，避免只是把工作移到另一段。

## 如何判斷做對了

Worker 不能直接操作 DOM；瀏覽器多進程架構也不會讓頁面 JavaScript 自動平行。

## 書籍逐頁核對｜紙本頁 3-2～3-8

### 3-2～3-4：早期單一程序的三個問題

書中從 2007 年前後的 Single Process 瀏覽器談起：頁面、外掛與 JavaScript 等工作集中在同一程序。第一個問題是**不穩定**：某個功能或外掛崩潰可能拖垮整個瀏覽器。第二個是**不流暢**：若某個 JavaScript 任務陷入無限迴圈，其他頁面工作也可能受牽連。第三個是**安全**：若缺少隔離，外掛或頁面腳本取得不應存取的系統資源時，風險擴大。這些是架構演進的背景，並非「多開一個程序就能讓任何網頁更快」的結論。

### 3-5～3-7：多程序隔離與成本

書中以 Chrome 的 Browser Process、Renderer Process、Plugins Process 示意多程序架構；頁 3-6 說明隔離帶來的穩定性，以及 Renderer／外掛程序在 sandbox 中執行以縮小權限範圍。頁 3-7 再加入 Network Process 與 GPU Process 等角色，讓網路與圖形相關工作可有自己的執行空間。不同程序必須透過 IPC 通訊，因此程序切分有記憶體用量與通訊成本；不能無限制地拆分。書中的「每個 Tab 一個 Renderer」是教學示意，實際程序分配仍受瀏覽器版本、站點隔離與情境影響。

### 3-8：往服務導向架構演進

書中最後介紹 Chrome 的 Service Oriented Architecture：把瀏覽器中的功能視為服務，依硬體資源條件與成本決定是否分到不同程序。高資源裝置偏向隔離與穩定，受限裝置則需控制程序數與記憶體。此節的用途是理解後續談的 Renderer 工作來自哪裡；優化網頁時仍要量測自己頁面的主執行緒、網路、渲染與 GPU 成本。

## 問題與解答：瀏覽器分工與瓶頸

**問題 1：多程序瀏覽器是否讓每個頁面的 JS 自動平行？** 沒有。瀏覽器把網路、渲染、GPU 等工作分工，並隔離不同站點；但單頁主要 JS、樣式計算和 DOM 工作仍可能爭用主執行緒。若一次同步計算 500 ms，頁面仍可能在這段時間無法回應。

**問題 2：為什麼不把所有工作丟到 Web Worker？** Worker 適合不依賴 DOM 的計算；它不能直接修改頁面 DOM，主執行緒與 Worker 間傳資料也有成本。先在 Performance trace 確認是計算長任務，再衡量搬移後的訊息與複製成本。

**問題 3：程序隔離的好處與代價是什麼？** 隔離有助於穩定性、安全性和單一頁面故障控制，但各程序需要記憶體與溝通。書中回顧單一程序的風險、多程序架構和服務導向演進；這些架構知識用來判斷瓶頸所在，而不是要求前端自行配置瀏覽器程序。

**問題 4：觀察到畫面慢，如何判斷是網路還是主執行緒？** Network waterfall 若顯示資源仍在等待或下載，先處理網路依賴；資源已到齊、Performance 的 Main 卻有長任務，便追查 JS、樣式與排版。兩者可能同時存在，要以時間線確認順序。
