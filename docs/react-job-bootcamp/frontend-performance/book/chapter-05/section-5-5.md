# 5-5 Stale While Revalidate

> 學習目標：能計算 stale-while-revalidate 視窗並選擇可容忍舊值的內容。

**核心觀念：** 在允許的陳舊期限內先顯示舊內容，再背景更新。HTTP 指令和前端資料層的同名策略用途相似，但控制範圍不同。

**實作與驗證：** 為一般內容定義可容忍的舊資料時間，測新鮮、剛過期、超過期限與背景更新失敗時的畫面。

**常見誤區：** 權限、付款與關鍵庫存等決策不宜依賴可能過期的快取。

### 計算允許舊資料的時間窗

例如 `max-age=60, stale-while-revalidate=300`：前 60 秒是新鮮，接下來最多 300 秒可在背景更新期間先使用舊回應；再往後就不能只靠這個指令直接提供舊值。實際快取行為還受瀏覽器與中間快取實作影響，需在目標環境測試。

對 UI 資料層，明確標示「顯示舊值、背景更新、更新成功／失敗」狀態。付款、權限或交易價格若不能容忍舊值，應改用更嚴格的新鮮度策略。

## 原理拆解

Stale-while-revalidate 讓快取在指定時間窗內先回舊資料，再嘗試背景更新。它的價值是降低使用者等待，但代價是短暫顯示過期資料。HTTP 回應的 `stale-while-revalidate` 由快取層處理；前端資料庫中的同名策略由應用程式控制，還要處理載入狀態、通知 UI 與競態。使用前先問：這筆資料舊幾分鐘是否會做出錯誤決策？

## 從頭做一次

1. 對一類內容寫下允許舊值多久，例如公告清單可容忍幾分鐘，付款權限則通常不能容忍。設定 max-age 和 stale-while-revalidate 後，測不同時間點是否回舊內容、何時背景更新。
2. 對前端資料快取，區分「目前顯示的是快取」與「背景更新中」。若更新失敗，決定保留舊值、顯示錯誤或要求重新整理。
3. 記錄競態：使用者切換查詢條件後，舊請求回來不能覆蓋新條件的結果。

## 如何判斷做對了

SWR 改善主觀等待，但資料新鮮度是明確取捨，不能默默用在關鍵決策。

## 書籍逐頁核對｜紙本頁 5-37～5-46

### 5-37～5-39：HTTP 指令與應用程式資料快取是不同層次

書中先介紹 HTTP `Cache-Control: max-age=1, stale-while-revalidate=59` 的概念：在新鮮期內直接使用快取；之後的一段容許時間可先回舊內容，同時在背景重新驗證，讓下次取得更新版。這主要作用於 HTTP 快取層。接著書中轉向 React 應用的 API 資料：即使 HTTP 快取可用，應用仍可能希望在畫面 state 中即刻顯示先前資料、背景再取最新版；SWR、React Query 等函式庫處理的是這一層的資料生命週期。

### 5-39～5-45：寶可夢列表的手寫 Hook

書中 demo 使用 Pokémon API 的 offset／limit 分頁。切換 offset 時若每次都清空列表等回應，使用者會看到空白 loading。手寫 `useStaleWhileRevalidate` 的想法是：把請求參數組成 cache key；若記憶體中已有相同 key 的資料，先放進 state 顯示；同時發新請求，回應到達後更新 cache 與畫面。書中還加入一個隨機字串，刻意讓每次 API 回應都不同，好讓讀者看出「舊資料先顯示，後來更新」的兩個階段。

範例中 `App` 切換 offset，列表元件使用 Hook 取得 `data` 與 `isLoading`。書中指出 `fetcher` 函式如果每次 render 都換引用，可能造成不必要的 effect 執行，因此示範比較參數內容。這是教學性簡化範例；真實產品還需處理請求競態、過期時間、錯誤、重試、取消、失焦重驗證及跨元件共享，不應把手寫 Hook 當作成熟資料快取函式庫的完整替代。

### 5-46：維持新鮮度與畫面連續性

本節的決策重點是：資料很快過期時，單純「只用快取」可能不合適；但每次都等最新回應才顯示也會造成畫面空白。Stale While Revalidate 在可容忍短暫舊資料的列表、探索內容等場景，兼顧立即回饋與後續更新。涉及帳戶餘額、交易狀態或不可容忍舊資料的操作，則要更嚴格地定義新鮮度與確認時機。

## 問題與解答：先顯示舊資料的條件

**問題 1：Stale While Revalidate 的流程是什麼？** 若有可用快取，先顯示舊結果，同時在背景請求新結果；新資料到達後更新畫面與快取。書中的寶可夢列表 Hook 用這種方式避免每次切頁都先空白等待。HTTP `stale-while-revalidate` 指令與應用資料層同名策略相似，但控制的是不同快取層。

**問題 2：哪些資料不適合先顯示舊值？** 權限、付款、關鍵庫存等若舊值會導致錯誤決策，應先確認新鮮度。一般文章列表或非關鍵展示資訊可容忍較短暫陳舊；要明確定義「最多可舊多久」。

**問題 3：背景更新失敗怎麼辦？** 若舊資料仍在可接受期限內，可繼續顯示並標記更新失敗；超過期限則應提示無法確認最新狀態。避免把網路錯誤默默吞掉，讓使用者誤以為資料剛更新。

**問題 4：快速切換頁籤會不會舊回應覆蓋新頁資料？** 會，若沒有按查詢鍵保存資料或取消／忽略過期回應。書中手寫 Hook 的概念要延伸到實務時，需處理請求競態、快取鍵與元件卸載，並測快速切換與慢網路。
