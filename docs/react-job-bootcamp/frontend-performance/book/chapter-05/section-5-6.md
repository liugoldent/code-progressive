# 5-6 升級 HTTP 版本

> 學習目標：能看出協定改善了哪些傳輸成本，以及哪些依賴仍然串行。

**核心觀念：** HTTP/2 的多工與標頭壓縮改變了 HTTP/1.1 時代合併檔案與切分網域的取捨；HTTP/3 基於 QUIC，在部分網路情境降低連線成本。

**實作與驗證：** 查看 Network 的 Protocol 欄和 waterfall，確認實際協定與請求依賴。比較關閉舊式 domain sharding 前後的連線時間。

**常見誤區：** 協定升級不能修正慢 TTFB、過大的 JS 或串行 API 依賴。

### 用 waterfall 看協定問題

先確認 Network 的 Protocol 欄真的顯示 h2 或 h3，再觀察是否有排隊、過早建立太多跨來源連線，或 API 彼此串行。HTTP/2 多工可減少 HTTP/1.1 的部分連線限制，但一個資源依賴另一個資源的邏輯順序仍在。

練習：找出瀑布中的最長串行鏈，估算每段等待時間。若主要時間在遠端 API 的 TTFB，單純升級前端靜態資源協定不會有太大收益。

## 原理拆解

HTTP/1.1 時代，多個請求常受連線數與阻塞影響，因此有人合併大量資源或把資源拆到不同網域。HTTP/2 多工和標頭壓縮改變這些取捨；HTTP/3 又改變底層傳輸行為。但協定只處理傳輸路徑的一部分。若 HTML 先下載 JS、JS 執行後才發現主圖，這個邏輯依賴仍存在；若 origin API 本身要兩秒，協定升級無法消除伺服器工作。

## 從頭做一次

1. 在 Network 開啟 Protocol 欄，確認靜態資源與 API 實際使用 h2／h3，而不是以伺服器設定推論。
2. 比較瀑布中的 DNS、連線、排隊與 TTFB；找出最長串行鏈，例如先下載 JS 才發現圖片、先完成 API A 才開始 API B。
3. 移除為 HTTP/1.1 時代設計的過度 domain sharding，並在目標地區、網路條件重測。

## 如何判斷做對了

多工降低部分連線成本，但不會讓過大的圖片、長主執行緒任務或慢 origin API 自動變快。

## 書籍逐頁核對｜紙本頁 5-47～5-55

### 5-47～5-50：HTTP/1.1 為何催生合併資源等技巧

書中先談 HTTP/1.1 在連線上的限制：請求排隊、同一來源可同時開啟的連線數量有限，舊式 pipelining 也可能因前面的回應慢而產生隊頭阻塞。Network waterfall 的 Queueing 可以讓讀者看到等待時段。請求與回應標頭也占用位元組，書中指出壓縮回應體不代表標頭也被壓縮。在這些條件下，過去常用 bundling、CSS sprites、inline script 和 domain sharding 等方法減少請求或增加並行機會；這些方法的收益需隨協定版本重新評估。

### 5-50～5-54：HTTP/2 的多工與標頭壓縮

書中介紹 HTTP/2 以 stream 和 frame 表示多個請求／回應，在同一連線上交錯傳輸，不用等某個完整回應結束才開始下一個。它也有標頭壓縮；但書中特別指出 HTTP/2 的多工**未消除 TCP 層的隊頭阻塞**。頁 5-52～5-54 再談當時的 Server Push：伺服器可主動送出預期會被需要的資源，但若推錯或使用者已有快取，反而浪費頻寬。這是書中的歷史機制，今天是否支援及值得使用應另外查現行瀏覽器與伺服器文件；不要直接照舊例部署。

### 5-54～5-55：HTTP/3 的關鍵差異

書中指出 HTTP/3 不再建立在 TCP 上，而是以 QUIC 在 UDP 上提供連線、加密與可靠傳輸機制，目的之一是改善 TCP 層因遺失封包造成的多 stream 阻塞。這不等於「所有站點改成 HTTP/3 都一定更快」；收益取決於網路品質、伺服器與 CDN、瀏覽器支援。書中也提醒升級協定常需確認 HTTPS、伺服器和 CDN 配置，並用 DevTools 檢查實際請求用的是哪個協定。

## 問題與解答：HTTP 協定升級的實際收益

**問題 1：HTTP/1.1 時代為何流行合併檔案與分散網域？** 連線數與請求往返限制，使很多小資源排隊；合併可減少請求，分散網域可增加同時連線。這些技巧也帶來巨大檔案、快取粒度差與額外 DNS／連線成本。

**問題 2：HTTP/2 的多工解決了什麼？** 多個請求可共用同一條連線的多條 stream，並使用標頭壓縮，因此不必無條件沿用過度合併或 domain sharding。它沒有讓依賴後一個 API 結果才發出的下一個 API 自動平行。

**問題 3：HTTP/3 又改變了什麼？** 它以 QUIC 為基礎，在某些網路條件下改善連線建立與傳輸中斷時的表現；實際收益取決於網路、伺服器、CDN 與瀏覽器支援。不要把協定升級當作修復巨大 JS 或慢後端的替代品。

**問題 4：怎麼知道用戶真的走到新協定？** 在 DevTools Network 打開 Protocol 欄，檢查實際請求協定；對照 waterfall、TTFB 與不同網路條件。伺服器設定支援 HTTP/3，不代表每個使用者每次都以 HTTP/3 連線。
