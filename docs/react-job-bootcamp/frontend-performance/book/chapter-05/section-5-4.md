# 5-4 Application Shell Architecture

> 學習目標：能分辨「骨架很快」與「主要任務真的可用」。

**核心觀念：** 把固定導航、基礎樣式和外框先交付，資料到達後再填入。可與 Service Worker 配合，但骨架顯示快不表示主要任務已可完成。

**實作與驗證：** 記錄 shell 出現、資料顯示和可互動的時間；骨架與內容尺寸接近，測試載入失敗與離線提示。

**常見誤區：** 把整個巨大的 SPA bundle 當作 shell 預快取，可能令首次載入更慢。

### Shell 的完成度要分層

把時間線記成：HTML 到達、外框可見、主要資料可見、第一個核心操作可用。骨架屏只能改善其中一段感受；若資料 API 三秒才回，使用者仍需等待。版面占位應接近實際內容尺寸，並提供錯誤、重試與離線狀態。

練習：對同一頁比較「白屏」、「有 shell 但無資料」、「內容可操作」三個時間點，再看哪一段最長。若 shell 自身依賴巨大 bundle，優先減少它的資源成本。

## 原理拆解

Application Shell 將導覽、外框和穩定 UI 先交付，使使用者在資料到達前知道自己位於哪個頁面。它可以改善感知速度，也便於離線 fallback，但不會神奇縮短資料 API。若 shell 的 CSS／JS 很大，第一次下載仍可能拖慢頁面。應區分「外框已見」、「主要資料已見」、「核心操作可用」三個里程碑；只量第一個會過度美化成果。

## 從頭做一次

1. 把頁面分成固定導航、主要資料、互動功能三層，記錄每層實際可用的時間。Shell 應小且穩定，不應帶入所有頁面的 bundle。
2. 為主要資料保留接近最終內容的空間，避免資料到達時造成 CLS；失敗時提供重試或離線說明。
3. 在慢網及離線下測試：使用者是否能識別目前畫面、是否知道仍在等待、是否可以完成至少一部分任務。

## 如何判斷做對了

先顯示漂亮的 spinner 或 skeleton，卻讓 API 一直慢，並不算完成效能優化。

## 書籍逐頁核對｜紙本頁 5-31～5-36

書中把 Application Shell 分成兩塊：相對穩定的 UI 骨架（例如導覽列、頁框、頁尾）與經常更新的動態內容。Service Worker 可快取 Shell，讓回訪者快速看到可操作或至少可辨識的介面；動態資料再向網路取得。頁 5-32～5-34 用離線維基百科示例展示：離線時仍顯示固定殼層和部分已快取內容，連線恢復後再取新資料。書中也示範 JSON 可由 Service Worker 快取，但須評估內容更新頻率，不能把所有動態資料都當成永久靜態檔案。

頁 5-35 對首次與再次造訪做區分。首次造訪需要註冊 Service Worker 並下載 Shell 資源，可能比沒有這套機制更慢；回訪才可能因快取取得明顯收益。書中引用舊版 3G 測試圖比較首次與回訪的 FMP，目的是說明評估要涵蓋不同訪問階段，而非保證每站達到相同秒數。頁 5-36 也提醒不是所有瀏覽器都支援 Service Worker，未支援時網站仍應能正常工作。App Shell 適合穩定骨架占比大、回訪頻繁且可容許內容分段到達的應用；若頁面主要是即時內容，骨架先出現卻長時間空白，使用者體驗可能反而不好。

## 問題與解答：App Shell 不是完整內容

**問題 1：Application Shell 指什麼？** 它是可重用的頁面外框，例如導覽、基本樣式與固定控制項；資料到達後再填入主內容。與 Service Worker 配合時，重訪可較快顯示外框，但這不等於使用者要看的資訊已到達。

**問題 2：骨架畫面很快出現，是否代表體驗很好？** 不一定。若主內容還要等很久，使用者仍無法完成任務。應分別量 shell、主要內容與可互動時間；骨架尺寸要接近真實內容，避免載入後位移。

**問題 3：離線時 App Shell 該做什麼？** 可顯示已快取的導覽與離線提示，但不可讓使用者誤以為未同步資料就是最新資料。對可離線完成的功能設排隊或同步狀態；對不能完成的操作清楚說明限制。

**問題 4：為何不把整個 SPA bundle 都預快取？** 首次下載與安裝可能因此變得更重，低頻功能也會占空間。應選真正構成 shell 的最小資源，再測首次訪問與重訪；不能只看重訪快就忽略首次成本。
