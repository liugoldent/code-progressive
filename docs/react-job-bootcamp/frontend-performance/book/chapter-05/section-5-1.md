# 5-1 HTTP Cache

> 學習目標：能為 HTML、帶 hash 靜態檔與敏感 API 選不同的 HTTP 快取策略。

**核心觀念：** Cache-Control 控制新鮮度；ETag／Last-Modified 協助重新驗證。帶內容 hash 的靜態檔可長期快取，入口 HTML 則須能及時發現新版本。no-cache 可存但使用前驗證；no-store 要求不存。

**實作與驗證：** 以 Network 看首次載入、重新整理及新部署後的狀態與 304。檢查 HTML、靜態檔、API 的回應標頭是否符合資料敏感度。

**常見誤區：** 沒有 hash 的檔案長期 immutable，會讓使用者長期拿到舊版本。

### 三種回應的快取設計

```http
# 內容 hash 靜態檔
Cache-Control: public, max-age=31536000, immutable
# 入口 HTML
Cache-Control: no-cache
# 敏感回應
Cache-Control: no-store
```

部署時先上傳新 hash 檔，再更新 HTML；舊檔保留一段時間，避免使用者持有舊 HTML 時請求變成 404。測試首次、重新整理、重新部署後三種情境。注意瀏覽器前進／後退可能由 bfcache 恢復，不能用它直接推斷 HTTP cache 行為。

## 原理拆解

HTTP cache 有「新鮮直接重用」和「過期後重新驗證」兩種常見節省。`max-age` 決定新鮮期限，ETag／Last-Modified 可讓伺服器在未變更時回 304。帶內容 hash 的檔名一旦內容改變就會換 URL，因而適合長期 immutable；HTML 通常維持相同 URL，需能迅速取得新版資源引用。資料是否能共享快取還要考慮登入與權限。

## 從頭做一次

1. 用 curl -I 或 Network 檢查 Cache-Control、ETag、Age、Vary，分別測首次請求、重新整理及新部署後請求。
2. 帶內容 hash 的靜態檔可長期 immutable，HTML 通常要重新驗證或短 TTL。部署時先上傳新檔再切換 HTML，並保留舊 hash 檔一段時間。
3. 對含私人資料的 API 檢查是否被共享快取；對需要避免儲存的回應使用合適的 no-store。

## 如何判斷做對了

`no-cache` 可儲存但重用前需驗證；`no-store` 才是不儲存。瀏覽器前進／後退還可能由 bfcache 恢復，不能據此推斷 HTTP cache。

## 書籍逐頁核對｜紙本頁 5-2～5-14

### 5-2～5-5：先想清楚快取何時有效

書中以重複取用圖片、API 資料為例，說明快取是把可能再次使用的結果保留一段時間，省去網路請求、伺服器處理或重新運算。Cache Hit 是可直接用到既有內容；Cache Miss 則要回來源取新內容。Hit 比率高不必然代表正確，因為內容如果已過期，仍被當成命中會讓使用者看到舊資料。書中區分瀏覽器私有快取與可供多用戶共用的快取，也列應用程式／CDN／資料擷取函式庫等不同層次；每層的有效期與資料範圍需分別設計。

### 5-6～5-8：新鮮度由回應標頭控制

頁 5-6 先介紹較早的 `Expires` 絕對時間，然後改用 `Cache-Control` 作相對時間與策略。`max-age=60` 表示回應可在一定時間內視為新鮮；`no-store` 指不要儲存；`no-cache` 並不是完全不快取，而是再次使用前要向伺服器驗證；`private` 限制共用快取使用；`public` 允許共用快取考慮儲存；`s-maxage` 針對共用快取。書中提醒 Expires 可能受客戶端時鐘影響，當兩者都存在時以 `Cache-Control` 的規則為主。

### 5-8～5-11：過期後的條件式驗證

書中先以 `Last-Modified`／`If-Modified-Since` 讓瀏覽器問「此日期後改過嗎」，未變時由伺服器回 `304 Not Modified`，省下回應體。但秒級時間戳可能漏掉極短時間內多次更動，或把無實質內容差異的更新誤判為變更。接著以 `ETag`／`If-None-Match` 比較資源版本標記，未變時同樣可回 304。這兩類「驗證快取」仍要發請求，但通常不用重傳整份內容；與 max-age 未過期時直接使用快取的成本不同。

頁 5-10～5-11 另外談多人同時編輯時避免覆蓋資料。**校正書中此處的標頭示意**：若目的在於「只有伺服器版本仍等於我讀到的版本時才允許寫入」，應使用 `If-Match` 與 ETag，版本不符可回 `412 Precondition Failed`；`If-None-Match` 通常用於 GET 的條件式驗證（也有 `*` 用於防止覆蓋既有資源的情境）。閱讀時不要把兩者混成同一用途。

### 5-12～5-14：Cache Busting 與記憶體快取

書中以 CSS 檔案內容更新但 URL 不變造成舊版繼續被快取的問題，引入內容雜湊檔名：只要內容改，檔名和 URL 也變，瀏覽器會把它當新資源；HTML 入口本身則需能重新驗證或取得新版，以引用新檔名。這種策略要讓 HTML 和靜態資源的快取期限不同。頁 5-14 又對照 DevTools 中 `from memory cache`、`from disk cache`；書中坦言瀏覽器如何決定資源放在哪一層的細節不完全公開。實務上應以回應標頭、URL 穩定性及實測行為判斷，不要把 Memory Cache 當成可精確配置的儲存層。

## 問題與解答：HTTP 快取怎麼設

**問題 1：`no-cache` 和 `no-store` 差在哪？** `no-cache` 允許儲存回應，但使用前須重新驗證；`no-store` 要求不要儲存。前者常用於需要確認是否更新的資源；敏感內容是否需要 `no-store` 還要依資料與隱私需求判斷。

**問題 2：有 `max-age` 的資源過期後會發生什麼？** 瀏覽器可帶 `If-None-Match` 或 `If-Modified-Since` 做條件式請求；伺服器若確認未變更，回 304 而不重送完整內容。書中同時提到 ETag、Last-Modified；要注意 `If-Match` 主要用於條件式修改與併發控制，不是一般取得 304 的請求標頭。

**問題 3：為何帶 hash 的 JS 可長期快取，HTML 卻通常不能同樣處理？** 檔名含內容 hash 時，內容一變 URL 也變，舊檔長期保存較安全；入口 HTML 若長期不重新驗證，就可能一直指向舊資源。發布新版本時應讓 HTML 能及時發現，靜態 hash 資源則可長期重用。

**問題 4：怎麼測快取設定？** 在 Network 中分別記錄首次載入、重新整理和新部署後的 Status、Size、Response Headers。確認預期資源是命中快取、回 304，還是取得新版；並測登入切換、語言切換後沒有拿錯內容。
