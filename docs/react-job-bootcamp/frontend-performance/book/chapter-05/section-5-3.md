# 5-3 CDN

> 學習目標：能區分 CDN 地理收益、命中收益與錯誤的共用快取風險。

**核心觀念：** CDN 將可快取內容放到靠近使用者的節點；收益取決於 cache key、TTL、命中率、資源版本與原站資料位置。

**實作與驗證：** 比較不同地區、冷／熱命中的 TTFB。確認 query、cookie、語系及登入狀態是否應進入 cache key，觀察 Age 或供應商命中標頭。

**常見誤區：** 共用快取若忽略個人化條件，可能讓使用者看到他人的內容。

### 命中率以外還要看正確性

同一 URL 若會依語言、地區、cookie 或權限回傳不同內容，快取鍵或 Vary 必須反映差異；否則命中率再高也可能送錯資料。先區分「公開共享」、「私人」、「不可快取」三種回應，再設 CDN 規則。

從不同地區測第一次與第二次請求的 TTFB，檢查 Age 或供應商命中標頭，並驗證更新後 purge／版本化是否生效。若 origin 資料查詢仍很慢，CDN 只會幫到可快取的部分。

## 原理拆解

CDN 將可共享的內容儲存在靠近使用者的節點，降低到 origin 的往返與負載。但「命中」的前提是兩個請求真的可以分享同一回應；語言、地區、cookie、權限與 query 參數都可能改變內容。快取鍵過粗會送錯內容，過細會讓命中率低。內容 hash 檔可安全長快取；動態頁面則要先建立清楚的共享界線與清除策略。

## 從頭做一次

1. 先把回應分類為公開共享、私人或不可快取；公開內容再定義 cache key 是否包含 query、語系及地區。
2. 從不同地區測冷／熱請求，檢查 TTFB、Age、命中狀態與 origin 負載。更新資源後測 purge 或內容 hash 切換是否生效。
3. 用兩個不同使用者帳號交叉檢查個人化頁面，確認 CDN 不會因忽略 cookie 或權限而送錯內容。

## 如何判斷做對了

如果瓶頸是遠端資料庫查詢，單純把 HTML 渲染移到 edge 或 CDN 前面未必能解決。

## 自我檢查

- 我能否指出這個技巧改善的是傳輸、載入、主執行緒、渲染、記憶體，還是資料新鮮度？
- 我是否保存相同條件下的改動前後證據，並檢查副作用？

## 書籍逐頁核對｜紙本頁 5-25～5-31

書中把 CDN 定義為在多個地理位置部署邊緣節點，讓使用者向較近或較合適的節點取資源。若邊緣快取命中，就不必每次回源站；未命中才向上游或 origin 取回並保留結果。除了降低延遲與來源流量，書中還提到跨區域可用性、故障轉移，以及 CDN 服務常提供的 DDoS 防護。這些是可能的能力，仍要看供應商方案與配置。

頁 5-27～5-28 用 DNS、負載平衡器、Cache Server 的簡化架構追蹤一次請求：使用者解析域名、被導向某個邊緣節點、該節點判斷快取是否命中，必要時回源站。這讓「CDN 加速」能被拆成可觀察的 DNS／連線／邊緣命中／回源階段，而不是抽象的一鍵加速。

頁 5-28～5-30 回答常見疑問：CDN 多半是針對特定域名啟用，網站可保留自己的域名；適合放較少變動的圖片、影音、CSS、JS，也可依業務需求快取其他回應。內容更新時須安排 URL 版本化、失效或清除快取；大幅變動或個人化內容若策略不當，可能讓使用者拿到舊內容或不該共用的資料。書中列出幾家 CDN 業者供探索，選用前仍要看地區、成本、快取規則與實測延遲。

頁 5-30～5-31 有一張 Memory Cache → Service Worker Cache → Disk Cache → CDN Cache 的簡化優先序示意。書中也提醒 Service Worker 和記憶體快取的實際互動更複雜，不能把這個箭頭當成所有瀏覽器、所有請求都固定經過的順序。驗證時應在 DevTools Network 看實際來源、回應標頭與 Service Worker 是否控制該頁。

## 問題與解答：CDN 何時加速、何時出錯

**問題 1：CDN 為何能縮短回應時間？** 可快取的內容放在更靠近使用者的邊緣節點，命中時不必每次回原站；通常降低傳輸距離與原站負擔。若資源不可快取、頻繁失效或真正慢的是後端查詢，CDN 的收益就有限。

**問題 2：Cache key 為何重要？** 若語言、查詢、裝置版或權限會改變內容，快取鍵必須能區分；反之，不必要的 cookie 或 query 進入鍵，可能讓命中率下降。最危險的是把個人化結果作為共享回應，讓別人看到錯誤或私密內容。

**問題 3：如何證明 CDN 有效？** 在不同地區比較冷命中、熱命中的 TTFB，觀察供應商命中標頭或 `Age`，同時看原站請求數。只看到 CDN 網域出現在 URL，不代表請求真的命中邊緣快取。

**問題 4：內容更新後使用者仍看舊版，查哪裡？** 先檢查瀏覽器 HTTP cache、CDN TTL／purge、檔名版本與 Service Worker，辨別是哪一層保留舊結果。靜態內容優先使用內容 hash；需要即時更新的資料則要有明確失效策略。
