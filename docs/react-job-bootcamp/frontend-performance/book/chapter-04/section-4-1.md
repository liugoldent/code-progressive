# 4-1 拆分應用 Bundle：Code Splitting 與 Dynamic Import

> 學習目標：能選擇路由、功能或大型依賴作為切割邊界，並評估新瀑布。

**核心觀念：** 依路由、大型套件或低頻功能切 chunk，可減少首屏 JS 的下載與解析。React.lazy 是元件層的用法，但拆分 API 請求與資料載入要另行設計。

**實作與驗證：** 用 analyzer 找最大模組。切出圖表或編輯器，量首屏 JS bytes、LCP／TBT，以及第一次打開功能的等待；必要時做預載。

**常見誤區：** 切得過碎會產生依賴瀑布、更多 loading 狀態與快取管理成本。

### 切割前先選邊界

假設登入後報表頁包含一個大型圖表套件，但首頁不使用。先看 analyzer 確認圖表佔用的 chunk，再把圖表頁或面板動態匯入。觀察首頁下載量是否下降，以及第一次開報表是否新增明顯等待；若後者太慢，可在使用者進入報表前的合理時機預載。

切割不保證 LCP 改善：若主畫面必須等新 chunk 與 API 才能出現，可能反而變慢。應同時檢查 chunk waterfall、fallback 的版面穩定性與實際使用路徑。

## 原理拆解

Code splitting 改變的是「何時下載某段程式碼」。按路由切割可避免首頁下載報表頁，按功能切割可避免不打開編輯器的使用者下載編輯器。但程式碼分離後，使用者首次進入功能時多了一個請求和 loading 狀態。若該功能是首屏必需，切割可能建立新的瀑布。切割邊界應依使用路徑選擇；高機率下一步會用的功能可在不影響當前頁面時預載。

## 從頭做一次

1. 用 analyzer 觀察首頁 JS 的組成，標出登入後才用到的報表、圖表、編輯器等模組。選一個低頻功能改為 dynamic import。
2. 比較首屏總 JS bytes、解析執行時間、LCP，以及第一次打開該功能的等待。若功能的首次等待過長，可在 hover、閒置或上一頁合理時機預載，但要重測是否擠掉主資源。
3. 為切割點加入穩定的 loading fallback 和錯誤處理，測失敗、慢網及返回功能頁時的行為。

## 如何判斷做對了

最小 chunk 並非最佳方案；過多小 chunk 可能形成串行載入和維護負擔。

## 書籍逐頁核對｜紙本頁 4-2～4-18

### 4-2～4-5：為什麼要拆 Bundle

書中從大型單一 `bundle.js` 問題切入：即使用戶只造訪 A 頁，也被迫下載 B、C 頁的程式。Code Splitting 把應用拆成較小 chunk，讓特定路由或功能在需要時才載入。作者先用 Webpack Bundle Analyzer 的矩形圖檢查哪些套件占空間，再提出兩種拆分：把第三方套件集中成 vendor chunk，或依更細的條件分成多個 chunk。前者便於獨立快取，但若 vendor chunk 太大仍會拖慢首次載入；後者較精細，也增加設定與請求管理成本。

### 4-5～4-8：Dynamic Import 的兩種切點

`import()` 是讓打包器建立非同步邊界的語法。書中用按需求才載入 `lodash` 的例子，指出靜態 import 會進入起始依賴圖，動態匯入則等呼叫發生才取得對應 chunk。接著用 React `lazy`／`Suspense` 示範按路由載入不同頁面，讓使用者只下載目前頁面要用的元件。頁 4-8 又用 `lottie-web` 作大型功能套件例子：動畫只出現在特定頁面，就不必讓每個頁面都先下載它。實務上要檢查動態載入造成的互動等待，必要時搭配提示或合理預取。

### 4-9～4-18：NBA 球員頁的完整 Demo

書中做了一個三位球員頁面的 React 範例。起初打包分析顯示許多共用與非共用技巧元件混在主檔案。第一步用 `splitChunks` 把 `node_modules` 抽成 vendor chunk；第二步用 `React.lazy(() => import(...))` 讓 LBJ、Curry、KD 三條路由各有自己的 chunk，並用 `Suspense` 提供載入中的畫面。Network 面板可看到造訪 LBJ 頁才取得 LBJ 的檔案。

第三步檢查分析圖，發現幾個球員都使用的投籃技巧被重複帶入不同路由 chunk；書中調整共用 chunk 規則讓重複模組拆出。隨後又發現一個灌籃元件只被兩個頁面用到，硬塞入共用 chunk 會讓不需要的頁面也下載它，於是改成動態匯入，讓真正用到的頁面才取得。這一串過程強調：切割後要回頭看 analyzer 和 Network，避免共用 chunk 變成新的大包，也避免 chunk 過碎增加載入成本。書中使用的是當時 React Router 與 Webpack 的 API 寫法，新專案要按目前版本調整。

## 問題與解答：什麼值得拆成 Chunk

**問題 1：為什麼下載同樣總量的 JS，拆分後首屏可能更快？** 因為首屏只需下載、解析與執行當下功能的程式，低頻頁面或編輯器可等使用者需要時再載入。書中的 NBA 球員頁示範把頁面和元件依使用時機拆開；重點是減少初次路徑上的工作，而非讓所有程式的總量神奇消失。

**問題 2：`import()` 與 `React.lazy` 分別做什麼？** `import()` 是動態載入模組的語法；`React.lazy` 用它包裝延後載入的 React 元件，通常配合 `Suspense` 顯示等待狀態。資料 API 是否同時延後、錯誤如何處理、何時預載仍要另行設計。

**問題 3：Chunk 切得越小越好嗎？** 不是。拆太細可能讓進入功能時產生連續請求、loading 閃爍和依賴瀑布。優先按路由、大型第三方套件或低頻功能設邊界。若使用者高度可能即將進入某頁，再考慮預取，但需量測是否擠掉首屏資源。

**問題 4：如何驗證拆分有收益？** 比較首屏 JS bytes、解析／執行時間、LCP 和 TBT；再測第一次打開被拆出的功能要等多久。若首屏快了 100 ms，卻讓核心操作第一次打開慢 3 秒，拆分邊界可能不對。
