# 4-2 移除用不到的程式碼：Tree Shaking

> 學習目標：能用產物證明 tree shaking 生效，並避免刪除有副作用的程式碼。

**核心觀念：** 打包工具利用 ESM 的靜態 import/export 和副作用資訊移除未使用的程式碼。sideEffects 設定錯誤會把全域註冊或 CSS 一起移掉。

**實作與驗證：** 用 production build 比較單一依賴改寫前後的模組樹和實際傳輸大小；檢查套件 ESM 入口及副作用檔案。

**常見誤區：** 程式碼沒呼叫不代表打包後必定消失；動態匯入與 CommonJS 行為要實測。

### 驗證 Tree Shaking 的最小實驗

建立 production build，記錄 bundle analyzer 中目標套件的大小；只改匯入方式或套件入口，再 build 一次並比較。檢查輸出 chunk 是否仍含未使用函式，別只根據原始碼推論。若套件有全域註冊或 CSS 匯入，必須保留相應副作用。

`sideEffects: false` 是發布套件時的強宣告，不能為了追求小 bundle 盲目套到有副作用的程式碼。驗證需要包含執行功能與樣式，而不只是看 KB。

## 原理拆解

Tree shaking 利用 ESM 靜態結構判斷哪些輸出沒有被使用，但真正刪除還受到副作用、打包設定與壓縮器影響。模組頂層若會註冊全域事件、修改環境或匯入 CSS，打包器不能隨意移除。`sideEffects: false` 等於向工具宣告模組可安全刪除，寫錯可能只在正式 build 出現問題。最可靠的方法是比較正式產物，並執行涵蓋受影響功能的驗證。

## 從頭做一次

1. 選一個大型依賴，記錄 production build 的模組樹和傳輸大小；改為 ESM 具名匯入或更小的入口，再重新 build。
2. 確認實際輸出 chunk 已去除不用的函式，而不是只看原始碼沒有呼叫。檢查套件的 sideEffects 設定、CSS 匯入及全域註冊。
3. 執行功能測試，確認被移除的程式碼不是必要初始化。若 bundle 變小但功能壞了，代表副作用宣告或打包設定有誤。

## 如何判斷做對了

ESM 有助靜態分析，但不是保證；最終要看打包器的真實輸出。

## 書籍逐頁核對｜紙本頁 4-19～4-30

### 4-19～4-22：Tree Shaking 的前提是可靜態分析

書中把 Tree Shaking 比喻成打包時移除未用到的匯出，並區分它與一般的 Dead Code Elimination：後者常是在程式分析／壓縮階段刪掉確定不會執行的內容，前者著重模組依賴圖中未被引用的部分。頁 4-20～4-21 先用 CommonJS 風格 `exports.add_100`／`exports.add_500` 示範：即使只使用前者，打包器可能仍把整個模組帶進 bundle，因為 CommonJS 匯出物件的屬性可以在執行時動態取用。ES Modules 的靜態 `import`／`export` 有利於預先辨認哪些匯出未被引用。

### 4-23～4-26：轉譯設定、匯出粒度與副作用

書中列三個常見障礙。第一，把 ES Modules 又經 Babel 轉成 CommonJS，打包器失去靜態分析線索。第二，把多個函式放在同一個 default 匯出物件裡，使用者只取一個方法時，其他方法不一定能單獨移除；較好的方式是具名匯出，讓函式粒度清楚。第三是 module level side effect：若模組載入時會執行其他動作，打包器不能隨便刪除。書中以 `memoize(add_100)` 在頂層呼叫的例子說明，除非打包器能證明呼叫沒有副作用，否則可能保留相關函式。頁 4-26 補充動態 `import()` 的載入條件只在執行時才知道，對當時打包器而言不能依相同方式在模組層級做 Tree Shaking；這是書中工具鏈的限制描述，現行工具要依版本驗證。

### 4-27～4-30：第三方套件與 `sideEffects`

書中用只想用 lodash 的 `flatten` 卻把整個 lodash 帶進 vendor bundle 的例子，改用 ES module 版本 `lodash-es` 後重新看 Bundle Analyzer，檢查輸出是否縮小。開發 npm 套件時，`package.json` 的 `sideEffects` 可告訴打包器哪些檔案能安全移除；但不能草率把所有檔案標為無副作用，否則單純 `import './index.css'` 一類樣式副作用可能被刪。書中示範以陣列保留 CSS 等確有副作用的檔案，並用 `module` 欄位指向 ES module 版本、`main` 保留其他環境入口。這些標註是對打包器的承諾，應用功能測試和產物分析共同驗證。

## 問題與解答：Tree Shaking 為何失效

**問題 1：Tree Shaking 如何知道一段程式沒被用到？** ES Modules 的 `import`／`export` 讓打包器能在建置時分析引用關係，並在確認沒有必要副作用後移除未使用匯出。它是 production build 的產物最佳化，不是瀏覽器執行時逐行刪程式。

**問題 2：明明只 import 一個函式，整個套件仍進 bundle，可能為何？** 套件若是 CommonJS、匯出粒度太粗、初始化有副作用，或轉譯流程先把 ESM 轉掉，工具就較難安全刪除。看 analyzer 中的模組樹與打包器的輸出，改用可靜態分析入口，再比較產物大小。

**問題 3：`sideEffects: false` 為何有風險？** 它等於宣告未被引用的模組載入沒有可觀察效果。若某檔會全域註冊、修改 prototype 或載入 CSS，錯誤設定可能讓它被刪掉，功能或樣式壞掉。應對真正有副作用的檔案保留例外，並在正式產物驗證。

**問題 4：怎麼做最小驗證？** 建一個只 import 套件單一函式的頁面，跑 production build，比較 module analyzer、實際輸出 bytes 與功能。不要只看原始碼中「沒有呼叫」就推定已被刪除。
