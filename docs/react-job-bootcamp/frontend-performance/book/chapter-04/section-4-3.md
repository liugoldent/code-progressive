# 4-3 Polyfill-less Bundling Script

> 學習目標：根據產品支援矩陣決定轉譯與 polyfill，理解雙產物的成本。

**核心觀念：** 瀏覽器支援矩陣決定能使用的語法與 API。過度轉譯和一次載入所有 polyfill 會增加 JS 成本；現代／舊版雙輸出可減少現代使用者的負擔，但要維護兩套產物。

**實作與驗證：** 先看真實使用者的瀏覽器分布，定義支援範圍，再調整 browserslist／polyfill 策略。若雙輸出，測現代與舊版環境是否各拿到正確程式碼。

**常見誤區：** 不要直接套用書中當年的支援百分比；瀏覽器分布會變，取消舊版支援也需產品決策。

### 支援矩陣決策

先從真實流量列出瀏覽器版本與佔比，再決定哪些瀏覽器是必須完整支援、哪些可以提示升級。只有確認產品允許，才調整 browserslist 或採現代／舊版雙產物。雙產物要測每組環境實際拿到的 JS、功能是否可用、polyfill 是否只載入必要部分。

```html
<script type="module" src="/modern.js"></script>
<script nomodule src="/legacy.js"></script>
```

此模式只是示意；實際打包與瀏覽器相容性應由專案工具鏈和測試矩陣決定。

## 原理拆解

轉譯與 polyfill 是為了讓較舊瀏覽器理解語法或具備缺少的 API，卻會增加下載和執行成本。策略不是盲目移除所有相容程式碼，而是先訂支援矩陣，再讓現代使用者取得較精簡的產物、舊使用者取得需要的 fallback。雙產物會增加 build、測試和部署成本；若實際舊版使用者很少但仍是關鍵客戶，仍不能只看流量百分比。

## 從頭做一次

1. 從 RUM 或分析資料統計瀏覽器版本，而不是沿用書出版時的市占率。與產品需求確認舊環境是否需要完整功能。
2. 調整 browserslist 後比較現代環境的 JS bytes、解析時間及功能。若採現代／舊版雙輸出，分別在兩種瀏覽器驗證正確產物和必要 polyfill。
3. 記錄部署與測試成本：兩套產物需要版本一致、快取策略與錯誤監控都能對應。

## 如何判斷做對了

直接放棄舊版瀏覽器是產品決策，不應只因 bundle 變小就私自更改支援範圍。

## 書籍逐頁核對｜紙本頁 4-31～4-38

### 4-31～4-34：現代語法的成本來自轉譯與補丁

書中指出「現代 JavaScript」不是固定等於某個 ECMAScript 年份，而是目標瀏覽器已能直接執行的一組語法與功能。若為舊瀏覽器把新語法轉成較舊語法，Babel 等轉譯器可能產生更長的程式；若瀏覽器缺 API，polyfill 又會增加下載與執行成本。頁 4-33 以 `String.prototype.repeat` 的 polyfill 實作說明：一個看似簡單的方法可能帶來不少附加程式。頁 4-34 的 class 轉譯圖亦顯示輸出比原始語法長。書中引用 Instagram 當時把目標提高到 ES2017 後約減少 5.7% bundle size 的案例；這是歷史案例，不能當成今日專案固定收益。

### 4-35～4-36：差異化交付

書中提出同時產生現代與舊版兩份 bundle：支援 ES Modules 的瀏覽器以 `<script type="module">` 取得現代版本；較舊瀏覽器以 `<script nomodule>` 取得 legacy 版本。這樣可避免所有使用者都付出相同的相容性成本。要實測兩份產物的大小、解析與執行時間，也要檢查目標瀏覽器支援率。書中還示範套件可提供不同入口，以便打包器選擇現代版本；真正的欄位語意要依目前套件與打包器文件確認。

### 4-37～4-38：估算與驗證

書中介紹 Estimator.dev 估算某網站採用現代 JavaScript 可能節省的體積，並提到它可用反向轉譯來推算差異。這適合作為調查線索，不能取代自家正式建置、目標裝置上的性能測試。這節的核心決策不是「刪掉所有 polyfill」，而是依實際支援矩陣，只讓需要相容程式的使用者下載它。

## 問題與解答：現代／舊版程式碼如何交付

**問題 1：Polyfill 與語法轉譯解決相同問題嗎？** 不同。轉譯把較新的語法改寫為舊環境可解析的形式；polyfill 補上缺少的 API。舊瀏覽器可能兩者都需要，但現代瀏覽器若一律下載大量相容碼，會增加傳輸及執行負擔。

**問題 2：為什麼不能立刻移除所有 polyfill？** 先看產品實際支援的瀏覽器與使用者比例，尤其付費或關鍵流程使用者。若使用者環境缺 API，頁面可能直接失效。決策順序是定義支援矩陣、產出對應程式、在各環境驗證，而不是盲目求小檔案。

**問題 3：差異化交付如何避免現代使用者負擔？** 可為現代瀏覽器提供較少轉譯與 polyfill 的產物，為舊環境提供相容產物。代價是兩套建置、測試與快取版本管理；要確認每類瀏覽器實際收到正確檔案。

**問題 4：書中的支援比例可直接套用今天嗎？** 不行。瀏覽器版本與受眾分布會隨時間改變。用自己的 RUM 或分析資料確認使用者環境，重新計算省下的位元組與維護成本。
