# 8-2 面對大量請求，前端可以做些什麼？

> 學習目標：能在請求尖峰時減少重複流量並保住核心流程。

**核心觀念：** 前端可藉公開內容快取、請求去重、限制並行、指數退避加 jitter、降級非核心服務來減少伺服器壓力。核心流程仍需後端容量、排隊與防重處理配合。

**實作與驗證：** 演練 429、5xx、第三方超時與尖峰重試。列出可停用功能及必須維持的搜尋、登入或付款流程；觀察請求數、錯誤率與完成率。

**常見誤區：** 立即無上限重試會造成重試風暴；非冪等操作須防止重複提交。

### 高流量演練

假設服務回 429，所有客戶若立即重試，會讓服務更難恢復。應依 Retry-After 或有上限的指數退避加 jitter 控制重試，並避免相同資料在同頁重複請求。非核心推薦區可顯示降級內容，主要搜尋或登入流程應保持可用。

付款等非冪等請求不能任意重送：需有前後端共同的防重機制。演練時記錄每位使用者平均請求數、429／5xx 比例與核心任務完成率，確認降級是否真的減壓。

## 原理拆解

高流量時每個客戶端多一次不必要請求，總量可能被使用者數放大。請求去重、可共享內容快取、限制並行與關閉非核心模組都能減壓；重試則要避免所有客戶端在同一秒再次打到伺服器。`Retry-After`、指數退避和 jitter 可分散重試。核心交易流程需要前後端協作處理冪等、防重與排隊，不能只由前端按鈕禁用來保證。

## 從頭做一次

1. 列出核心和非核心請求，對公開可快取內容使用 CDN，對同鍵 API 做去重與短期快取。對長列表限制並行抓取。
2. 模擬 429、5xx 和第三方超時。重試要有上限，遵守 Retry-After 或採指數退避加 jitter；非核心推薦、分析可暫時降級。
3. 對付款、提交表單等非冪等操作驗證防重，觀察每位使用者請求數、錯誤率與主要任務完成率。

## 如何判斷做對了

前端減壓不能取代後端容量規劃；真正的尖峰演練要跨前後端一起做。

## 書籍逐頁核對｜紙本頁 8-21～8-33

### 8-21～8-23：前端也是流量放大器

本節從活動或尖峰流量出發：大量使用者同時到站，每個頁面若產生多筆不必要請求，Web App 與後端都會額外承受壓力。書中用「使用者 → Web App → Server」的圖比較正常流量、尖峰造成服務無法處理，以及在前端／邊緣層減少到達後端的請求。前端無法憑空增加後端容量，但能避免自己製造額外流量。

作者先列出幾個方向：暫緩不必要請求、降低 HTTP 請求數、善用 Cache、CDN、避免事件高頻觸發網路請求。前面章節的影像與檔案優化，也可減少載入時的請求和傳輸成本。公開靜態內容若能由 CDN 回應，便不需要每個使用者都回源抓取。

### 8-24～8-27：SSR 回應快取示意

書中以 Next.js 搭配 Express 的範例說明：SSR 若每個請求都由 Node.js 渲染，流量增加時渲染伺服器會變重；可依請求 URL 作為快取鍵，對成功渲染的 HTML 設定一段存活時間，命中時直接回傳快取結果，降低重複渲染。範例使用記憶體內 LRU Cache，並示意只快取成功回應、錯誤時走渲染錯誤處理。

這段是**概念示範**，不是可直接套到所有 SSR 頁面的設定。實作時必須確認快取鍵涵蓋語言、查詢參數及其他會改變輸出的因素；帶有登入狀態、個人資料或權限差異的 HTML 不可用公開共用快取，否則會把一位使用者的內容送給另一位。多台伺服器的本機記憶體快取也不會自動共享，必須處理失效、一致性與容量上限。

### 8-27～8-29：Debounce，等待輸入停下來

書中的搜尋框例子會在每個輸入事件直接送 AJAX：輸入完整關鍵字前，每打一個字都發出一次請求，其中大多數中間結果可能根本不需要。Debounce 的做法是每次事件發生便取消前一個計時器，等一段時間都沒有新事件才執行。書中以約 500 ms 的事件時間線示意：連續輸入期間不送，停下後只送最後一次。這適合搜尋建議、輸入驗證或 resize 後重新計算。

Debounce 減少觸發次數，但不是取消已經送出的請求。搜尋 UI 還應處理過期回應覆蓋新結果、空字串、不再需要的請求與錯誤提示；必要時使用 `AbortController` 取消舊請求，並以查詢鍵確認回應是否仍適用。

### 8-29～8-33：Throttle，限制持續事件的頻率

Throttle 允許持續發生的事件在固定間隔內至多執行一次。書中用格鬥遊戲按鍵與長頁捲動作類比：使用者可能一直觸發 input 或 scroll，但處理函式沒有必要對每個事件都完整執行。這適合捲動位置更新、拖曳、持續性的視覺回饋；若只需要「停止後最後結果」，Debounce 通常更貼切。

書中示範自寫兩個函式：Debounce 用 `clearTimeout` 重排工作；Throttle 用上次執行時間和延遲計時器限制頻率，也提到可使用 Lodash 或 RxJS 的現成實作。讀程式時要確認所需的 leading／trailing 行為：第一次是否立即執行？最後一次事件是否保留？元件卸載時是否清理計時器？這些細節會決定 UI 是否漏掉最後狀態。

最後，作者強調前端節流只能減輕一部分負擔；快取、請求減量仍須和伺服器端容量規劃協作。將本節用在真實系統時，可以以「每位使用者平均請求數、尖峰回源量、429／5xx 比例、主要任務完成率」驗證效果。前面提到的 Retry-After、指數退避、非冪等防重屬本筆記的延伸補充，不是本節書中示範的核心內容。

## 問題與解答：尖峰時前端如何真正減壓

**問題 1：一個使用者多發幾次請求，為何高流量時問題很大？** 若每個輸入字元、每次捲動都發請求，使用者數一增加，重複請求會一起放大。先列出同頁每次操作的請求數，分辨必需與可延後的工作，再看是否能快取、去重或由 CDN 回應。

**問題 2：SSR HTML 為何可以快取？哪些頁面不能直接共用？** 相同公開頁面每次都重新渲染會耗伺服器資源；書中用 LRU Cache 示意成功回應短期重用。但登入、語系、權限或查詢條件改變內容時，快取鍵與共享範圍必須正確；個人化 HTML 不能當公開結果給別人。

**問題 3：搜尋框應用 Debounce 還是 Throttle？** 若只要使用者停止輸入後的最後查詢，用 Debounce：每次輸入重排計時器，停止一段時間才送。若持續捲動期間需要定期更新位置，用 Throttle 限制固定間隔內的執行次數。也要決定第一次立即執行、最後一次是否補執行。

**問題 4：Debounce 後為何仍可能看到過期搜尋結果？** 已送出的舊請求可能晚於新請求回來。Debounce 只減少事件觸發，不保證網路回應順序。需按查詢鍵比對結果，或取消過期請求，避免舊結果覆蓋新查詢。

**問題 5：如何知道前端節流真的保護了後端？** 比較修改前後每位使用者請求數、尖峰回源量、429／5xx 與核心任務完成率。前端只能減少不必要流量；若必需請求本身已超過容量，仍需後端擴容、排隊與快取協作。
