# 2-2 圖片資源最佳化

> 學習目標：能根據顯示尺寸、DPR、畫質與載入優先序設計圖片交付。

**核心觀念：** 依用途選 SVG、JPEG、PNG、WebP 或 AVIF；再配合實際展示寬度與 DPR 輸出多尺寸圖片。srcset/sizes 解決候選圖選擇；width/height 或 aspect-ratio 預留空間；首屏 LCP 圖要及早載入。

**實作與驗證：** 在 Network 找最大圖片，檢查實際選用的候選圖及 transferred bytes。比較品質與尺寸，測 LCP 變化；非首屏圖片可 lazy load。

**常見誤區：** 把原圖以 CSS 縮小並不會減少下載；Base64 內嵌也可能讓 JS/CSS 變大且失去獨立快取。

### 圖片決策例子

卡片寬 300 CSS px，DPR 2 的手機通常需要約 600 實際像素；直接下載 3000 像素原圖沒有必要。照片可比較 AVIF／WebP／JPEG 的畫質與 bytes；線條圖示可先試 SVG；需要透明且無法向量化的影像可評估 PNG 或現代格式。

```html
<img src="card-600.webp"
  srcset="card-300.webp 300w, card-600.webp 600w, card-900.webp 900w"
  sizes="(max-width: 600px) 50vw, 300px"
  width="900" height="600" alt="商品照片" loading="lazy" />
```

`sizes` 描述圖片在版面中的 CSS 寬度。驗證時確認瀏覽器實際選用的檔案，並為首屏 LCP 圖取消 `loading="lazy"`。

延伸：[Day 06 原系列筆記](../../day-06.md)。

## 原理拆解

瀏覽器選圖需要知道候選檔案的實際像素寬度和圖片在版面中的 CSS 寬度。`srcset` 的 `w` 描述檔案尺寸，`sizes` 描述顯示尺寸，瀏覽器再考慮 DPR 選擇候選。這和 CSS 的 `width: 100%` 不是一回事：CSS 縮小只改變顯示大小，原圖仍會下載。首屏主圖要與離屏圖片分開處理；對主圖，及早發現與優先下載可能比極端壓縮更重要。預留寬高比例是避免圖片載入後推開文字的關鍵。

## 從頭做一次

1. 在 DevTools 選中圖片，確認實際 CSS 顯示尺寸與來源像素。若 300 CSS px 的卡片在 DPR 2 裝置下載 3000 px 圖，先產生約 600 px 候選版本。
2. 將候選圖寫入 srcset，將版面寬度寫入 sizes，保留 width/height 比例。對首屏主圖優先確保 HTML 可直接發現、不要 lazy load；必要時測 fetchpriority。
3. 對同一畫面比較實際選用圖片、總圖片傳輸量、LCP 與 CLS。切換行動版和桌面版，確認沒有因 sizes 寫錯而下載過大圖。

## 如何判斷做對了

注意圖檔縮小未必改善 LCP：若節省的下載時間被元素渲染等待吃掉，應轉查 CSS／JS 阻塞。

## 書籍逐頁核對｜紙本頁 2-11～2-36

以下按書中實際展開的順序整理。前文的 AVIF、LCP 優先序與 CLS 實作，是額外補充，不應誤認為本小節原文的內容。

### 2-11～2-14：先選格式，再談壓縮

書中從 HTTP Archive 的圖片資源占比切入，指出圖片常是網頁中最重的一類資源。它先比較 JPEG、PNG：兩者都是點陣圖，但壓縮機制和合適的畫面不同。書中以大背景照片為例，JPEG 在檔案大小與肉眼畫質之間取得較好的折衷；有明確輪廓或透明需求時，PNG 值得評估。頁 2-12 展示 tiny-png 服務，說明現成工具、打包器外掛都能在交付前處理圖片。頁 2-13 區分 JPEG 的有損壓縮與 PNG 常見的無損處理，提醒「壓縮」必須連同畫質需求一起判斷。

頁 2-14 轉到 SVG。書中用放大的文字圖示比較點陣圖與向量圖：向量圖放大後仍可保持邊緣清楚，適合圖示、圖表、線條等場景；SVG 本身仍可用 svgo 一類工具清理不必要的資料。不能把「SVG 一定比較小」當成規則；複雜照片仍適合點陣圖。

### 2-15～2-17：WebP 與格式相容性

書中用 YouTube 縮圖 URL 比較同畫面的 JPEG 與 WebP：範例在 DevTools 中分別約為 234 KB 與 187 KB，表示該次測試的 WebP 較小。這是單一圖片、特定編碼設定下的例子，不是每張圖片的固定縮減比例。書中也提到 WebP 可支援動畫，並以當時的瀏覽器支援表說明要考慮相容性。該表有年代性；今天要以目標使用者的瀏覽器資料和現行相容性文件重新核對。

頁 2-17 開始轉向響應式圖片。書中指出，只提供一張大圖給所有裝置，手機仍可能下載超過顯示所需的位元組；Lighthouse 的「Properly size images」提示就是線索。

### 2-18～2-23：響應式圖片的三個層次

1. **DPR 與 `x` 描述符（2-18～2-19）**：CSS 像素與實際裝置像素不同。同一個顯示寬度在 DPR 2 裝置上可需要約兩倍來源像素；用 `srcset` 的 `1x`、`2x` 提供候選，瀏覽器依裝置密度選擇。
2. **`w` 描述符（2-19）**：若只備有 small、medium、large 等寬度版本，可以用 `300w`、`600w`、`1000w` 標記來源圖片自身寬度。書中以 450 CSS px、不同 DPR 的裝置推算候選圖，不要求每種 DPR 各產一張檔案。
3. **`sizes`（2-20）**：光有 `w`，瀏覽器在尚未完成版面計算時不知道圖片將顯示多寬。`sizes` 用媒體條件描述預期的版面寬度；頁中的例子在窄於 400 px 時用 80vw，其他情況用 50vw。這是給瀏覽器選擇圖片的提示，需要與實際 CSS 保持一致。

頁 2-20～2-23 再處理 **art direction**：窄螢幕不一定只需縮小同一張圖，有時需要不同裁切或構圖。`<picture>` 包含多個依 `media`／`type` 選用的 `<source>`，末尾 `<img>` 當作後備；書中先用 viewport 條件挑大、中、小構圖，再把 WebP 與 JPEG 的格式後備合在一起。`srcset` 著重同內容的解析度選擇；`picture` 還能處理不同構圖與格式。頁 2-24 強調它們和 CSS media query 的差別：HTML 層的選圖可讓瀏覽器更早決定該下載哪張圖。

### 2-24～2-27：Image CDN、打包器與 Base64

書中舉 imgix、Cloudinary 為 Image CDN 例子：透過 URL 參數或服務 API 依尺寸、格式轉換圖片，減少自己維護大量版本。頁 2-25 則示範舊版 Webpack 的 `url-loader`：尺寸低於設定值時內嵌成 Data URL，超過時保留外部檔案。此處的 8,878 bytes 是書中設定例子，不是推薦的通用門檻；目前打包器也可能用不同機制處理資源。

頁 2-26 專門列 Base64 內嵌的交換條件：可省個別圖片請求，但編碼後文字往往比二進位原檔大，更新也和容器檔案綁在一起，獨立快取與維護較困難。書中的判斷偏向只對小圖示評估內嵌；大圖多半不合適。頁 2-27 用 Google 圖片搜尋頁的縮圖與大圖作例子：縮圖可能內嵌，完整圖片則用 URL 載入。

### 2-28～2-36：CSS Sprites 的機制與限制

書中從作者網站多個小圖示各發一個請求切入，介紹把小圖拼到同一張圖中的 Sprite。頁 2-29～2-30 用首頁與下一頁圖示示範：兩個元素都載入同一張底圖，依各自的 `background-position` 露出不同區域。頁 2-31～2-33 接著使用 CSS Sprite Generator 產生合圖與各圖示的座標 CSS，再將 class 套到 HTML 上。這個例子重點是「一張資源 + 不同座標」，不是要求手算每個座標。

頁 2-34～2-35 回到適用性：若合圖過大，下載整張圖未必划算；變動一個小圖可能要重建合圖，舊頁面還可能因快取或座標變更出錯。書中認為選單小圖示、企業 Logo 集合、相同互動狀態的多張圖比較可能適用。頁 2-36 以台灣網站仍使用 Sprites 的例子提醒：技術是否過時要依情境判斷。現代專案也應把 HTTP/2/3、多路複用、SVG 等替代方案納入實測，不應只以「減少請求數」斷定收益。

## 問題與解答：圖片該如何交付

**問題 1：同一張圖該用哪種格式？** 圖示和線條先考慮 SVG；照片評估 JPEG、WebP、AVIF 的畫質與大小；需要透明度的點陣圖再看 PNG、WebP 或 AVIF。格式選擇要用實際圖片、目標瀏覽器和可接受畫質測量，不能只看副檔名宣稱某格式必然最小。

**問題 2：圖片在畫面只顯示 400 px，為什麼還下載 3000 px 原圖？** CSS 只改顯示尺寸，不會自動縮小檔案。輸出符合展示寬度與 DPR 的候選圖，用 `srcset` 列出版本，讓 `sizes` 告訴瀏覽器此版面實際占多寬；在 Network 檢查選到哪個檔案與傳輸量。

**問題 3：`srcset` 和 `<picture>` 有何差別？** `srcset` 主要讓瀏覽器在同一內容的不同解析度／寬度間選擇；`<picture>` 可依媒體條件或格式提供不同來源，適合手機裁切版與桌機構圖不同，或需要格式後備。兩者都應為圖像預留寬高或 `aspect-ratio`，避免內容載入後位移。

**問題 4：Base64 和 CSS Sprite 何時反而變慢？** Base64 內嵌會放大 CSS／JS、減少獨立快取；Sprite 可減少舊式大量小圖請求，但更新一個圖示可能讓整張圖失效，還增加定位維護成本。先看實際 HTTP 協定、圖片數量與快取命中，再決定是否使用。

**問題 5：首屏主圖可否加 lazy loading？** 通常不宜。若它是 LCP 候選，延遲載入會讓瀏覽器更晚發現資源。優先讓主圖在 HTML 中可發現、使用正確尺寸與適當優先級；只對離視窗遠的圖片延遲載入。
