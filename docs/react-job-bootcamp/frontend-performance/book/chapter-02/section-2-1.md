# 2-1 程式碼最佳化

> 學習目標：分辨 minify、壓縮、刪除程式碼與延遲載入的收益範圍。

**核心觀念：** Minify 移除語法中不影響行為的內容，mangle 縮短名稱；它們通常由 production build 完成。更大的收益常來自刪除未使用依賴、切割低頻功能和避免重複 polyfill。Source map 用於還原錯誤堆疊。

**實作與驗證：** 用 bundle analyzer 列出最大模組，區分原始大小、傳輸大小與解析執行時間。先量測，再刪除或延後低頻程式碼，重跑相同頁面。

**常見誤區：** 混淆不是安全措施，不能保護送到瀏覽器的秘密。

### 三種大小要分開看

磁碟上的 bundle 大小、Network 的傳輸大小，以及瀏覽器解析與執行成本是三回事。假設壓縮後只剩 80 KB 的 JS，仍可能在低階手機花很久執行。先用 analyzer 找內容，再用 Coverage 找目前路徑未使用的部分，最後用 Performance 查真正的主執行緒成本。

### 操作次序

先移除不需要的依賴或重複 polyfill，再依路由／功能切割，最後確認 production minify 與傳輸壓縮已啟用。每一步都要比較相同頁面的 bytes、LCP 與主執行緒時間；保留 source map 供錯誤追蹤，但不要把機密寫入前端程式。

## 原理拆解

程式碼有三種成本：下載位元組、解析／編譯、執行。Minify 和 Brotli 主要處理前兩者中的傳輸部分；刪除依賴能同時減少下載與執行；延遲載入則把目前不需要的成本移出關鍵路徑。Bundle analyzer 看「載入了什麼」，Coverage 看「這次用到多少」，Performance 看「執行花了多少時間」。這三種工具得到的答案不同，需結合使用。不要把 source map 當作降低正式環境執行成本的工具，它主要幫助除錯。

## 從頭做一次

1. 用 production build 和 analyzer 列出首屏 chunk 的來源。先找未使用的大型套件、相同功能的重複依賴，以及只在低頻頁面使用的模組。
2. 在 DevTools Coverage 觀察特定路徑未執行的程式碼，但注意「本次未用」不等於「整站無用」；需走過主要互動路徑再判斷。
3. 依序評估刪除、替換、動態匯入，再確認 minify 與傳輸壓縮。對每次修改同時記錄 transferred bytes、解析執行時間及功能測試結果。

## 如何判斷做對了

若 bytes 降了但主執行緒時間沒變，收益可能主要在慢網；若 bytes 不變卻執行變快，可能是演算法或渲染改善。兩種成果都要分開呈現。

## 自我檢查

- 我能否指出這個技巧改善的是傳輸、載入、主執行緒、渲染、記憶體，還是資料新鮮度？
- 我是否保存相同條件下的改動前後證據，並檢查副作用？

### 2-2～2-4：Minify 與 Uglify 解決的問題不同

書中先用 Google 首頁原始碼說明：正式站點的程式碼常是一整段難以閱讀的文字，這不表示開發者原本就這樣寫，而是發佈流程處理後的產物。Minify 刪除空白、註解、可省略的符號等不影響執行的字元；Uglify 在本節的用法則包括縮短識別名稱與調整程式結構。書中用計算質數的函式對照處理前後，讓讀者看到「可讀性下降，功能仍相同」的結果。

這個例子值得分清兩種成本：檔案的位元組減少，可改善下載；識別名稱變短和語法變形不保證讓程式的運算更快。書中特別提醒，這種處理提高閱讀和除錯難度。HTML、CSS 也能 Minify，並非 JavaScript 專屬。

### 2-5～2-7：交給打包流程，並看數據而非只看工具名稱

書中展示 Webpack 的 UglifyJsPlugin／OccurrenceOrderPlugin 設定，以及 Gulp 的 `gulp-uglify` 工作流程。這些是**書中當時的工具範例**，新專案應查目前版本的正式建置設定，不宜直接貼用舊外掛。頁 2-7 的 benchmark 表格比較不同 Minifier 對 React 程式碼的輸出大小、gzip 後大小和執行耗時；此處的判讀方式比「某工具永遠最快」更重要：要同時看壓縮結果與建置時間，並以自己專案的產物驗證。

### 2-8～2-10：壓縮後如何除錯

書中接著介紹 source map：它記錄壓縮後程式碼如何對回原始檔案與位置，DevTools 可利用它顯示原始碼。書中的 JSON 範例有 `version`、`file`、`sources`、`sourceRoot`、`names`、`mappings` 等欄位；其中 `mappings` 是位置對應資料，而非可直接閱讀的原始程式碼。頁 2-9 還展示以 UglifyJS CLI 產生 map 的選項。頁 2-10 說明瀏覽器可從檔案尾端的 `sourceMappingURL` 註解或 `X-SourceMap` 回應標頭找到 map，並示範 DevTools 中啟用 JavaScript/CSS source maps。

實務上需要檢查 map 的交付方式與原始碼揭露範圍；source map 的目的在於除錯，不是效能優化本身。

## 問題與解答：程式碼體積與執行成本

**問題 1：Minify、Uglify、壓縮傳輸是一回事嗎？** 不是。Minify 移除空白、註解並縮短可安全改寫的語法；mangle 會縮短識別名稱；gzip／Brotli 是 HTTP 傳輸壓縮。前兩者改產物內容，後者改傳輸位元組。檢查時要分清原始 bundle、壓縮後大小與執行時間。

**問題 2：把 JS 壓到很小，為何首屏仍慢？** 瀏覽器還要解析、編譯和執行。若一大段低頻功能仍放在首包，傳輸縮小後主執行緒仍可能長時間忙碌。用 bundle analyzer 找最大模組，再在 Performance trace 確認執行成本；不必要依賴優先移除，低頻功能可延後載入。

**問題 3：正式環境壓縮後報錯，怎麼找回原始碼位置？** 產生與部署版本對應的 source map，讓錯誤堆疊或 DevTools 映回原始檔。Source map 需與精確的 build 版本配對；若混用不同版，行列號會錯。公開提供 source map 也需評估程式碼可見性與部署政策。

**問題 4：混淆過的前端程式可以藏 API 密鑰嗎？** 不行。送進瀏覽器的內容終究可被下載和分析。混淆或縮名可改變可讀性，但不能當安全邊界；秘密應保留在伺服器端。
