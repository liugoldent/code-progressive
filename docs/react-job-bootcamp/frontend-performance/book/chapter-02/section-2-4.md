# 2-4 可適性服務 Adaptive Serving

> 學習目標：設計在 API 不支援時仍正確運作的省流量體驗。

**核心觀念：** 依使用者情境交付不同品質的圖片或影片。Network Information API 可提供網路類型、估計速度或 saveData 線索，但支援度和數值精度有限；應以功能偵測與使用者選擇為主。

**實作與驗證：** 預設提供可接受品質，再提供「省流量／高畫質」選項。若 navigator.connection 存在，可把 saveData 作為降品質訊號；用 Network 面板驗證載入大小，並測 API 缺席時的 fallback。

**常見誤區：** 不要只憑 effectiveType 判斷使用者能力；網速會變，CPU、記憶體與主觀偏好也影響體驗。

### 漸進增強範例

```js
const saveData = navigator.connection?.saveData === true;
const imageQuality = saveData ? 'low' : 'balanced';
```

這只是可選訊號，程式在 `navigator.connection` 缺席時仍能運作。更可靠的做法是讓使用者手動切換省流量／高畫質，並保存偏好。測試慢網、快網和 API 不支援三種情況，確認不會因偵測錯誤而永遠送低畫質。

## 原理拆解

適性服務是「根據可用訊號與使用者偏好選擇交付品質」，並非單純偵測網速。網路估計值可能不準，也可能在一次瀏覽中變動；裝置 CPU、記憶體和使用者是否願意省流量同樣重要。因此合理策略是預設提供足夠好的內容，讓使用者能主動切換，再把 `saveData` 等 API 當作附加提示。若低畫質版本已快取而使用者切到高畫質，應確認 URL 與快取鍵可區分版本，否則可能始終顯示舊資源。

## 從頭做一次

1. 先決定預設交付品質與使用者可選的「省流量」模式。省流量不應只縮圖，也可降低非必要預載、動畫或影片自動播放。
2. 若瀏覽器提供 navigator.connection.saveData，可作為額外訊號；如果 API 缺席，維持合理預設與手動選項。不要把 effectiveType 當精準頻寬測速。
3. 測三種情境：快速網路、慢速網路，以及缺少 Network Information API。觀察圖片／影片 bytes、等待時間與畫質是否仍可接受。

## 如何判斷做對了

選擇能由使用者覆蓋的策略，避免「網路一時變慢」就永久提供低品質內容。

## 書籍逐頁核對｜紙本頁 2-43～2-44

書中把「可適性服務」定義為依使用者當下網路情況調整體驗。頁 2-43 以 YouTube 可切換影片畫質為直觀例子：當網路較慢時提供較低成本的內容，或延後非必要資源。書中列出的方向還包含依網路狀況決定是否預載、在特定情況支援離線模式，以及收集網路情況作分析。

頁 2-44 示範在 DevTools Console 讀取 `navigator.connection`，其中 `effectiveType` 描述估計的連線類型，`rtt` 是往返延遲估計；也可聆聽 `change` 事件，在網路情況變動時調整策略。這些值只能當提示，並非對每個使用者、每個瀏覽器都可靠或可用。書中自己也提醒 Network Information API 的瀏覽器支援仍不普遍，因此應以功能偵測和漸進增強設計：沒有此 API 時仍能正常使用，只在有資料時調整圖片／影片品質或預載策略。

## 問題與解答：可適性服務的邊界

**問題 1：`navigator.connection.effectiveType` 是精確網速嗎？** 不是。它是瀏覽器提供的粗略線索，值可能變動，且 API 並非所有瀏覽器都有。只能以功能偵測使用；缺席時仍要有合理預設，不可讓頁面失效。

**問題 2：想為慢網路送低畫質圖片，應怎麼做？** 先提供可接受的預設品質，再依 `saveData`、當前估計或使用者選項選擇更小版本。實際效果要看 Network 中選到的圖片與位元組，以及使用者是否能主動切到高畫質。不要永久把一次慢網路判斷寫死。

**問題 3：為什麼只按網路速度調整不夠？** 慢裝置的 CPU 可能比下載更成問題；使用者也可能在快網路下主動節省流量。可適性服務應把裝置成本、內容重要性與使用者偏好一起考慮，避免把主要資訊直接刪除。
