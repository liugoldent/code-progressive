# Day 30｜系列總結

> 本篇是對 2021 年原系列第 30 篇的學習整理，加入現行實務補充；驗證時以你專案的實測結果為準。

**精華：** 效能優化應形成循環，而不是一次性專案：量測 → 找瓶頸 → 設預算 → 做最小有效修改 → 驗證 → 持續監控。

**解答：** 建立效能責任制度：PR/CI 檢查 bundle 與 Lighthouse budget，上線後監測真實使用者指標與錯誤，定期檢查第三方腳本及熱門路徑。發現退化時以相同測試案例定位到變更，修正後留下自動化守門條件。

**最重要的結論：** 不要為了「看起來很進階」而加技術。最佳解取決於使用者、裝置、網路、內容、架構與維護成本。

## 深入理解

完整流程是選使用者任務、取 baseline、找最大瓶頸、提出假設、只改一項、重新量測、上線後監控。一次優化成功只是開始，產品與第三方資源變動會讓效能再次退化。

## 實作與驗證

每個 PR 記錄受影響頁面、目標指標、前後數值與測試條件。對 bundle bytes、圖片大小、關鍵頁面設定 CI budget；RUM 監測 p75 與尾端使用者，並定期檢查第三方腳本和快取命中。

## 常見誤區與取捨

任何技巧都有成本；若沒有可觀察的使用者收益，應保留更簡單的方案。效能預算也需隨產品與裝置分布調整。
