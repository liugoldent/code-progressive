### 1. 看到這題，怎麼想到要用左右最大值與雙指標？

**先抓住這個想法：** 一格能留多少水，取決於它左邊和右邊各有多高的牆；水面只能到兩邊較低的那道牆。雙指標讓我們先結算已經有足夠資訊的一側。

可以照這個順序想：

1. **題目要我回答什麼？** 所有位置能留下的水量總和，所以先想單獨一格怎麼算。
2. **最直接怎麼做？** 每格往左、往右找最高柱，再以兩邊較低的高度減去該格柱高。
3. **哪件事一直重複？** 每換一格，又從頭找左右最高柱。先存兩張前後最大值表，就能避免重找。
4. **真的需要存整張表嗎？** 如果只求總量，當已知一側最高柱比另一側低，較低側這一格的水深已可確定；結算後就往內移動。

拿 `[4, 2, 0, 3, 2, 5]` 的索引 1 想一次：左邊最高是 4，右邊至少有高度 5，因此這格水位只能到 4，留住 `4 - 2 = 2`。只看緊鄰柱會漏掉遠處高牆；只保存「某高度出現過」的 Set 也不能表達每格左右的邊界。

**下次可以怎麼想：** 若每格的答案受左右邊界中較小的一側限制，且另一側已有至少同高的邊界，就能先結算較小側。先從逐格正確計算出發，再找可省掉的重複掃描。

### 2. 暴力解

每格 i 各掃一次含自己的左側、右側最大值，相減算該格水量；邊界至少包含自己，因此結果不會為負。

#### TypeScript

```ts
function trapBrute(height: number[]): number {
  let total = 0;
  for (let i = 0; i < height.length; i++) {
    let leftMax = height[i], rightMax = height[i];
    for (let j = 0; j < i; j++) leftMax = Math.max(leftMax, height[j]);
    for (let j = i + 1; j < height.length; j++) rightMax = Math.max(rightMax, height[j]);
    total += Math.min(leftMax, rightMax) - height[i];
  }
  return total;
}
```

#### Python

```python
def trap_brute(height: list[int]) -> int:
    total = 0
    for i in range(len(height)):
        left_max = right_max = height[i]
        for j in range(i):
            left_max = max(left_max, height[j])
        for j in range(i + 1, len(height)):
            right_max = max(right_max, height[j])
        total += min(left_max, right_max) - height[i]
    return total
```

### 3. 暴力解的瓶頸

`n` 格各掃一次左右兩側，單格最多檢查 `n` 根柱子，總時間 `O(n²)`、額外空間 `O(1)`。例如相鄰兩格都會再次檢查多數相同柱子，反覆尋找同一段的最高高度。

### 4. 從瓶頸推導資料結構／演算法

先用一次由左到右的掃描記下每格「到此為止的最高柱」，再由右到左記下「從此往右的最高柱」。每格直接查兩張表後加總，時間降為 `O(n)`，額外空間是 `O(n)`。

如果只要總量，就繼續問：可否在走到一格時直接結算，而不保存所有格子的最大值？兩端逐步縮進，每輪先更新兩側已知最大值。較小最大值那側已經有足夠高的對面邊界，因此能立刻結算，省掉兩張表。

### 5. 為什麼是這個資料結構／方法

| 需要的操作 | 使用的狀態 | 成本 |
| --- | --- | --- |
| 讀取兩端高度 | `height[left]`、`height[right]` | 每輪 `O(1)` |
| 記住兩側已見過的最高柱 | `leftMax`、`rightMax` | 每輪 `O(1)` |
| 加入已確定的一格水量 | `total` | 每輪 `O(1)` |

兩個最大值是各自已掃過區段的最高柱，不只是目前端點高度。這個版本以最大值決定移動哪一側；不能把另一種雙指標版本的判斷條件任意混進來。

### 6. 最佳解法步驟

1. 設 `left = 0`、`right = n - 1`，兩側最大值與 `total` 都從 `0` 開始。
2. 先把目前兩端柱高納入 `leftMax`、`rightMax`。
3. 若 `leftMax <= rightMax`，加上 `leftMax - height[left]`，再讓 `left` 往右移。
4. 否則加上 `rightMax - height[right]`，再讓 `right` 往左移。
5. 直到 `left > right`；每格恰好結算一次。

### 7. 核心不變量：每輪都要保持什麼

每輪更新最大值後，`leftMax` 是 `[0, left]` 的最高柱，`rightMax` 是 `[right, n - 1]` 的最高柱；區間外格子的水量已正確計入 `total`。

若 `leftMax <= rightMax`，右側已經有一根至少與 `leftMax` 一樣高的柱子，所以左端這格的水位由 `leftMax` 決定。相反情況就結算右端。兩側相等時，任選一側都正確。

### 8. 手動演算

| [4,2,0,3,2,5] 的 left,right | leftMax,rightMax | 本輪新增水量 | 總量 |
| --- | --- | --- | --- |
| 0,5 | 4,5 | 4−4=0 | 0 |
| 1,5 | 4,5 | 4−2=2 | 2 |
| 2,5 | 4,5 | 4−0=4 | 6 |
| 3,5 | 4,5 | 4−3=1 | 7 |
| 4,5 | 4,5 | 4−2=2 | 9 |

### 9. 完整實作

以下函式可直接拿來做本機練習。提交 LeetCode 時，依編輯器模板保留要求的函式名稱；Python 可放進 `class Solution` 並加上 `self`，其餘演算法相同。

#### TypeScript

```ts
function trap(height: readonly number[]): number {
  let left = 0, right = height.length - 1;
  let leftMax = 0, rightMax = 0, total = 0;
  while (left <= right) {
    leftMax = Math.max(leftMax, height[left]);
    rightMax = Math.max(rightMax, height[right]);
    if (leftMax <= rightMax) {
      total += leftMax - height[left];
      left++;
    } else {
      total += rightMax - height[right];
      right--;
    }
  }
  return total;
}
```

#### Python

```python
def trap(height: list[int]) -> int:
    left, right = 0, len(height) - 1
    left_max = right_max = total = 0
    while left <= right:
        left_max = max(left_max, height[left])
        right_max = max(right_max, height[right])
        if left_max <= right_max:
            total += left_max - height[left]
            left += 1
        else:
            total += right_max - height[right]
            right -= 1
    return total
```

### 10. 複雜度分析

- 時間複雜度：`O(n)`。指標每輪只移動一次，共結算 `n` 格，每輪只有固定次數的比較、加減與更新。
- 額外空間複雜度：`O(1)`。只保存兩個指標、兩個最大值與總量，沒有建立與 `n` 同長度的表。
- 暴力解是 `O(n²)` 時間、`O(1)` 空間；前後最大值表是 `O(n)` 時間、`O(n)` 空間。

在官方限制下，水量總和不超過 `2 × 10^9`，JavaScript `number` 能精確表示這個整數範圍。

### 11. 邊界條件與常見錯誤

- **先相減再更新最大值：** 目前柱子可能高於舊的最大值，造成負水量；先更新再計算。
- **取兩側較高者當水位：** 水會從較低的一側流走，必須受較低邊界限制。
- **只看緊鄰柱：** 遠處更高的柱子也可能擋水，例如 `[3, 0, 1, 0, 3]`。
- **和 Container With Most Water 混淆：** 本題加總所有格子的水，不是從兩根柱子中挑最大面積。
- **混用雙指標版本：** 這份實作先更新最大值，再比較 `leftMax` 與 `rightMax`；若改成比較端點高度，需要重新檢查不變量。

### 12. 為什麼不用其他方法

| 方法 | 時間 | 額外空間 | 適用情況 |
| --- | --- | --- | --- |
| 每格重找兩側最高柱 | `O(n²)` | `O(1)` | 最容易先驗證題意，規模小時可作基準 |
| 前後最大值表 | `O(n)` | `O(n)` | 要畫每格水深，或想直接看到每格兩側邊界 |
| 單調堆疊 | `O(n)` | `O(n)` | 逐個凹槽結算，需小心寬度與等高柱 |
| 左右最大值＋雙指標 | `O(n)` | `O(1)` | 只需要總量時省記憶體 |

若題目改成「回傳每格水深」，輸出本身就需 `O(n)` 空間，前後最大值表通常更方便解釋與實作。

**單選｜每輪更新左右最大值後，為什麼可以先結算較小最大值的那一側？**

- [ ] A. 對側已有至少同高的柱子，這格的水位上限已可確定。
- [ ] B. 因為目前端點一定是整張圖最高的柱子。
- [ ] C. 因為任何凹槽只需要看左右相鄰兩根柱子。

<details>
<summary>選完再看答案與解析</summary>

**答案：A。** 例如 `leftMax <= rightMax`，右側已有高度至少為 `leftMax` 的邊界，左端這格的水深就是 `leftMax - height[left]`。B、C 都不是演算法的保證。

</details>

## Stage C｜解題後：遷移到 Production（50–60 分鐘）

### 1. 【這個資料結構／演算法是為了解決什麼問題？】

**回答：** 不想為每個位置再把左右兩邊查一遍。若一排高度要反覆預覽，逐格重找高牆會做很多重複工作。

例如 `[3, 0, 3]` 的中間格，左右都有高度 3 的牆，水深是 3。暴力解每換一格又找一次牆；雙指標則記住兩側已看到的最高牆，在能確定水位時立刻加總。

`leftMax`、`rightMax` 保存已知的邊界高度；雙指標演算法決定哪一側已可結算。從逐格掃描的 `O(n²)` 時間降到 `O(n)`，核心只需 `O(1)` 額外空間。代價是它只直接產生總量；若畫面要顯示每格水深，仍需 `O(n)` 的輸出資料。

### 2. 【現實工作中哪裡會遇到？可以用這個題型去改善什麼？】

#### 情境 A：遊戲關卡編輯器的剖面預覽

- **原本麻煩在哪？** 編輯器每次更新高度圖，都為每格重新搜尋左右最高點；地形長、更新頻繁時，重複掃描可能影響預覽。
- **怎麼套用本題？** 將陣列元素對應到等寬地形格的高度，用雙指標算出靜態可蓄水的剖面面積，再乘實際格寬。
- **做到哪裡就不夠？** 若要顯示每格水位，需要保存每格結果；若有三維側向出口或排水孔，這個一維模型就不適用。

#### 情境 B：教學工具的演算法示意

- **原本麻煩在哪？** 學生拖動柱高時，工具要即時更新水量；逐格重找邊界會重複計算。
- **怎麼套用本題？** 柱高就是 `height[i]`，雙指標可快速更新總量；若要動畫展示每格水深，可選前後最大值表，讓每格的邊界可直接顯示。
- **做到哪裡就不夠？** 這只是在一維靜態剖面計數，不是流體的流速、時間或排水預測。

### 3. 工程遷移情境

下面展開關卡編輯器的靜態剖面檢查。輸入是等寬格子的高度和每格寬度；回傳剖面面積，單位為「高度單位 × 寬度單位」。這是編輯器的示意數值，不宣稱是現實排水量。

### 4. 常見直覺寫法

```ts
function validateProfile(heights: readonly number[], cellWidth: number): void {
  if (!Number.isFinite(cellWidth) || cellWidth <= 0 || cellWidth > 1000
      || heights.length > 20000
      || heights.some(h => !Number.isFinite(h) || h < 0 || h > 100000)) {
    throw new Error("Invalid one-dimensional profile.");
  }
}
function basinAreaBefore(heights: readonly number[], cellWidth: number): number {
  validateProfile(heights, cellWidth);
  return trapBrute([...heights]) * cellWidth;
}
```

這個版本先驗證資料，再借用 Stage B 的暴力解。複製陣列是為了配合暴力解接受可寫陣列的型別；暴力解本身不會修改輸入。資料少時，這種寫法容易閱讀，也足夠使用。

### 5. 潛在問題與觸發門檻

一次有 20,000 格時，暴力解約需檢查 `n × n` 量級的高度；拖曳期間若多次重算，累積成本會增加。這是工作量推估，不是實測耗時。先量測一次更新的格數、觸發頻率和整體畫面延遲，才能判定這段是否真的是瓶頸。

### 6. 套用本題技巧

LeetCode 的「一格柱高 → 這格水深」對應到編輯器的「一格地形高度 → 這格剖面蓄水深度」。兩端開放、等寬、靜態這三個前提要保留；算出所有格子的水深總和後再乘格寬。若高度是小數，同樣的邊界推理成立，但結果會有浮點誤差，測試應使用容許誤差。

### 7. Production 風格優化

工程例子以 TypeScript 展示資料契約；演算法本身的雙語版本與測試見 Stage B。Stage B 的 `trap` 不修改輸入，完整實作可將參數標為 `readonly number[]`，因此不需要複製整份高度圖。

```ts
function basinArea(heights: readonly number[], cellWidth: number): number {
  validateProfile(heights, cellWidth);
  return trap(heights) * cellWidth;
}
```

驗證與演算法各走訪一次陣列，仍是 `O(n)` 時間；函式不保留輸入，也不更改編輯器持有的資料。若狀態在計算期間可能被其他流程修改，呼叫端需提供穩定快照。

### 8. 優化前後比較

| 面向 | 逐格重找邊界 | 雙指標結算 |
| --- | --- | --- |
| 單次計算時間 | `O(n²)` | `O(n)`，含輸入驗證 |
| 額外空間 | 暴力解本身 `O(1)`；目前包裝時的複製為 `O(n)` | `O(1)` |
| 輸入修改 | 不修改 | 不修改 |
| 回傳內容 | 總面積 | 相同的總面積 |
| 小數高度 | 近似面積 | 同樣是近似面積 |

這是複雜度比較，不是延遲實測。若要驗證小數面積，應使用明確的誤差容許值，不要求十進位逐位相等。

### 9. 使用界線與代價

- 圖很短、更新很少時，簡單的暴力解可能更容易維護；是否換法取決於實測與需求。
- 每次修改仍會重算全圖 `O(n)`，雙指標不是常數時間的局部更新。
- 需要逐格水深時，結果本身就占 `O(n)` 空間；前後最大值表可能更清楚。
- 若關卡有排水孔、三維旁路或流動速度要求，需另外建立模型；此演算法不能替代物理模擬。

### 10. Code Review 說法

> 這裡每次更新都為每格重找左右邊界。若高度圖規模和更新頻率已影響預覽，可以用左右最大值加雙指標，一次走訪取得同樣的總面積。建議一起寫清楚格寬、開放邊界與小數容差；若畫面要逐格水深，則保留逐格資料的方案更合適。
