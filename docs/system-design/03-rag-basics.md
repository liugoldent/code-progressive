# RAG 入門：讓 AI 根據自己的資料回答

**RAG** 是 **Retrieval-Augmented Generation**，中文常譯作「檢索增強生成」。白話說：**先從指定資料中找出相關內容，再把找到的內容交給語言模型組織答案**。這是一種系統設計方法，不是一個模型名稱，也不等於向量資料庫。[RAG 原始論文](https://arxiv.org/abs/2005.11401)、[Azure AI Search 的 RAG 說明](https://learn.microsoft.com/en-us/azure/search/retrieval-augmented-generation-overview)

## 1. 先看一個你可能會做的功能

假設你做了「企業稽核與監控平台」，裡面有操作手冊、稽核規則與故障紀錄。使用者問：

> 「上週那次付款告警是什麼原因？後來如何處理？」

一般語言模型沒有讀過你公司的上週紀錄。直接請它回答，可能得到一段流暢但沒有根據的推測。RAG 的流程是：

```text
使用者問題
    ↓
後端確認使用者身分與資料權限
    ↓
從使用者可讀的故障紀錄中找相關片段
    ↓
把問題與片段交給語言模型
    ↓
回傳摘要、來源連結；證據不足就說明查不到
```

例如系統找到 `INC-104` 的處理紀錄後，可以回答「監控顯示付款回呼重試造成重複告警；團隊調整去重規則並補上測試」，並附上紀錄連結。**來源連結幫助使用者核對，但模型仍可能誤讀內容；不能把有引用當成正確保證。**

## 2. RAG 分成建資料與回答問題兩段

| 階段 | 做什麼 | 需要注意 |
| --- | --- | --- |
| 建資料 | 收集文件，解析文字與表格，切成可搜尋的片段，保存文件 ID、版本、來源、權限等資訊並建立索引 | 文件更新或撤權時，索引也要跟著更新 |
| 回答問題 | 根據問題檢索片段，過濾無權限內容，挑選足夠且相關的證據，交給模型產生答案 | 找不到證據時不要要求模型猜；答案要能回到原文核對 |

「切塊」（chunking）是把長文件分成可檢索的片段。太大可能帶進很多無關內容；太小可能失去上下文。例如一條稽核規則的「條件」與「例外」若被拆開，只找回條件就容易答錯。切塊時要保留章節標題、來源與相鄰內容，並用實際問題測試效果。[Azure 文件切塊說明](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents)

## 3. 一定要用向量資料庫嗎？

**不用。** 檢索可以從普通資料庫篩選或全文搜尋開始。向量搜尋會把文字轉成 embedding（用數值表示語意），適合找字面不同但意思接近的內容；但精確的事件編號、錯誤碼與人名，關鍵字或欄位查詢往往很重要。兩者結合稱為 **hybrid search（混合搜尋）**；候選內容太多時還可以用 reranker 重新排序。[Azure AI Search 的檢索說明](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-information-retrieval)

對這個作品，第一版可以先用 **FastAPI + PostgreSQL 全文搜尋**，從有權限的故障紀錄取回少數片段。當你發現同義詞、不同說法導致漏找，再測試向量或混合搜尋，量化是否真的改善。React／Vue 前端只負責提問、顯示答案與來源；檢索、權限、模型呼叫都在後端。

## 4. 它與一般搜尋、長提示、微調有什麼差別？

| 做法 | 適合的情況 | 要付出的代價 |
| --- | --- | --- |
| 一般搜尋 | 使用者願意自己閱讀原文，或需要精確篩選與列表 | 不會自動整理跨文件答案 |
| 把文件直接貼進提示 | 資料少、更新不頻繁，能放進模型上下文 | 文件增多後，成本、長度與挑選資料會變難 |
| RAG | 資料多、會更新，需要依問題取用並附來源 | 要維護解析、索引、檢索、權限與評估流程 |
| 微調 | 想改變模型的行為、格式或特定任務表現 | 需要訓練資料與評估；不能把它當成會即時更新的文件庫 |

選法取決於需求。若只是查 `INC-104` 的原始紀錄，資料庫查詢或搜尋可能已足夠；若要綜合多份有權限的紀錄並用自然語言回答，才值得加入 RAG。

## 5. 上線前最容易踩的坑

1. **找到錯資料。** 分別檢查「正確來源有沒有被找到」與「模型有沒有根據來源回答」；只看答案是否流暢不夠。
2. **權限外洩。** 每次查詢都依使用者權限限制可檢索文件；不能只在前端藏連結，也不能先把所有文件送給模型再請模型自行忽略。[Microsoft Foundry 的權限與限制說明](https://learn.microsoft.com/en-us/azure/foundry/concepts/retrieval-augmented-generation)
3. **文件過期。** 保存版本與更新時間；刪除或撤權後要同步更新索引，避免舊片段繼續被找到。
4. **沒有證據仍硬答。** 設定可核對的來源格式；沒有足夠片段時回覆「目前資料不足」，並允許使用者打開原文。
5. **只測理想問題。** 準備一組真實問題，包含錯字、同義詞、跨文件問題、無答案問題與無權限問題。先量「檢索是否找對」，再看「答案是否忠於找到的內容」。[Azure RAG 評估指南](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-llm-evaluation-phase)

## 6. 你可以先做的最小練習

用 10～20 份**自製的假資料**，各寫一個故障編號、原因、處理方式、時間與可讀角色。完成後，用以下五題手動驗收：

- 問精確編號時，能找到正確紀錄並附來源嗎？
- 換一種說法問同一事故時，能找到嗎？
- 問兩份紀錄的共同原因時，能區分各自的證據嗎？
- 問不存在的事故時，會明確說資料不足嗎？
- 用沒有權限的角色提問時，檢索結果與答案都不會露出受限內容嗎？

先把「找得到、找得對、看得到來源、守得住權限」做好，再決定是否需要 embedding、向量資料庫或 Agent。這也是[職涯與面試藍圖](../career-blueprint/01-future-blueprint.md)中全端 AI 作品可以逐步加上的功能。
