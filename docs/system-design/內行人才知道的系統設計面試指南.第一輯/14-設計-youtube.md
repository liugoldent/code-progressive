**讀這章的順序：**先把錄播影片的上傳與播放分開；再問大檔、轉碼成本、終端相容性與權限。原書的 DAG、資源管理工具與暫存空間是轉碼路徑的核心，並非所有影片都要同步完成全部畫質才能發布。以下狀態機、欄位與故障演練是本站的具體化推導。

## 先縮小題目範圍

YouTube 是大型產品，不可能在一次面試中設計全部。先確認核心範圍：上傳、轉碼、播放、搜尋、推薦、留言、直播，哪些要做？以下假設只做**錄播影片上傳、基本 metadata 與播放**，不做推薦和直播。品質要求包括大檔可續傳、上傳成功後不遺失原檔、轉碼可重試、播放可依網速選畫質。

## 把控制平面與資料平面分開

API 管帳號、影片權限、metadata、狀態與播放授權；真正的大檔位元組走物件儲存與 CDN。若每段影片都流經 API 主機，擴容與出口成本會很快失控。

```text
Creator → API 取得上傳授權 → Object Storage 分段上傳
                              → 完成事件 → Queue → Transcode Workers
                                               ├→ 多畫質片段與 manifest
                                               └→ 縮圖/審核/metadata

Viewer → API 驗權並取得播放 manifest → CDN → 各畫質片段
```

## 上傳狀態機

`initiated → uploading → uploaded → processing → ready`；失敗進 `failed`，並保留原因與重試方式。上傳端將檔案切片，每片有序號、大小與校驗碼；中斷後查已完成片段，只補缺少的部分。完成事件要驗證總片數、內容雜湊與總大小。客戶端宣稱完成，不等於伺服器已取得完整可靠原檔。

上傳授權應有時效、大小上限與對應對象；不允許持有授權的人覆蓋其他影片。暫存片段若長時間未完成，要定期清理。使用者看到的狀態要準確：「上傳完成，正在處理」和「可播放」是不同承諾。

## 轉碼管線

轉碼 Worker 讀原檔，輸出多種解析度/碼率，切成可串流片段，產生播放清單與縮圖。工作需要固定 `job_id`、輸入版本與輸出版本；重試時若已有成功輸出，應核對並重用，不能無限制重複占用 CPU。輸出先放暫存命名空間，全部片段與 manifest 驗證完成後，再讓 metadata 原子地切成 `ready`。

若轉碼三次失敗，保留原檔和失敗紀錄，前端顯示可理解狀態；人工修復或新版本轉碼不能誤把半成品標成可播放。不同畫質可按需求逐步生成，但播放清單只能列出真的可用版本。

### 封裝格式、編碼與畫質版本是三個概念

**容器**（例如 MP4）規定影音軌道與 metadata 如何封裝；**codec**（例如 H.264、AV1）規定影像如何壓縮與解碼；**解析度/碼率**則影響每個播放版本的畫質、頻寬與成本。相同容器可以放不同 codec，相同 codec 也可以有多種解析度。選轉碼組合時要考慮裝置支援率、授權/編碼成本與輸出體積，不能把「轉成 MP4」當成所有播放器都能播的充分條件。

### 把轉碼排成有依賴的 DAG

```text
原檔驗證 / 媒體探測
  ├→ 擷取縮圖
  ├→ 360p 轉碼 → 分段與校驗 ┐
  ├→ 720p 轉碼 → 分段與校驗 ├→ 產生 manifest → 發布版本
  └→ 1080p 轉碼 → 分段與校驗┘
```

縮圖與各畫質轉碼可平行執行；manifest 必須等它要列出的片段完成並通過檢查。若產品允許「低畫質先上線」，可以先發布只含 360p 的 manifest v1，後續新增 720p/1080p 時發布 v2；不能先列出尚未存在的片段。DAG 任務表可記 `job_id, input_hash, step, output_version, status, attempt, lease_until`，Worker 租約過期後可重跑；輸出使用固定的版本路徑，完成發布才切換對外指標。

轉碼資源應按輸入長度、解析度與 codec 估成本，大影片可能佔用 Worker 很久。若單一 FIFO 讓長任務排在前面，短影片也會久等；可分尺寸佇列或採公平排程，但仍要防止長影片飢餓。監控每一 DAG 階段的排隊、執行、失敗與重試時間，才能知道「上傳到可播放」慢在哪裡。

### 預處理、排程與 Worker 的責任界線

原檔到達後，預處理器先做媒體探測：長度、軌道、解析度、codec、檔案是否能解碼，再依輸出規格建立 DAG。若把影片切成 GOP（影格群）處理，要確認切點可獨立解碼、聲畫時間戳能對齊；最後合併不能只照任務完成時間，必須依媒體時間順序。每個 DAG 節點應有輸入版本、預期輸出、相依節點與完成條件。

排程器只派發相依任務已完成的節點。資源管理者追蹤 Worker 的能力和空閒量，例如 CPU/GPU、可用記憶體、支援 codec、所在區域。Worker 領到任務後設租約，定期心跳；超時才由其他 Worker 接手。完成回報先驗證輸出物件與校驗碼，然後原子地把任務狀態從 `running` 改成 `done`。若原 Worker 在租約過期後才回報，不能覆蓋新 Worker 的結果；可用 attempt/lease token 比較。

暫存空間用來存切片、中間音軌、工作設定與重試線索。它的保留期要長於可重試窗口，正式發布後再依引用關係清理。若暫存空間塞滿，直接增加 Worker 只會製造更多中間檔；排程器需依剩餘容量回壓，暫停接新任務或降低並行度。

## 播放與適應性串流

播放器先取得 manifest，再依網路速度、緩衝與裝置能力選片段畫質。熱門影片適合 CDN 快取，冷門影片可能常回源。CDN key 要包含內容版本和必要的權限資訊；私有影片授權不能只靠播放器 UI 隱藏。播放失敗時可降畫質、換 CDN 路徑或重試片段，但重試須設上限。

| 指標 | 為何重要 |
| --- | --- |
| 開始播放時間 | 封面到首幀的用戶感受 |
| 卡頓比例與次數 | 比 API 平均延遲更貼近播放品質 |
| 平均畫質與切換 | 太積極升畫質可能導致卡頓 |
| 轉碼等待時間 | 上傳後多久可播放 |
| CDN 命中與回源 | 成本與來源站壓力 |

## 容量與成本估算

10 萬人同時看平均 2 Mbps，對觀看者的出口約 `100,000 × 2 Mbps = 200 Gbps`。這遠高於一般 metadata API 頻寬。儲存要算原檔、多畫質版本、縮圖、暫存、備份；轉碼要算每天上傳分鐘數、每分鐘需要的 CPU/GPU 時間，以及尖峰排隊。CDN 命中降低來源站流量，但對外傳輸仍有成本。

## 熱門、冷門與授權一起算

CDN 的價值取決於重複觀看和地理分布。熱門片段可提前推到多個邊緣節點；冷門影片若每個地區只看一次，快取收益可能小於儲存與回源成本。可按最近觀看量、回源率與地區將影片分層，但移出 CDN 後要量測首幀延遲，不能只看帳單。這些是示意策略，實際 CDN 定價、計費方向與最小快取單位需按供應商確認。

預簽名上傳 URL 要綁定影片、物件路徑、方法、期限與內容大小；API 發出授權前先驗使用者配額和權限。私有影片的播放授權則可用短效簽名 cookie 或片段 URL，撤權時要有明確的最長生效時間。DRM、加密與水印處理的是不同風險：加密保護傳輸或儲存，DRM 控制受支援播放器的授權播放，水印提高外流追溯能力；它們都無法保證已觀看內容永遠不被錄製。

## 故障與自測

1. 上傳完成事件重複投遞，如何避免同一影片被轉碼兩次？
2. 轉碼輸出 90% 片段後 Worker 當機，哪個狀態對外可見？如何修復？
3. 影片被撤權，但 CDN 還有快取片段，授權多久必須生效？
4. 若熱門影片 1 小時有 200 萬人觀看，最先估的是 API QPS、CDN 出口還是資料庫寫入？為什麼？

## 自測參考解答與面試追問

### 為何影片上傳與播放不都經過 API 伺服器？（對照原書第 255–261 頁）

**答：**API 處理身份、metadata 與授權，影片位元組是大吞吐資料路徑。若 1 GB 上傳或 2 Mbps 的播放都穿過 API，API 的網卡與出口費會先成瓶頸。上傳時 API 發短效預簽名 URL，客戶端直接送物件儲存；播放時 API 回授權資訊與 manifest，片段由 CDN 供應。這也讓 API 可無狀態擴容；但需要明確驗證物件上傳完成事件、權限和 CDN 撤銷窗口。

### DAG 裡哪些任務能平行，哪些必須等待？（第 262–270 頁）

**答：**讀取原檔後，影像、音軌、縮圖、不同解析度轉碼可依輸出需求平行；封裝與 manifest 只能引用已完成且校驗通過的產物。排程器維護每個節點的相依計數，只有前置任務全成功才派發。若縮圖失敗但影片片段完成，是否允許先發布，要由產品的「可播放」條件定義；若 manifest 列了尚未生成的片段，播放器會在播放中途失敗。暫存空間保存中間產物，以免一個節點失敗就重做整部影片。

### 1. 完成事件重複投遞，如何避免重複轉碼？（對照原書第 256–259、264–269 頁）

**答：**事件至少一次投遞是正常情況。用 `(video_id, source_version, output_profile)` 當工作唯一鍵，排程器以條件插入建立 DAG；重複事件只讀既有工作狀態。Worker 即使重跑，也輸出到同一版本化暫存路徑，核對成功後才提交完成狀態。這能避免重複對外發布，但仍可能多消耗一次轉碼 CPU；要靠租約、進度 checkpoint 與重試上限降低浪費。

### 2. 轉碼到 90% Worker 當機，使用者看到什麼？（第 262–271、277 頁）

**答：**使用者應看到「處理中」或先前已驗證可播放的低畫質版本，不能看到列出缺少片段的 manifest。排程器在租約逾時後只重跑未完成的 DAG 節點，已有校驗通過的片段可重用；完成者清單和中間檔要保存在可恢復暫存空間。最後由發布步驟檢查 manifest 中每個片段都存在且可讀，再原子切換 metadata 到 `ready`。若原檔本身損毀，進 `failed` 並保留原因，不可無限重試。

### 3. 影片撤權但 CDN 有快取，多久失效？（第 274–278 頁）

**答：**先和產品定義撤權 SLA，例如 60 秒內阻止新的播放授權；技術方案才有可驗證目標。短效播放 token、每段請求驗證、CDN 清除與版本化路徑可縮短窗口，但各自有延遲及成本。若 token 有效 10 分鐘且邊緣不回源驗權，就不能承諾 60 秒撤權。已被下載到客戶端的位元組也無法由伺服器追回，應把保證範圍寫清楚。

### 4. 200 萬人一小時看熱門影片，先估什麼？（第 253–255、272–276 頁）

**答：**先確認平均觀看秒數和平均碼率，再估對外視訊流量；這通常遠大於 metadata API。若每人完整看 10 分鐘、平均 2 Mbps，總傳輸是 `2,000,000 × 600 × 2 Mb = 2.4 Pb ≈ 300 TB`，平均一小時出口約 `667 Gbps`。同時看 CDN 命中率以估回源流量；API QPS 主要受開始播放、換清單和控制操作影響，不是每個影格都打 API。算式是假設例子，實際需按觀看完成率與畫質分布重算。
