## 先界定 feed 是什麼

使用者可發文、追蹤別人、查看首頁動態。先問：首頁嚴格按時間還是演算法排序？發文後多久讓追蹤者看到？私密帳號、封鎖、刪文多久生效？是否顯示已看過的文章？這些決定 fan-out、快取與讀取時的權限檢查。

最小模型：`Post(post_id, author_id, body_ref, created_at, visibility, status)`、`Follow(follower_id, followee_id)`、`FeedEntry(user_id, post_id, sort_key)`。權威來源是貼文與追蹤關係；FeedEntry 可以是可重建的派生資料。

## 發文與讀取資料流

```text
發文 → Post DB 成功 → 發出 post_created 事件 → Fan-out workers
                                       └→ 一般作者：寫粉絲 FeedEntry
                                       └→ 名人：保留供讀取時合併

首頁 → 個人 feed ID 清單 + 名人近期貼文 → 合併排序
     → 批次取 Post/Author → 再驗可見性 → 回傳與游標
```

先讓貼文持久化，再非同步傳播。若 fan-out 落後，發文者自己的頁面仍可從權威 Post DB 看見文章，但追蹤者首頁可能稍晚；要定義可接受的新鮮度。

## 寫入時推送或讀取時合併

| 方案 | 好處 | 代價 |
| --- | --- | --- |
| Fan-out on write | 個人首頁讀取快 | 發文寫入量與粉絲數成正比 |
| Fan-out on read | 發文寫入少 | 首頁要合併大量作者，讀取延遲高 |
| 混合 | 一般作者快讀、名人避免巨量寫入 | 兩條路徑與快取更新更複雜 |

一位名人有 5,000 萬粉絲，同步寫 5,000 萬筆 FeedEntry 會造成巨大寫入放大。讀取時合併名人貼文可避開發文尖峰，但熱門名人的貼文會成為讀取熱點。可快取名人近期貼文 ID，按活躍粉絲數、發文頻率和讀取延遲調整「名人門檻」，而不是設任意常數。

## 只存 ID 或複製正文

FeedEntry 只存貼文 ID，節省空間，也讓內容修改和刪除有單一權威；讀取時需批量取正文，避免對 20 則貼文做 20 次獨立 DB 查詢。若直接複製正文，讀取快，但刪文、改權限時要更新大量副本。常見折衷是存 ID 與小型快照，呈現前仍以權威狀態/版本驗證可見性。

## 排序與分頁

時間序可用 `(created_at, post_id)` 做游標，post ID 解決同一時間戳的平手。若演算法分數會變，使用者翻第二頁時第一頁的文章可能已移動；可固定查詢快照/排序版本，或接受有限重排並在客戶端去重。單純 `OFFSET 100000` 對大型 feed 成本高，且新貼文插入會讓頁碼不穩。

## 隱私與刪文

追蹤關係改變、封鎖、私密帳號、貼文刪除後，舊 FeedEntry 可能仍存在。讀取時必須再檢查權限，背景清理則可稍後做。若產品要求撤權在數秒內生效，不能只依賴長 TTL 的公共快取。互動計數（讚、留言）可較晚更新；正文可見性則要更嚴格。

## 失敗與重試

Fan-out Worker 寫了部分粉絲後當機，重試應以 `(user_id, post_id)` 唯一鍵去重。佇列積壓時可優先處理活躍粉絲或熱門內容，但不可讓其他用戶永久漏貼文；可設補償掃描。貼文刪除時，先改權威狀態使讀取過濾，再非同步清理 FeedEntry。監控 fan-out backlog、首頁 p95、缺失率、重複率、刪文曝光窗口與快取命中率。

## 自測

1. 名人發文後不做寫時 fan-out，首頁要如何在低延遲內合併其貼文？
2. 一位使用者取消追蹤後，舊 feed entry 還在，哪一層防止越權顯示？
3. Feed Worker 重試造成同一貼文寫兩次，你要在哪裡放唯一約束？

## 自測參考解答與面試追問

### 1. 名人不做寫時 fan-out，首頁怎麼查？（對照原書第 189–197 頁）

**答：**普通作者發文後可把 post ID 推進追蹤者的 feed；名人貼文只保留在作者時間線。讀首頁時先讀使用者的預製 feed，再查其追蹤的名人最近貼文，按時間或排序分數合併、去重並截取一頁。名人集合若很大，需限制候選數、快取近期結果或做分層索引；不能對每位名人逐一跨網路查詢。這是把極大的寫入扇出換成可控的讀取合併成本。

### 2. 取消追蹤後，舊 FeedEntry 還在怎麼辦？（第 198–202 頁）

**答：**FeedEntry 是加速首頁的衍生資料，不能單獨當權威授權。讀取時根據目前追蹤/封鎖/貼文可見性過濾；背景任務再清理舊 FeedEntry，以降低長期儲存和查詢浪費。若要求數秒內撤權，權限快取 TTL 與失效通知要符合該窗口。單純等非同步 fan-out 清理完成，期間仍可能曝光私密內容。

### 3. Fan-out Worker 重試，唯一約束放哪裡？（第 193–199 頁）

**答：**在 FeedEntry 的權威儲存上設 `(recipient_id, post_id)` 唯一鍵或冪等 upsert；queue 的去重通常有保留期，也可能在重平衡後重送，不能當唯一防線。若同一貼文可能因排序版本需要重建，可將版本或 feed 類型納入鍵，再定義舊版本清理。Worker 寫了一半失敗時，用相同 event ID 重跑未完成收件者即可，不需回滾已成功的項目。監控每事件完成比例與積壓，避免永久缺貼文。
