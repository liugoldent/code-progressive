面試中要分開說明「事件已記錄」「通知工作已排入佇列」「第三方已接受」「裝置已收到」四個狀態。供應商回成功通常只能證明它接受投遞，不能證明使用者看見。

## 功能需求與優先級

通知可能經 Email、SMS、行動推播與站內通知送達。先問：是交易通知、行銷活動還是驗證碼？是否允許延遲？同一事件要送幾個裝置？使用者能否靜音或取消訂閱？安全驗證碼與行銷訊息不能共用完全相同的優先級、成本上限與重試策略。

一個可靠的通知系統應區分：**業務事件已成立**、**通知工作已排入**、**供應商已接受**、**對方裝置已收到**、**人已閱讀**。後兩種狀態不一定可得，不能把 API 回 `200` 誤寫成使用者已讀。

## 為何先寫 outbox

若訂單資料庫先寫成功、接著送佇列失敗，通知就漏了；反過來先送佇列，訂單交易若回滾，通知又指向不存在的訂單。Transactional outbox 把訂單狀態與待送事件放在同一資料庫交易，背景 relay 再把事件送入佇列。

```text
訂單交易：Order 狀態變更 + Outbox(event_id, order_id, type)
                                      ↓
Relay → Queue → Worker → 偏好/模板/管道 → Email/Push/SMS 供應商
                     └→ Attempt、Receipt、Dead Letter
```

Relay 可能在「送出佇列成功，記錄已送前」當機，所以事件可能重複。outbox 解決的是雙寫遺失窗口，不代表端到端 exactly once。

## 一筆通知的資料模型

`Notification(event_id, recipient_id, channel, template_version, status)`；`Attempt(attempt_id, notification_id, provider, sent_at, provider_message_id, result)`。可用 `(event_id, recipient_id, channel)` 當唯一鍵處理重複事件。模板版本要固定，否則重試時套用新模板，內容可能改變。跨語系時要記錄使用者語言與時區的選取時間。

送出前再檢查偏好、取消訂閱與靜音時段。事件在佇列待了 30 分鐘，使用者可能已改偏好；若依建立當下偏好發送，就會違反後來的選擇。某些安全通知不受一般靜音規則影響，應由產品規則明定。

## 重試、去重與無法完全避免的重複

Worker 可用固定 idempotency key 呼叫支援該功能的供應商。若供應商逾時但其實已送成功，且不支援查詢/冪等，重試可能發兩次。對 SMS 高成本管道，可在逾時後先查供應商狀態或延遲重試，但仍可能有不確定性。系統需明確記錄 `unknown` 狀態，不要把不確定當成未送。

重試應依錯誤類型：暫時 5xx/限流可退避；永久格式錯誤、無效 token、取消訂閱不應無限重試。超過上限進死信佇列，附原因、事件 ID 和修復路徑。若大量供應商故障，要限制重試風暴和積壓對正常新通知的影響。

## 多供應商與管道差異

| 管道 | 特別要處理 |
| --- | --- |
| Email | 退信、投遞延遲、寄送信譽、退訂 |
| SMS | 單價、國別限制、供應商配額、發送窗口 |
| Push | 裝置 token 過期、使用者多裝置、通知權限 |
| 站內通知 | 權威儲存、分頁、未讀數與多裝置同步 |

供應商備援可降低單一供應商故障，但切換時仍可能重複。應記錄選用供應商、切換原因與發送嘗試，並測試備援是否真的能在配額與模板限制下工作。

## 觀測與故障推演

監控 queue age（等待最久多久）、端到端送出延遲、各管道成功/永久失敗/未知率、供應商 429/5xx、重試倍率、死信數與成本。用事件 ID 串起業務、outbox、佇列、Worker 和供應商紀錄，才能追查「客戶說沒收到」。

**情境：** 訂單成功，SMS 供應商逾時但其實已接受；Worker 當機。恢復後先查是否有 provider message ID 或供應商狀態；若查不到，只能依產品設定決定重試或人工處理，不能宣稱絕不重複且絕不漏發。

## 自測

1. 畫出「寫訂單成功但送佇列失敗」的雙寫故障，並用 outbox 改寫。
2. 同一事件重複送達三次、使用者有兩台手機，通知唯一鍵應包含哪些欄位？

## 自測參考解答與面試追問

### 1. 訂單寫成功、送佇列失敗，outbox 怎麼修？（對照原書第 171–180 頁）

**答：**直接「先寫訂單，再送 queue」會在兩步之間當機，留下有訂單、沒有通知的狀態。把訂單與一筆 `NotificationRequested` outbox 紀錄放在同一個資料庫交易；交易提交後，由 relay 掃 outbox 發佈到 queue。Relay 發佈成功、標記 outbox 已處理前也可能當機，所以事件會重複；消費者仍需用 event ID 去重。這保證不因雙寫缺口漏掉已提交訂單的通知意圖，並不保證外部供應商只發一次。

### 2. 事件重複三次，使用者有兩台手機，唯一鍵怎麼設？（第 176–184 頁）

**答：**先分清**業務通知**與**裝置投遞**。業務通知可用 `(event_id, recipient_id, channel, template_version)` 去重；Push 投遞則再加入 `device_id` 或裝置 token 版本，使兩台手機各收一次，但同一台不因三次事件重複建立三筆投遞。若使用者關閉某裝置權限，該裝置任務應取消或標成永久失敗，不應影響另一裝置。實際顯示仍可能因供應商重送而重複，App 可用 notification ID 做最後一道去重。

### 3. 供應商故障一小時後恢復，怎樣排空？（第 182–188 頁）

**答：**先把佇列依優先級、到期時間與管道分開：驗證碼等短效訊息過期後不應再送，交易通知優先於行銷訊息。Worker 用供應商允許的速率逐步放量，加退避和抖動；有備援供應商時也要確認其配額與模板已備妥。觀測 queue age、重試率、429/5xx 和每秒實際送出量，並用死信佇列收斂永久失敗。一次把所有 Worker 開滿只會再次把供應商打倒。
