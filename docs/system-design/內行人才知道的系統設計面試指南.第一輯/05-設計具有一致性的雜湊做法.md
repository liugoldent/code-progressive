原書著重**環上的映射如何變化**；實務上還要補問「資料何時完成搬遷、期間寫入交給誰、舊路由如何退場」，因此下面另列擴容時間線。

## 為什麼 `hash(key) % N` 會出問題

把 `key` 的雜湊值除以節點數 `N` 取餘數，固定 N 時容易實作；但 N 從 4 變 5，原本多數 key 的餘數可能改變。大型快取會發生大量 miss；權威資料庫分片則要搬大量資料。這不是雜湊函式品質不好，而是分母 N 改變造成的映射變化。

一致性雜湊把 key 與節點都放在同一個環狀雜湊空間。從 key 的位置順時針找到第一個節點，該節點負責 key。新增一個節點時，主要只有新節點接手的環區間改變負責者；刪除一個節點時，主要由順時針下一個節點接手其區間。

```text
環上的位置（示意）
A ── key1 ── B ── key2 ── C ── key3 ── (回到 A)
key1 → B；key2 → C；key3 → A
```

這個示意只描述**路由**。新節點不會因為上環就突然持有資料；舊副本、新副本、變更日誌與切換時機需要單獨設計。

## 兩個最重要的分布問題

**實體節點分布不均。** 若每台節點只在環上有一個位置，某節點可能負責很大的區間。讓每台機器擁有多個虛擬節點，可把責任區間拆散，降低不均衡。容量較大的機器可配置更多虛擬節點，但多一層路由管理與搬遷成本。

**key 數量平均不等於負載平均。** 一個有千萬次/秒讀取的熱門 key，即使只占一筆資料，也會打滿其負責節點。可做讀取副本、本地短 TTL 快取、熱 key 複製或業務拆鍵；若是寫入熱點，複製讀取資料不能解決寫入競爭。

## 擴容時的實際時間線

1. 發布新的環版本與節點健康資訊；舊版本路由器暫時仍可能存在。
2. 新節點從原負責者複製將接手的資料。原節點繼續處理請求。
3. 捕捉搬遷期間的增量寫入：變更日誌、雙寫或短暫暫停寫入均有不同取捨。
4. 核對資料量、校驗碼、複寫落後，達到門檻才把新節點設為權威。
5. 舊路由收到請求時轉送或要求客戶端重試；觀察一段時間後回收舊資料。

若第 3 步雙寫只有一邊成功，就需要重試、操作 ID 與核對。若在資料搬遷過程又有節點故障，需能暫停、回滾或重新配置責任。**演算法降低映射變動，不等於線上遷移零停機。**

## 複本與故障切換

每個 key 若要三份副本，可以取環上後續三個**不同故障域的實體節點**；不能把同一台主機的三個虛擬節點當三份容錯副本。節點故障後，路由表與副本集合要更新；原節點恢復時不能直接以舊資料覆蓋較新的版本。要以版本/日誌決定資料追趕。

## 何時不必用環

若是少量可重建快取、節點很少且擴縮頻率低，簡單路由也許足夠；若資料庫已有內建分片與重平衡，應理解並使用它的機制，不必自己在應用層再造一個環。若需求是範圍掃描或同租戶資料共置，純雜湊可能讓查詢跨許多節點，需另選分片鍵或二級索引。

## 自測

1. 畫三台節點的環，加入第四台後標出哪些 key 改變負責者；再說資料如何搬。
2. 若某台節點有 10% 的 key 卻承受 70% 流量，虛擬節點是否一定有用？
3. 節點恢復時，如何避免其舊資料覆蓋故障期間的新寫入？

## 自測參考解答與面試追問

### 1. 三台變四台，哪些 key 會搬？（對照原書第 81–90 頁）

**答：**把節點與 key 都映射到同一個環，key 交給順時針遇到的第一個節點。第四台加入位置 `h(D)` 後，只有它前一個節點到 `h(D)` 之間的 key 主要負責者改成 D；不是所有 key 都重新取模。不過這只說明路由，線上搬遷還要先複製快照、追增量寫入、核對、切路由，最後回收舊副本。若使用虛擬節點，D 會在環上有多個位置，搬遷來源也可能不只一台。

### 2. 10% 的 key 吃掉 70% 流量，虛擬節點一定有用嗎？（第 88–94 頁）

**答：**若流量集中在少數 key，把 key 均勻分散到環上仍無法把**同一個**熱 key 拆開；虛擬節點主要改善 key 數量/容量分布。先查是某一 key、某一租戶，還是某一節點的整體偏斜。讀熱點可用快取或複本分攤；寫熱點可能要把計數拆成多 key 再聚合，或把同一對象的更新序列化。做法取決於讀寫語意，不能只靠改 hash 函式。

### 3. 故障節點回來後怎麼避免舊值覆蓋新值？（第 91–94 頁）

**答：**先把恢復節點標為 `joining`，不要立刻接權威讀寫。從當前責任副本補快照與故障期間的增量，再用版本、log position 或向量時鐘核對。若同一 key 有並發版本，依系統的衝突政策合併或保留多版本，不能只看「哪台最後恢復」。追平後才讓路由把它納入，並在切換時監控讀修復與副本差異。
