書中的小群範例將訊息複製到各收件者的收件箱，讀取簡單但寫入與儲存隨群組人數放大。下面的「只存一份、按游標拉取」是面對大群時另行推導的方案，不能誤認為小群方案可直接擴到所有規模。

## 先問清產品承諾

一對一、群聊、附件、撤回、已讀、搜尋、離線同步、多裝置會改變資料模型。所謂「即時」要問 p95 送達時間；所謂「送達」要問是伺服器收到、持久化、接收裝置收到，還是使用者已讀。這些狀態不能混用。

```text
Sender → Chat Gateway → Message Service → Message Store
                         │                    └→ 收件者同步游標
                         └→ Presence/Route → 在線裝置推送
                                         └→ 離線時推播提醒
```

Gateway 維持 WebSocket 等長連線，驗證身分並路由訊息。持久儲存與同步游標不能只放在 Gateway 記憶體，否則連線節點故障就會遺失已承諾的訊息。

## 一則訊息的生命週期

1. 發送端產生 `client_message_id`，送 `conversation_id, payload, client_message_id`。
2. Gateway 檢查會話權限與訊息大小，Message Service 依會話規則配置 `server_message_id` 與序號。
3. 訊息持久化後回 `server_ack`。這只代表伺服器承諾保存，不是對方已讀。
4. 在線裝置收到推送後可回 `device_ack`；離線裝置稍後用游標補取。
5. 使用者開啟會話時送 `read_receipt`，多裝置之間同步已讀位置。

若發送端 timeout，可能是請求根本沒到，也可能訊息已存但 ACK 遺失。重試必須帶同一 `client_message_id`，服務端以 `(conversation_id, sender_id, client_message_id)` 去重並回原有 server ID。接收端也依 server ID 去重，因為補發和即時推送可能重疊。

## 順序的範圍

多數聊天只需**同一會話內**有穩定順序，不需要所有會話的全域順序。可以讓單一會話的寫入經同一排序分區或序列配置器；但超大群聊會形成熱點。以服務端接受/持久化順序為準，比相信各手機時鐘安全。訊息到達 UI 順序可能與序號不同，客戶端需插入正確位置並處理缺口。

### 離線與多裝置

每台裝置保存最後套用的會話游標。重新連線先拉取游標之後的訊息，再接即時流；若只靠推播提醒，推播遺失就會漏訊息。已讀狀態可記每個使用者在會話中的最高已讀序號，避免為每則訊息每個成員存一筆。若產品要求每台裝置獨立已讀，則需要裝置層紀錄。

## 小群與大群

小群可以逐個在線裝置推送。若群組有 10 萬成員，每則訊息都寫 10 萬份收件箱會造成寫入放大。可讓訊息只存一份、成員按會話游標拉取，Gateway/推播僅提示有更新。大群還需要控制發言權限、限流、訊息保存期限與高峰廣播流量。

## 連線與 Presence

Presence（在線狀態）可由 Gateway 心跳與短 TTL 紀錄推導，但網路抖動會讓它近似而非絕對準確。Gateway 故障後，連線重建要重新註冊路由、補拉訊息。容量估算要同時算連線數、每連線 buffer/TLS 記憶體、每秒發訊息數、群組 fan-out 與儲存量。只算 QPS 會漏掉長連線成本。

## 安全與觀測

訊息與附件需驗權、大小限制、濫用防護和保留政策。若要求端對端加密，伺服器不應假定能讀明文做全文搜尋；多裝置金鑰同步、備份、成員變更都是另外的設計題。監控在線連線、重連率、server ACK 延遲、送達延遲、同步缺口、重試去重率與單會話熱點。

## 自測

1. 收件者看見訊息後、ACK 前斷線，重連時如何不漏、不重複顯示？
2. 兩台裝置同時向同一會話送訊息，排序以什麼為準？
3. 群組從 10 人增加到 10 萬人時，哪條資料流先需要改？

## 自測參考解答與面試追問

### Server ACK 與已讀回執有何差別？（對照原書第 208–215 頁）

**答：**Server ACK 只表示服務端已把訊息寫到其承諾的持久化層，或至少已接受排隊；這個界線要明說。送達回執表示接收裝置已確認收到，已讀回執表示使用者在產品定義下看過。三者可能相隔很久，也可能有多個接收裝置各自不同狀態。若把「送到 Gateway」誤說成「對方已讀」，網路斷線時就無法解釋使用者看到的狀態。

### 長連線服務壞了，為何訊息仍不能丟？（第 215–223 頁）

**答：**Gateway 只管理目前連線與路由，不應是唯一訊息儲存。發送成功的訊息先進持久化會話日誌，再嘗試推送；Gateway 當機後客戶端重連，帶最後已套用序號補拉。Presence 可因心跳 TTL 短暫不準，但訊息資料仍應完整。容量上要分別估同時連線記憶體、每秒訊息寫入、每個群組的推送扇出，不能以單一 API QPS 代替。

### 1. 收件者看到訊息、ACK 前斷線，重連怎樣不漏也不重複？（對照原書第 203–214 頁）

**答：**伺服器先持久化訊息並給它會話內的 `message_id/sequence`，再推給在線裝置。裝置收到後以 ID 去重、持久化已套用的游標，接著回 ACK；若 ACK 遺失，伺服器可重送同一 ID，客戶端不重複顯示。重連時帶最後**連續**套用的 sequence 拉缺口，不能只帶「看過的最大值」，否則中間漏一則會被跳過。ACK 的含義也要寫清：到達 Gateway、裝置收到或使用者已讀，是三種不同承諾。

### 2. 兩台裝置同時往同一會話送訊息，怎麼排序？（第 210–220 頁）

**答：**不要用裝置本地時間決定權威順序，兩台時鐘可能偏移。訊息先進同一會話的序號分配或單一分區日誌，由伺服器在成功持久化時分配遞增 sequence；客戶端以 `(conversation_id, sequence)` 排序。這只保證**同一會話內**的順序，不代表跨會話全域排序。若序號服務故障，應暫停確認成功或切到可追趕的新主節點，避免同序號對應不同訊息。

### 3. 群組由 10 人變 10 萬人，先改哪條路？（第 220–228 頁）

**答：**若每發一則就寫 10 萬份收件箱，寫入扇出、推播與儲存會先爆。可將群組訊息寫一次到會話日誌，成員用個人游標拉取；在線 Gateway 只推「有新訊息」提示，並對廣播節流。小群仍可用逐人推送以取得低延遲，兩種路徑可按群組大小切換。切換時要確保訊息 ID、歷史讀取與成員權限語意一致，不能讓切換窗口漏訊息。
