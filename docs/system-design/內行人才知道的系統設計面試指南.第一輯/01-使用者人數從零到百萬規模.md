閱讀順序不是「每多一些使用者就加一種技術」的固定配方。每一頁增加元件時，都要回答：它移開了哪個瓶頸、創造了哪個新失敗點、怎麼確認改善真的發生。

## 先定義「規模」

「百萬使用者」可能指註冊帳號、月活、日活或同時在線；它們不能互換。系統負載還取決於每人每天的操作、單次回應大小、讀寫比例、地域和尖峰集中度。假設 100 萬 DAU、每人每天 20 次頁面請求，平均約 `1,000,000 × 20 / 86,400 ≈ 231 QPS`；若同時推播造成 20 倍尖峰，則是約 4,630 QPS。單一熱門貼文可能比全站平均更早形成瓶頸。

設計之前先寫下四類目標：**功能**（能做什麼）、**延遲**（如 p95）、**可用性**（故障時能否服務）、**資料正確性**（成功回應後資料是否保留、多久可見）。沒有這些約束，架構圖很容易只是在堆元件。

### 先把一次請求走完

使用者輸入網域後，瀏覽器先透過 DNS 取得服務入口的 IP，再建立連線、送出 HTTP 請求。小規模時入口可能就是唯一的 Web 主機；加入負載平衡器後，DNS 指向負載平衡器，由它挑選健康的 API 副本。API 可能查資料庫或快取，再回傳 HTML 或 JSON。圖片與程式碼等靜態資源通常由另一個網址載入，之後可改由 CDN 提供。**DNS 解析、請求分配、資料讀取、靜態資源下載是四個不同環節**，每一段都可能有自己的延遲與故障。

Web 和行動 App 可以共用 API，但不能因此假設兩者的請求型態一樣。Web 首次載入可能同時下載 HTML、JS、CSS 與圖片；行動 App 可能頻繁呼叫 JSON API。估容量時應分開統計 API QPS、靜態資源的流量、單次回應大小與尖峰時段。

### 先選資料模型，再選資料庫產品

把應用和資料庫拆到不同主機，是為了讓兩者能分別擴容與排查；**拆主機不等於一定要改用 NoSQL**。選型時先列出主要讀寫操作、資料之間的關係和正確性要求。

| 問題 | 偏向關聯式資料庫的情況 | 需要評估其他資料模型的情況 |
| --- | --- | --- |
| 交易與約束 | 訂單、付款、庫存需要跨資料列的交易與唯一約束 | 寫入可拆成獨立事件，能接受之後再彙整 |
| 查詢形狀 | 常依多個條件查詢、排序，或需要 JOIN | 主要按已知 key 讀寫，或沿圖關係遍歷 |
| 資料結構 | 欄位與關係相對穩定 | 文件欄位差異大、資料模型常變 |
| 擴展方式 | 可先靠索引、讀副本與垂直擴展滿足需求 | 已確認資料量或吞吐量超出單一部署的可行範圍 |

「資料量很大」或「要低延遲」本身不足以決定 SQL/NoSQL；索引、查詢形狀、資料局部性與部署方式也會左右結果。選了 NoSQL，仍要回答資料如何分區、哪些查詢不能跨區高效完成，以及需要什麼一致性。

## 第一步：單機方案與首次量測

```text
Browser → Web/API + Database + 靜態檔（同一台機器）
```

小規模單機的價值是容易部署、備份與追查。它的限制包含單點故障、應用與資料庫爭 CPU/記憶體、磁碟和網路共用，以及擴容需要搬遷。先量測 p95/p99、CPU、記憶體、GC、磁碟 I/O、網路、資料庫慢查詢和連線池。哪一項先到上限，下一步就不同。

遇到系統變慢時，先找出是哪個環節忙不過來，再決定要改哪裡：

| 看到的情況 | 怎麼確認 | 下一步可以做什麼 |
| --- | --- | --- |
| 很多人下載圖片，主機的網路頻寬快用完 | 看圖片等靜態檔占了多少流量，以及使用者集中在哪些地區 | 把圖片放到物件儲存，再用 CDN 從靠近使用者的節點提供，減少每次都向原本的主機下載 |
| 處理請求的 API 主機 CPU 很忙，資料庫卻還有餘力 | 找出是哪個功能或運算最花 CPU | 先改善耗時運算；若請求量仍超過單台主機能處理的量，就把 API 與資料庫分開部署，增加 API 主機分攤請求 |
| 資料庫回應很慢，API 大多在等它 | 找出跑很久的查詢，檢查索引、互相卡住的交易與資料庫連線是否用滿 | 先改善查詢；若重複讀取很多，再考慮快取；若讀取量仍太大，再評估讀副本 |
| 很多人同時搶同一商品或活動名額 | 看同一筆資料是否被大量請求、交易是否互相等待，以及失敗率是否升高 | 用資料庫的條件更新確保名額不會超賣；流量太集中時，讓請求排隊，或依商品／活動分組處理 |
| 唯一一台主機壞掉，整個服務就停了 | 確認備份能否還原、系統能否發現主機故障，以及其他主機是否也會受同一故障影響 | 準備多台能接手的 API 主機，並規劃資料庫故障時如何切換與恢復 |

## 第二步：把無狀態應用橫向擴充

```text
Browser → DNS → Load Balancer → API A / API B / API C → Database
```

這裡的**副本**是指執行同一套 API 程式、都能處理請求的另一個程序或伺服器實例，不是某個檔案的備份。負載平衡器會定期向每個副本發送健康檢查請求（例如 `GET /health`）；若某個副本連續無法正常回應，就暫時不把新請求分配給它。部署時也需先停止讓舊副本接新流量、等既有請求完成，再關閉程序。

例如活動報名服務有 API A 和 API B 兩個副本，平時負載平衡器把報名請求分給兩者。若 A 的程序當機，健康檢查失敗，負載平衡器便把後續新請求交給仍健康的 B；A 修好並通過健康檢查後，才重新接收流量。這只能讓 API 層繼續服務：若兩者共用的資料庫也故障，單靠 B 無法完成報名。

API「無狀態」指處理下一次請求所需的資料，不只存在某一台 API 自己的記憶體裡；因此任何副本都能處理使用者的請求。例如登入後，第一次請求由 API A 處理，下一次分給 API B，B 仍可根據請求帶來的憑證取得使用者資料並完成處理。如果登入資訊只存在 A 的記憶體，B 就無法辨識使用者，也就難以直接增加副本分攤流量。

無狀態不代表系統沒有狀態。使用者 Session、上傳進度、排程工作仍然是狀態，只是要放在明確的外部儲存或以可驗證憑證承載。黏性 Session 可能是過渡手段，但副本故障仍會讓使用者失去狀態。

API 副本增加時要檢查**下游總連線數**。例如每台 100 個 DB 連線，從 2 台變 20 台便可能達 2,000 個連線，先把資料庫耗盡。連線池、逾時、熔斷與重試上限須一起配置。

## 第三步：讓讀取離資料與使用者更近

**CDN** 服務可公開快取的圖片、JS、CSS 或適合快取的內容。要先定義 TTL、版本化檔名、主動清除，以及使用者權限變更時舊內容可留多久。私有資料不能只因 URL 很難猜就直接放公共快取。

第一次請求某張圖片時，邊緣節點可能沒有副本（miss），會向來源站或物件儲存取回、快取並回傳；後續相同資源可直接在邊緣節點命中。來源站修改圖片後，邊緣節點不一定立即知道。對會改內容的 URL，可用短 TTL 或主動失效；對以內容雜湊命名的靜態檔，可使用較長 TTL，更新時換網址。設計時再檢查回源頻寬、CDN 費用，以及 CDN 故障時是否有可承受負載的備援路徑。

**應用快取**可用 cache-aside：先查快取，miss 才查 DB，之後回填。只快取重複讀取且可容忍短暫舊值的資料。資料更新後刪快取與 TTL 都有競爭窗口；熱門 key 同時失效可能讓回源量暴增，需考慮請求合併、錯峰 TTL、熱 key 分散。詳見[Redis 與 Cache 入門](/docs/system-design/redis-cache-react-python)。

快取空間滿了，又要放入新資料時，才需要決定**先移除哪筆舊資料**。**LRU（Least Recently Used，最久沒使用）**移除「距離上次使用最久」的項目；**LFU（Least Frequently Used，使用次數最少）**移除「使用次數較少」的項目。兩者都可能留下熱門資料，但 LRU 看的是**最近有沒有用**，LFU 看的是**用了多少次**；**FIFO**則只看放入順序。

例如快取只能放兩筆，目前有 A、B：A 先被讀了 10 次，接著 B 被讀了 1 次。現在要放入 C，**LRU 會移除 A**，因為 B 比 A 更晚被使用；**LFU 會移除 B**，因為 B 只被使用 1 次。也就是說，LRU 不保證留下累計使用次數最多的資料。

沒有一種策略對所有流量最好：短期突發可能讓 LRU 擠掉穩定熱資料；LFU 若缺少時間衰退，舊熱點可能長期占位。除了命中率，也要看 miss 時的資料庫負載與熱 key 分布。快取服務本身失效時，回源量可能形成第二次故障，需限流或降級。

**讀副本**分攤可接受複寫落後的查詢，不能提高主庫寫入能力。若使用者剛更新個人資料便立即查詢，要讀主庫、在短時間內做會話黏附，或明確接受短暫舊值。

讀副本也不是自動備份。正常寫入通常先進主庫，再複寫到副本；副本落後時，使用者可能讀到舊資料。副本故障可暫時把讀取導向其他副本或主庫，但要確認主庫能承受額外讀取。主庫故障則要選出新主庫、阻止舊主庫繼續接收寫入，並確認先前已回覆成功的寫入是否都存在。副本會同步誤刪與錯誤更新，因此還需要可還原的備份與復原演練。

| 故障 | 使用者可能看到什麼 | 切換時要確認什麼 |
| --- | --- | --- |
| 一台讀副本離線 | 查詢變慢或短暫失敗 | 健康檢查移除副本；剩餘副本及主庫的讀取容量 |
| 主庫離線 | 更新、報名等寫入失敗或結果不明 | 新主庫的資料進度、唯一寫入者、應用連線重建 |
| 複寫落後 | 剛更新的內容又變回舊值 | 哪些操作需要讀自己的寫入；落後量是否超過承諾 |

## 第四步：拆解寫入與背景工作

發送通知、生成縮圖、轉碼和報表不必卡在請求的同步路徑。可以先在權威資料庫保存業務結果與待處理事件，再由佇列和 Worker 非同步處理。Worker 應可重試、去重並有死信與積壓監控。若用戶看到「上傳成功」，要說清楚是原檔已持久化，還是所有後處理已完成。

例如上傳頭像：API 收到圖片後，先保存原檔與工作紀錄，回覆「已收到」；Worker 從佇列領取縮圖工作，完成後更新狀態。若 Worker 失敗，佇列可以重新交付；因此縮圖輸出要能以同一工作 ID 重複執行而不產生多份錯誤結果。**佇列吸收尖峰，不會讓工作憑空消失或保證立即完成**；應監控最老工作的等待時間、重試次數和死信量。佇列的持久性也取決於實際產品與設定，不能因為畫了佇列就假設訊息永不遺失。

當單一資料庫的寫入或容量接近極限，才考慮分片。選分片鍵須同時檢查分布、常見查詢與資料搬移：`user_id` 可能適合使用者資料，卻未必適合「按活動查所有報名」；跨片交易和查詢會更難。以一致性雜湊分配節點能減少重映射，但不會自動完成資料搬遷。

最簡單的示意是 `shard = user_id % 4`：同一使用者的資料會落在固定分片，按使用者 ID 查詢可直接路由。但從 4 片增加到 5 片時，多數 ID 的餘數會改變，舊資料不會自己移動；讀寫兩端若使用不同版本的路由規則，甚至會查不到資料。實際遷移需有新舊映射、資料回填、增量同步、校驗、切換與回退計畫。若某位熱門使用者的請求量遠高於其他人，即使資料筆數分布均勻，他所在的分片仍可能成為熱點。跨分片 JOIN 和交易也會增加延遲與協調成本；在分片前要確認索引、查詢改善、讀副本或升級單機已不足以解決瓶頸。

## 第五步：跨區與高可用

跨區部署可降低遠端讀取延遲和單區故障影響，但寫入路由、複寫延遲、衝突與資料主權會增加複雜度。先定義 RTO（恢復時間）和 RPO（最多可接受遺失的已確認資料），再決定單主、多主或其他策略。備份要做恢復演練；有副本不代表能從誤刪或程式錯誤恢復。

如果 GeoDNS 把 A 地區流量導向資料中心 A，A 故障後要轉到 B，除了調整 DNS/入口路由，還要確認 B **有容量、讀得到所需資料、使用同版程式與設定**。DNS 快取讓流量轉移不是瞬時；已在 A 的長連線也不會因改 DNS 自動搬到 B。跨區切換演練應分別量測入口轉移、資料追上與服務真正恢復的時間。

## 一個完整例子：活動報名服務

活動詳情可放 CDN/快取，報名狀態與剩餘名額由權威資料庫決定。報名交易可使用「名額尚有餘額才扣減」的條件更新，並對 `(event_id, user_id)` 設唯一約束。若最後一個名額同時有千人搶，快取顯示的剩餘數只能當提示，成功與否要以交易結果為準。通知從 outbox 非同步送出；通知延遲不應改變已完成的報名結果。

## 故障推演與觀測

- API 副本故障：健康檢查多久移除？進行中的請求若重試，會不會重複報名？
- 快取叢集故障：所有讀取回源時，DB 能承受嗎？是否需要降級或回源限流？
- DB 主節點切換：剛回成功的寫入是否會遺失？客戶端如何查到最終結果？
- 單區故障：流量轉移後，另一區的容量、資料版本與成本如何變化？

至少監控流量、錯誤率、p95/p99、DB 連線與鎖等待、快取命中率、佇列積壓、複寫落後、CDN 回源和每請求成本。每次擴容後再壓測與演練，驗證瓶頸是否真的移開。

日誌用於重建單次請求經過哪些服務；基礎設施指標觀察 CPU、記憶體、磁碟與網路；業務指標觀察報名成功率、留存或其他產品結果。它們應可用 request ID 或操作 ID 關聯。部署自動化則讓多資料中心保持一致，降低手動逐台更新造成的版本漂移。

分片後還要留意三種成本：資料成長時重新分片要搬移資料並處理新舊路由共存；名人或熱門商品可能讓單片過熱，即使總資料均勻；原本單庫可做的 JOIN 或交易跨片後變貴。選 `user_id` 作分片鍵前，列出最常見的五個查詢，逐一確認是否能由 user ID 路由，否則要設計索引、彙總表或服務邊界。

## 自測

1. 100 萬 DAU 與 100 萬同時在線有何不同？為兩者各選三個最重要的容量指標。
2. 將 API 從 2 台擴到 20 台後反而變慢，列出三個可能原因與驗證方式。
3. 讀副本延遲 5 秒時，哪些頁面可接受？報名成功頁如何保證「寫後讀」？

## 自測參考解答與面試追問

### 先問：流量成長時，哪一層應先擴？（對照原書第 1–10 頁）

**答：**先觀察瓶頸，不能照「單機 → Redis → CDN → 分片」的固定順序。若 API CPU 滿、資料庫仍空閒，先讓 API 無狀態並增加副本；若慢 SQL 占主要延遲，先修索引與查詢；若熱門圖片佔出口頻寬，才考慮 CDN。每次更動都要對照 p95、錯誤率、飽和度與成本，確認瓶頸真的移走，並找新瓶頸在哪。

### 再問：快取與 CDN 要設什麼失效承諾？（第 11–16 頁）

**答：**先把資料分成可短暫過期的公開內容，以及權限、價格、庫存等需要較新值的內容。快取 key 應含資料版本或租戶/權限範圍，TTL 只是一種上界近似；更新時可寫穿、主動失效或換版本 key。若 CDN 在來源站故障時仍回舊內容，必須知道使用者能接受多舊。快取故障還需回源限流，否則全量 miss 會壓垮資料庫。

### 最後問：跨區故障切換為何不能只改 DNS？（第 20–26 頁）

**答：**另一區要有足夠預留容量、相容版本、可用的權威資料和背景任務狀態。DNS TTL 及客戶端快取使切流不會瞬間完成；複寫若落後，成功寫入的資料可能在新區看不到。要先定義可容忍的 RPO/RTO，演練主區不可用時由誰升主、如何防止雙主、怎麼驗證復原後資料一致。只畫 GeoDNS 箭頭，仍沒有回答資料與寫入權威問題。

### 1. 100 萬 DAU 與 100 萬同時在線有何不同？（對照原書第 1–6 頁）

**答：**DAU 是一天內不重複的活躍人數，並未說明請求是否集中。假設 100 萬 DAU 每人每天 20 次操作，平均只有約 231 QPS；若 100 萬人同時在線，每人每 30 秒發一次請求，光這項就約 33,333 QPS，還沒算長連線記憶體。前者先估每人操作數、尖峰倍數、單次資料量；後者先估連線數、每連線資源、同時請求與廣播流量。兩者的儲存容量可能相近，連線與瞬時負載卻差很多。

### 2. API 從 2 台擴到 20 台後反而變慢，怎麼查？（第 6–10、27–30 頁）

**答：**先比較擴容前後的請求鏈路耗時，而非再加主機。可能是 20 台各開 100 條 DB 連線，使資料庫同時承受 2,000 條連線；也可能是共用快取熱 key、負載平衡健康檢查或 Session 黏著不均。分別看 DB CPU/鎖等待/連線池、快取每 key QPS、每台 API 的流量和 p95；用壓測控制變因，找出真正飽和的共享資源。若瓶頸在資料庫，API 擴容反而會更快把它壓垮。

### 3. 讀副本落後 5 秒，報名成功頁怎麼保證寫後讀？（第 7–10 頁）

**答：**公開活動資訊或非關鍵統計可能容忍 5 秒舊值；「我已報名」不能在成功後又顯示未報名。寫入交易提交後，成功回應可帶 `registration_id` 和已確認的狀態；接下來一段時間把該使用者的查詢導向主庫，或等待副本追到該寫入的 log position 再讀。若切主庫期間結果不明，客戶端用同一操作 ID 查詢，不能直接重試新增另一筆報名。寫後讀的保證應明確限定在需要它的操作，而非強迫所有讀取走主庫。
