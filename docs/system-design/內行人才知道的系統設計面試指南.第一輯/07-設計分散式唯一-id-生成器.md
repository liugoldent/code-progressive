原書範例將 10 位節點識別再拆為 **5 位資料中心 ID + 5 位機器 ID**，因此單一資料中心欄位最多 32 個值，每個資料中心的機器欄位最多 32 個值。下面合併寫成 10 位節點 ID，是同樣的總位元預算；若改變拆法，必須重新計算部署上限。

## 先問四個不等價的要求

**唯一性**指某範圍內不重複；**排序性**指能否大致按時間排序；**不可預測性**關係到是否會被枚舉；**可用性**指中心服務故障時能否繼續發號。ID 也要問長度、整數/字串形式、生成速率、是否跨區、要用多久。沒有一個做法同時在所有面向最好。

| 方法 | 優點 | 代價 |
| --- | --- | --- |
| 資料庫自增 | 簡單、單表有序 | 中心依賴、跨片整合、可枚舉 |
| UUID v4 | 可分散產生、碰撞機率極低 | 長、無時間排序、索引局部性較差 |
| 時間＋節點＋序號 | 多節點本地生成、大致有序 | 時鐘回撥、節點 ID 租約、序號耗盡 |
| 預分配 ID 區段 | 中央低頻配置、節點本地發號 | 區段浪費、租約重疊、全域排序不保證 |

## 時間型 ID 的位元預算

示例為 64 位整數：`1 位保留 + 41 位毫秒時間 + 10 位節點 ID + 12 位同毫秒序號`。12 位序號最多 `2^12=4,096` 個值/節點/毫秒；10 位節點 ID 最多 `2^10=1,024` 個同時身份。41 位毫秒從選定 epoch 起約可用 69 年。這些是理論上限，實際還要考慮儲存型別、語言整數精度、資料庫索引與生成器實際吞吐。

```text
| reserve | timestamp since epoch | node ID | per-ms sequence |
```

它只保證在設計前提成立時不碰撞：同一時段 node ID 不重複、時鐘不倒退到已使用的時間、序號不溢位。先說前提，再談特性。

## 三個必須處理的故障

### 時鐘倒退

系統時鐘可能因 NTP 調整、虛擬機遷移或管理操作回撥。若目前毫秒小於上次發號毫秒，不能直接重置序號。策略包含等待時鐘追上、持久化上次時間並使用邏輯時間、拒絕發號並報警；等待影響可用性，邏輯時間需處理重啟持久化，拒絕則影響請求成功率。

### 節點身份重複

容器重啟、租約過期或配置錯誤可能讓兩台機器同時使用同一 node ID。可使用具互斥租約的協調服務、持久化配置或運維分配；租約到期時生成器應停止，不能繼續假裝自己有唯一身份。跨區若各區配置獨立 ID 範圍，也要預防錯誤部署。

### 單毫秒序號用盡

超過 4,096 個值時，要等待下一毫秒或回傳受控錯誤；從 0 重來會碰撞。壓測要看 burst，而不是只看秒平均。若單節點尖峰遠高於該上限，需調整位元配置、增加節點或改算法。

## 對外 ID 與內部主鍵分離

按時間遞增 ID 可能洩露新增量與時間，也容易被掃描。權限驗證不能依賴 ID 難猜；若要對外不可預測，可另給一個隨機 public ID，內部仍用有序 ID 作索引與追蹤。兩種 ID 的映射也需要唯一索引與更新規則。

## 實作與驗證清單

每個生成器實例應記錄最後 timestamp、node ID、序號耗盡次數與時鐘回撥次數。驗證要包含多節點同時發號、快速重啟、租約交接、時間回撥、未來時鐘、同毫秒高峰和資料庫型別溢位。只跑單機一百萬次無碰撞，不能證明分散式情境正確。

## 自測參考解答與面試追問

### 1. 64 位怎樣配置，能用多久、每節點多快？（對照原書第 121–128 頁）

**答：**可留 1 個符號位，用 41 位毫秒時間、5 位資料中心、5 位機器、12 位同毫秒序號，合計 64 位。時間欄從自訂 epoch 起約可用 `2^41 ms ≈ 69.7 年`；每資料中心最多 32 個機器編號，共 1,024 個組合；單機每毫秒最多 4,096 個 ID，理論均勻負載約每秒 409.6 萬個。這是位元上限，不是實際吞吐保證；時鐘、持久化和下游寫入仍可能更早成瓶頸。

### 2. 兩台機器同拿 node ID 7，怎麼防？（第 125–129 頁）

**答：**啟動時從有唯一約束的註冊服務取得帶租約的 ID，確認租約尚未被其他實例持有，才能開始發號；網路分區時應停止已失去租約者的發號能力，不能讓兩個實例都自認持有 7。若機器時鐘和序號也恰好相同，會直接產生重複 ID。事後可用資料庫唯一索引、衝突指標發現，但那只能攔住寫入或告警，無法挽回已對外發出的重複識別碼。因此啟動和租約交接是主要防線。

### 3. 連續自增訂單號對外顯示有什麼問題？（第 121–130 頁）

**答：**它可能洩漏訂單總量與建立順序，也讓攻擊者容易枚舉別人的訂單 URL。使用隨機 public ID 可降低猜測與商業資訊外洩；內部仍可用較有序的主鍵改善索引局部性。但「難猜」不是授權，查詢任何訂單都必須驗使用者是否有權限。對外 ID 還要有唯一約束、長度與錯誤處理策略。
