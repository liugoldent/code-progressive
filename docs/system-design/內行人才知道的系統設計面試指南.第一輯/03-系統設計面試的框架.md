書中以約 45 分鐘面試為例，第一步約 3–10 分鐘、第二步約 10–15 分鐘、第三步約 10–25 分鐘、第四步約 3–5 分鐘。下面的時間表是本站為練習設的較窄目標；若面試官引導深入，應調整節奏。

## 面試考的是決策過程

系統設計題通常沒有唯一正解。面試官要看你能否從模糊需求找出關鍵約束，建立可工作的方案，並在規模或故障條件變化時調整。把所有熟悉的技術畫上白板不會自動加分；每個元件都應對應具體問題和代價。

## 四段式流程

| 階段 | 建議時間（45 分鐘題） | 要留下的成果 |
| --- | --- | --- |
| 1. 理解問題與範圍 | 5–8 分鐘 | 核心功能、排除項、規模與品質目標 |
| 2. 提出高階方案 | 10–15 分鐘 | API、資料模型、讀寫路徑與系統邊界 |
| 3. 深入一至兩個難點 | 15–20 分鐘 | 替代方案、取捨、故障行為 |
| 4. 回顧與驗證 | 3–5 分鐘 | 容量、可用性、觀測與未決風險 |

時間只是節奏參考；面試官若已給定某些需求，可直接往下。講完高階圖後先確認「你想深入哪個部分」，避免在次要功能耗盡時間。

## 第一段：釐清需求

以「設計短網址」為例，不要立刻說 Base62。先問：短碼是否自訂？同一長網址要同一短碼嗎？是否過期？跳轉目的地可修改嗎？要即時點擊統計嗎？建立是否匿名？讀寫比例和延遲要求？這些問題會改變產碼、索引、快取與 301/302 選擇。

功能需求與非功能需求分開寫：

- **功能**：建立短網址、跳轉、過期、統計、管理者封鎖。
- **規模**：DAU、每日新增、日跳轉、熱門碼長尾、地區分布。
- **品質**：跳轉 p95、可用性、統計可延遲多久、封鎖生效時間。
- **邊界**：濫用防護、權限、成本、個資保留。

問不完所有問題時，選最會改變方案的問題；其餘寫明假設並往下走。例如「假設目的地不可修改，統計可延遲一分鐘」。這比把假設藏在架構裡好。

## 第二段：一張能跑通的高階圖

先畫最短的成功路徑：請求從哪進來、權威資料在哪、何時回應。再畫讀取路徑和背景工作。對短網址：`POST /links` 寫 `code → URL`，`GET /{code}` 查映射並跳轉，點擊事件非同步送分析管線。資料模型可先寫 `Link(code, url, owner, expires_at, status)`。

標註哪些資料可快取、哪些需要交易、哪些故障可以延後。若只說「用 Redis、Kafka、Cassandra」，面試官仍不知道它們各處在何處，以及為何需要。

## 第三段：抓住最難的約束深入

| 題目 | 最值得深入的候選點 |
| --- | --- |
| 限速器 | 原子性、分散式配額、超限回應 |
| 短網址 | 唯一碼、碰撞、熱點讀取、濫用 |
| 動態訊息 | 名人 fan-out、首頁新鮮度、刪文/權限 |
| 聊天 | 單會話順序、離線補發、重試去重 |
| 影音 | 分段上傳、轉碼重試、CDN 成本 |
| 雲端硬碟 | 檔案版本、多裝置衝突、刪除同步 |

每個深入點可用同一個句型：**方案 A 怎麼運作 → 何時失效 → 方案 B 解哪個問題 → 新增什麼成本 → 根據本題約束選哪個。** 例如名人的 feed 不適合對 5,000 萬粉絲同步寫入，故可將名人貼文留給讀時合併；代價是首頁讀取更重。

## 第四段：用失敗路徑驗證設計

在架構圖每條箭頭上問：「這一步成功後、下一步之前當機，會發生什麼？」可能出現雙寫不一致、重複通知、遺失訊息、孤兒區塊。回答要涵蓋重試、冪等、版本、超時、死信、回滾或人工補償。不要以「Kafka 保證 exactly once」一句話跳過端到端副作用。

收尾可回顧：目前方案滿足哪些明確要求；容量假設若十倍會先撞哪裡；還有哪些未解問題；要看哪些指標證明設計有效。讓面試官知道你有意識地取捨，而不是沒想到。

## 自測

1. 用 3 分鐘向別人說明「設計聊天系統」的前三個需求問題，並解釋每題會改變哪個設計。
2. 為短網址畫最小可行方案，不使用超過四個主要元件；再選一個瓶頸擴充。
3. 對「通知已送供應商但尚未記錄成功就當機」畫故障時間線，說出無法保證的部分。

## 自測參考解答與面試追問

### 1. 聊天題前三個需求問題怎麼問？（對照原書第 43–47 頁）

**答：**第一問「一對一、群組，還是兩者都要？」因為 10 人小群和 10 萬人頻道的扇出方式不同。第二問「訊息要在單一會話內有序，還是要求跨會話全域順序？」後者成本高且通常不必要。第三問「離線多久必須能補收，已讀/送達回執要到哪一層？」這決定訊息持久化、同步游標與 ACK 語意。每問都應連到一個實際會改變的元件或資料模型。

### 2. 短網址的最小方案怎麼畫？何時才擴充？（第 48–51 頁）

**答：**先用 `Client → API → Database`，資料庫對短碼設唯一索引；建立時選碼並插入，跳轉時查碼再回 HTTP redirect。這已能展示完整成功路徑。若讀取 QPS 遠高於寫入且資料庫讀取飽和，才加快取；若某個短碼特別熱門，需檢查單 key 熱點與快取失效。面試官要看的是每增加一層帶來的收益與新風險，不是第一張圖的元件數量。

### 3. 通知已送供應商、未記錄成功就當機，能保證什麼？（第 51–54 頁）

**答：**重啟後本地狀態仍像「未送」，但供應商可能已接受。盲目重送會重複；不重送可能漏發。若供應商支援 idempotency key 或可查詢 provider message ID，先以固定事件 ID 查證；否則只能明說這是未知狀態，依通知類型選擇重送、人工處理或容忍遺漏。這個故障點應在設計圖旁標出，而不是宣稱 queue 自動帶來 exactly-once。
