**複雜度要連同前提說明。** 在節點已保存 Top K 且 prefix 長度有上限時，可把熱門查詢近似視為常數量級；若要現場遍歷整個子樹、做個人化 ACL 過濾或拼字容錯，不能照搬這個說法。資料收集與快照切換也有不同的新鮮度要求。

## 先界定候選集合

補全可以來自熱門查詢詞、商品名、文章標題、個人歷史或多來源混合。先問是否只做字首匹配、要不要容錯字、語言/地區分開嗎、熱門詞多久更新、個人化與敏感詞如何處理。中文輸入法有組字階段；若每次按鍵都呼叫 API，可能產生無意義且大量的請求。

示例目標：輸入兩個以上字元後，p95 在 100 ms 內返回最多 10 個候選；公共熱門詞可延遲 5 分鐘更新，私人歷史即時但只能本人看到。這些是示意 SLA，不是通用標準。

## 查詢路徑

```text
前端輸入 → debounce → Suggest API → prefix cache / 索引 → 候選合併
       → 權限與敏感詞過濾 → 排序 → Top K → 回應
```

前端要取消或忽略過期請求。用戶依序輸入 `ca`、`cat`，`ca` 的回應若晚到，不能覆蓋 `cat` 的結果；可附 request sequence 或檢查目前輸入值。debounce 可降 QPS，但太長會讓建議變慢，應以實測打字節奏調整。

## Trie 與其他索引

Trie 每個邊是一個字元，走到 prefix 節點後可找其後代詞。若每個節點保存 Top K，查詢快，但更新一個詞可能影響它所有 prefix 節點，而且熱門詞、語言和排序版本會增加記憶體。另一選擇是使用具 prefix 能力的搜尋引擎或排序索引；若來源是大量商品名而且頻繁增刪，專用搜尋系統可能比自己維護巨大 Trie 更合適。

### 用三個詞看懂節點 Top K

假設熱門詞有 `cat=100`、`car=80`、`camera=50`。`ca` 節點若保留 Top 2，內容為 `[cat, car]`；`cam` 節點則為 `[camera]`。查 `ca` 只需走兩個字元並讀候選，不必每次掃遍整棵子樹。若 `camera` 熱度升到 120，更新不只改詞尾，還可能影響 `c`、`ca`、`cam` 等祖先節點。這就是預計算讀取快、更新較貴的原因。

可把事件先依 1 分鐘與 1 小時窗口彙總，定期建立新 Trie 快照，再原子切換索引版本。切換時 API 的一次請求應固定讀同一版本，避免前半段看舊索引、後半段看新索引。新版本的快取 key 帶上版本號，舊快取自然過期；若所有 prefix 同時失效，可能出現重建後的快取冷啟動尖峰，可先預熱熱門 prefix。

| 方案 | 適用 | 代價 |
| --- | --- | --- |
| 預計算 prefix → Top K | 公共熱門詞，更新可延後 | 重建與儲存空間 |
| Trie 動態維護 | 前綴匹配簡單、更新量可控 | 節點/更新成本 |
| 搜尋引擎 prefix 索引 | 多欄位、篩選與語言分析 | 集群成本和索引延遲 |
| 個人歷史本地或私有索引 | 每人資料量小、隱私要求高 | 跨裝置同步與權限 |

## 排序不能只看總次數

候選分數可綜合長期頻率、近期熱度、語言/地區、拼字品質與個人偏好。純總次數會讓舊熱門詞長期壟斷；純近期計數容易被機器刷榜。可在不同時間窗計數，對可疑流量過濾與限權重。離線批次重建適合分鐘級更新；秒級熱點可另設串流計數補丁，但要有合併規則與衰退策略。

## 快取與權限

公共 prefix 可按 `(normalized_prefix, locale, index_version)` 快取；個人化結果不能放進同一公共 key。若候選含私有文件標題，索引找到候選後必須依請求者 ACL 再過濾，否則即使無法點開文件，光標題也可能洩漏資訊。敏感詞過濾也要在返回前執行，並考慮索引更新後快取仍有舊候選。

## 更新流程與觀測

```text
搜尋事件 → 去機器/清洗 → 時間窗彙總 → 建立索引版本
                                   → 驗證 → 切換新版本 → 回收舊版本
```

新索引應先驗證候選數、敏感詞、語言分布與延遲，再切換；切換失敗可回舊版本。監控 p95 延遲、空結果率、建議採用率、索引落後、快取命中、錯誤排序和敏感候選漏出。採用率低可能是候選品質差，也可能是 UI 位置或使用者任務不同，不能只憑一個指標判定。

## 估算與自測

假設 100 萬同時在線，每人每分鐘開始 2 次搜尋，每次輸入平均 5 個字，若每個字都查，理論輸入事件約 `1,000,000 × 2 × 5 / 60 ≈ 166,667/s`。debounce 和最短 prefix 長度會改變實際 API QPS，應量測而不是直接用理論值部署。

## 自測參考解答與面試追問

### 1. 熱詞 10 秒內更新，與 10 分鐘更新差在哪？（對照原書第 229–243 頁）

**答：**10 分鐘可將搜尋事件批次彙總、離線重建 Trie/Top K，再整批切換索引版本；查詢路徑簡單、快照穩定。10 秒則需串流計數和頻繁的增量更新，還要處理事件晚到、重複、刷榜與多副本同步；每個 prefix 的 Top K 更新成本會顯著提高。可用穩定的批次基底加短期熱門補丁，在查詢時合併候選，但需定義衝突和過期方式。沒有明確新鮮度需求時，不應一開始就付即時更新的成本。

### 2. 公共熱門詞與個人歷史怎樣合併才不洩漏？（第 240–249 頁）

**答：**公共候選用 `(normalized_prefix, locale, index_version)` 快取；個人歷史從使用者私有儲存查詢，key 至少要包含經驗證的 user ID，或直接不放共用快取。合併前先做 ACL/敏感詞過濾，再排序取 Top K；私人文件標題不能先進公共 Trie 再祈望前端隱藏。日誌也應避免記錄完整個人查詢或文件標題。登出、權限撤銷時清除客戶端私有建議，並定義伺服器快取生效窗口。

### 3. `ca` 比 `cat` 晚回，前端怎麼處理？（第 244–249 頁）

**答：**每次輸入遞增 request sequence，回應只在 sequence 等於目前輸入狀態時套用；也可取消舊請求，但取消不能保證網路回應不會已在路上。伺服器可照常快取兩個 prefix 的公共結果，過期回應的判斷應在 UI 層完成。中文輸入法組字期間可暫不查詢，配合 debounce 和最短字數減少無效 QPS。這是正確性與負載控制一起處理的例子。
