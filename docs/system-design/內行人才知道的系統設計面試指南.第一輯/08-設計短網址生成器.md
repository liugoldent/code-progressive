`62^7` 是所有七位 Base62 字串的理論空間，不等於可以直接承諾永遠不碰撞或不被枚舉。Hash 截斷方案要處理碰撞；順序 ID 編碼方案要處理唯一 ID 來源與外部可預測性。

## 需求與規模先界定

核心是建立 `long_url → short_code`，再由短碼快速查目的地並跳轉。先問是否允許自訂碼、過期、修改目標、刪除、登入、點擊分析，以及「相同長網址」是否應回同一短碼。若要支援修改目標，快取與永久重新導向都要重新考慮。

假設每天建立 100 萬筆、每筆平均被點 20 次，平均建立約 12 QPS、跳轉約 231 QPS；熱門短碼可能單獨承受很大比例，仍要估尖峰。若每筆映射含索引約 500 bytes，原始資料每天約 500 MB；實際還有索引、副本、分析事件與備份。

## API 與資料模型

```text
POST /links {long_url, custom_code?, expires_at?}
→ {code, short_url, created_at}

GET /{code} → HTTP redirect
```

`Link(code, destination_url, owner_id, created_at, expires_at, status)` 中 `code` 必須有唯一索引。若建立可能重試，接受 idempotency key，讓「資料已寫成功但回應遺失」的重試回到同一結果。自訂碼需保留系統路徑、檢查大小寫、Unicode、長度與不當詞。

## 短碼生成方案

**唯一 ID 編 Base62**：先拿全域唯一 ID，轉成 0–9、a–z、A–Z 字元。7 碼理論組合 `62^7 ≈ 3.52 兆`，但連續 ID 可被枚舉；如果不想暴露順序，還要做可逆置換或另產生 public code。**隨機碼**：用安全亂數產碼，寫入唯一索引；撞碼就重試。碼越短、使用越久，碰撞機率和重試成本越高。資料庫唯一約束是最終防線，不能只靠「機率低」。

Hash 長網址再截斷也可用，但相同網址、參數與不同用戶的去重語意須先定義；截斷仍會碰撞，而且「同網址但不同有效期/追蹤設定」可能需要不同短碼。

## 建立與跳轉路徑

```text
建立：驗證 URL → 限流/濫用檢查 → 產碼 → 唯一約束寫入 → 回傳
跳轉：接收 code → 查 cache → miss 查權威 DB → 查狀態/過期 → Redirect
                                                      └→ 非同步點擊事件
```

熱門短碼可快取，但目的地修改、過期或封鎖時必須讓快取在要求時間內失效。負面快取可保護不存在的短碼大量查詢，但若剛建立同碼，短 TTL 或主動失效要避免暫時 404。跳轉失敗時區分 404 不存在、410 已過期/移除、429 超限與服務故障，產品語意要一致。

## 301、302、307 如何選

`301` 是永久搬移，瀏覽器可能長時間快取；適合目的地確定不變且不要求每次跳轉都打統計。`302` 常用於可變更目標與點擊統計；`307` 明確保留原請求方法。對以 GET 為主的短網址，最重要的取捨是**未來能否修改或封鎖，以及快取多久生效**。不要只背狀態碼名稱。

## 統計與濫用

點擊事件可帶 `event_id, code, timestamp, coarse_region, referrer`，送佇列後彙總；跳轉主路徑不應同步等分析資料庫。是否精確計數、是否收 IP、保留多久，都需依產品與隱私要求決定。對惡意網站要有目的地檢查、建立配額、檢舉與封鎖流程；短碼不是安全或權限保證，私密目的地仍須目標站授權。

## 故障與自測

- 建立成功但回應遺失：同一 idempotency key 的重試回既有 code。
- 快取命中封鎖前的舊目標：封鎖生效 SLA 需要主動清除或短 TTL。
- 點擊佇列滿：跳轉要保留還是拒絕？若分析可近似，可降級統計。
- 熱門短碼突然爆量：看單 key、單分片與 CDN 邊緣負載，不能只看全站 QPS。

**練習：** 每天 100 萬新碼、保留 5 年，估碼長、映射容量和熱門碼快取；再把「可修改目的地」加入需求，重做快取與重新導向設計。

## 練習參考解答與面試追問

### 1. 每天 100 萬新碼、保留五年，要幾個字元？（對照原書第 131–138 頁）

**答：**需求約 `1,000,000 × 365 × 5 = 18.25 億` 個不同碼。Base62 的 5 位約有 9.16 億種，不夠；6 位約有 568 億種，容量上足夠，但要預留保留字、封鎖碼與成長空間。若只存 150 B 映射，主資料約 274 GB；索引、複本、分析事件、備份與未滿頁空間要另算。Base62 長度足夠不代表一定要用遞增編號：亂數碰撞重試、可預測性、建立吞吐也要比較。

### 2. 同一長網址被建立兩次，應回相同短碼嗎？（第 135–141 頁）

**答：**先問產品語意。若每個使用者可為同一目的地建立不同活動碼，應產生不同短碼，並用 `owner_id + idempotency_key` 讓**同一次建立請求**重試得到相同結果。若產品承諾相同正規化網址永遠同碼，則要定義 URL 正規化、所有權、到期日與可修改目的地如何共存；單純對長網址做 hash 會遇到碰撞，也無法自然支援一個網址多個分析活動。先說清楚唯一性的對象，再選產碼演算法。

### 3. 目的地可修改或封鎖，跳轉快取怎麼辦？（第 140–144 頁）

**答：**不要長期使用可能被瀏覽器永久快取的 `301`；可回 `302` 並設定較短的快取 TTL。修改目的地時更新權威映射的 version，再失效或版本化快取；封鎖惡意碼則應走快速撤銷通道，並定義最長生效窗口。若多地 CDN 已快取 redirect，也要考慮清除傳播時間。點擊統計放非同步路徑，不能為了等待分析寫入拖慢跳轉。
