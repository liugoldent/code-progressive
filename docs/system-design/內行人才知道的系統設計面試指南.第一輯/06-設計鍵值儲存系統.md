### CAP 在這題的精確問法

書中以 CP/AP 分類幫助建立直覺。面試時應更精確地問：**當必要副本互相無法通訊時，這個操作要拒絕/等待，還是接受可能暫時分歧的讀寫？** CAP 的 C 指線性一致性語意，A 指每個非故障節點都能回應請求；平常沒有分割時，不是固定從 C、A、P 中任選兩項。不同操作甚至可採不同門檻與故障策略。`R+W>N` 也只有在固定副本集合、正確版本處理等前提下才有交集意義，不能單靠公式宣稱線性一致。

## 先給 `put` 和 `get` 一個明確語意

介面可從 `put(key, value)`、`get(key)` 開始，但必須說明：`put` 回成功是本機記憶體收到、寫進 WAL、還是多個副本已持久化？`get` 是否允許讀到舊值？多個客戶端並發寫同一 key，誰勝出？刪除後舊副本上線會否讓資料復活？

假設需求為：單一區域三份副本、一般讀取可短暫落後、節點故障時仍能讀寫；對特定設定更新須做條件寫入，避免靜默覆蓋。這不是所有業務資料都適用的規格。付款或庫存可能要更嚴格的權威交易模型。

## 路由、分片與複本

```text
Client → Coordinator → 找出 key 所在分片與副本集合
                    ├→ Node A
                    ├→ Node B
                    └→ Node C
```

一致性雜湊或分區表決定責任節點，並支持新增/移除節點時搬遷。副本要分散到不同主機、機架或可用區。Coordinator 不是資料權威；它負責路由、收集回應、超時與結果合併。避免它成為單點，通常讓任意節點或前端服務都能充當協調者。

## 寫入與讀取門檻

設複本數 `N=3`，寫入等待 `W=2` 份確認，讀取從 `R=2` 份取得版本。固定副本集合下 `R+W>N` 表示讀寫集合有交集，卻**不單獨保證線性一致性**。理由包括：sloppy quorum 把資料暫放別的節點、並發寫入版本衝突、網路分割、讀取未做修復與不同副本集合的路由版本。

選較大的 W 可提升已確認資料的耐故障程度，但寫入延遲與可用性可能下降；較大的 R 能比較更多副本，但讀取更慢。要定義「失敗」：如果只收到一份確認而回 timeout，寫入可能已部分成功，客戶端重試需用操作 ID 或版本條件。

## 並發寫入與版本

| 方法 | 適用時機 | 風險 |
| --- | --- | --- |
| 最後寫入者勝 | 允許覆蓋，且時鐘/排序規則明確 | 可丟失較早但有效的更新 |
| Compare-and-set | 要求以已讀版本為前提更新 | 客戶端必須處理衝突重試 |
| 多版本並存 | 離線/跨區並發修改 | 業務端需要合併 |
| 單 key 排序器/主節點 | 要求明確的同 key 順序 | 主節點切換與可用性成本 |

裝置實體時鐘可能偏移，不能把較新的時間戳直接等同較新的業務意圖。若不能自動合併，保留衝突版本並交由業務決策，比無聲丟棄安全。

### 用向量時鐘判斷「先後」與「並發」

向量時鐘記錄各寫入者或副本已看過的版本進度。以兩個寫入者 A、B 為例，初始值是 `(0,0)`；A 寫入後為 `(1,0)`，B 若未看過 A 的寫入而獨立寫入，得到 `(0,1)`。兩個向量沒有一個在每個分量都大於等於另一個，因此是**並發版本**，不能僅靠向量判定誰應覆蓋誰。若 B 先讀到 A 的 `(1,0)` 再寫，會得到 `(1,1)`；它在每個分量都不小於 `(1,0)`，所以可判定 B 的更新發生在 A 之後。

| 比較 | 結論 | 處理 |
| --- | --- | --- |
| `(1,0)` 與 `(1,1)` | 前者因果上較早 | 可保留後者 |
| `(1,0)` 與 `(0,1)` | 並發，沒有因果順序 | 保留 siblings，請業務合併或套用明定規則 |
| `(2,1)` 與 `(1,2)` | 仍是並發 | 不能用分量總和或實體時間任意裁決 |

合併購物車可以取商品集合，但「移除商品」與「新增商品」並發時，集合聯集不一定符合使用者意圖。合併規則要從資料語意出發。向量時鐘提供因果關係，**不提供全域時間線**；寫入者很多時向量也會變大，需要裁剪或改用其他版本方案，裁剪後可能降低衝突判斷精度。

## 成員發現與故障偵測

節點需要知道誰在環上、每個節點的資料範圍和健康狀態。Gossip 可讓節點定期交換成員資訊與 heartbeat 計數，逐步傳播新節點、離線與恢復事件。若某節點的 heartbeat 很久沒有前進，只能先判定「疑似不可達」；網路延遲、暫停或分割也會造成同樣現象。應把偵測閾值、路由摘除、資料遷移分開處理，避免短暫抖動觸發大量搬遷。

一條具體時間線：A 暫時不可達 → Coordinator 依當前成員檢視挑選替代節點 D → D 保存資料與「稍後交給 A」的 hint → A 恢復後 D 回送 → 背景修復再核對。這種 **sloppy quorum** 讓寫入在暫時故障時較容易繼續，但 `R+W>N` 的交集推論此時不能直接套在固定的原始三個副本上。hint 必須有容量、期限與積壓告警；原節點長期不回來時，仍須正式重配置副本，不能永遠靠 hint。

## 本機儲存引擎的讀寫路徑

分散式複寫決定資料要到哪些節點；節點內部還要決定**如何落盤與查找**。以下以常見的 log structured 儲存引擎作模型，實際產品細節會不同：

```text
寫入：收到 key/value → 附加到 commit log → 更新記憶體 memtable
      → 達到門檻後 flush 成不可變 SSTable → 背景 compaction

讀取：先查 memtable → 再檢查可能含 key 的 SSTable
      → 比較版本與 tombstone → 回傳有效值
```

`put` 回成功前要等到哪一步是**持久性契約**。只寫入作業系統緩衝區與等待 `fsync` 的風險不同；複本的「已確認」也應說明是否已持久化。Memtable 讓最近寫入可快速讀取，commit log 讓當機後能重播尚未 flush 的資料。SSTable 不原地改寫，所以刪除先寫 tombstone，舊值在 compaction 過程中才可能被回收。

SSTable 的 Bloom filter 可快速判斷某檔案**一定沒有** key 或**可能有** key；偽陽性只造成多查檔案，不應造成漏讀。Compaction 會整理重複版本與回收空間，但消耗磁碟 I/O；若寫入尖峰與 compaction 競爭資源，p99 會升高。面試中要同時估讀寫放大、磁碟空間放大與修復流量，而非只估原始資料容量。

> 延伸閱讀：[Dynamo 原始論文](https://pdos.csail.mit.edu/6.824/papers/dynamo.pdf)討論向量時鐘、gossip、hinted handoff 與副本修復；[Apache Cassandra 儲存引擎文件](https://cassandra.apache.org/doc/stable/cassandra/architecture/storage-engine.html)說明 commit log、memtable、SSTable 與 Bloom filter。這些是不同系統的設計材料，不表示它們具有相同的讀寫保證。

## 暫時故障與長期修復

- **Hinted handoff**：副本暫時不可用時，在其他節點保留提示寫入，待原節點回來補送；要限制保留期限與容量。
- **Read repair**：讀取比較多份版本後，將落後副本補齊；熱門 key 修得快，冷 key 可能長期沒人讀。
- **Anti-entropy**：背景掃描與摘要樹等方法比較區間，修復沒被讀到的資料。要限制修復頻寬，避免擠壓線上請求。
- **備份**：副本間會同步錯誤刪除；備份和版本保留提供另一種恢復能力。

## 刪除為何要有 tombstone

若直接把 key 從兩個副本刪掉，而第三副本離線，第三副本回來後可能把舊值再次複寫出去。刪除標記（tombstone）代表「此 key 在某版本已刪」，先複寫到副本；經過足夠長的修復窗口後再回收。保留太短會復活，保留太長增加儲存與掃描成本。

## 熱點與容量

資料量均勻不代表流量均勻。單一熱 key 可以用讀副本或快取，寫入熱點可能要依業務拆 key、做計數聚合或序列化。除了磁碟容量，也估 WAL、compaction、索引、複寫流量與大規模故障後的重建時間。監控副本落後、衝突率、hint 積壓、修復吞吐、p99 與資料核對結果。

## 自測參考解答與面試追問

### `N=3, W=2, R=2` 是否就保證讀到最新值？（對照原書第 99–108 頁）

**答：**在固定同一副本集合、成功寫入確實落到其中 W 份、讀取也取同一集合的 R 份且沒有並發寫入時，因 `R+W>N`，兩個集合至少交於一個副本，讀取可比較版本取得已確認寫入。但若允許 sloppy quorum 把寫入暫存到原副本集合外、發生網路分區、並發寫入或時鐘/版本比較錯誤，這個算式本身不足以保證線性一致。面試時要分清「節點數學上的交集」與「產品對客戶端承諾的讀寫語意」。

### 用向量時鐘判斷同時寫入，為何不能直接選時間較晚者？（第 103–109 頁）

**答：**若版本 A 的所有分量都不大於 B，且至少一項較小，A 因果地先於 B，可以用 B 覆蓋 A。若 A、B 各有一項比對方大，代表並發，不能判定誰應覆蓋誰。機器牆上時鐘可能偏移，最後寫入勝出雖簡單，會丟失另一端的內容；若業務不能容忍，就要保留多版本讓應用合併，或用 CRDT/特定欄位合併規則。選擇應由資料語意決定。

### 節點離線時 hinted handoff 與 anti-entropy 各做什麼？（第 110–118 頁）

**答：**Hinted handoff 暫存在別處的寫入提示，原目標副本恢復後盡快補送，改善短暫故障後的追趕。若提示過期、丟失，或副本間有未被讀到的舊差異，anti-entropy 仍要定期比較資料摘要並修復。Read repair 只會修到被讀取的 key；不能取代背景掃描。修復任務需限速，避免區域恢復時反而吃光線上 I/O 和網路。

### 1. A、B 是 version 2，C 離線仍是 version 1；讀到 A、C 怎麼辦？（第 95–106 頁）

**答：**若版本 2 明確因果地晚於版本 1，協調節點應回 version 2，並安排 read repair 讓 C 追上。只讀 A、C 能否安全回應，還取決於設定的讀取門檻 R、寫入門檻 W、複本數 N 和故障模式；不能光靠「多數較新」下結論。若兩值是並發寫入而非先後版本，應保留 siblings、交由應用合併或按預先約定的衝突政策處理。背景 anti-entropy 也要修復未被讀取的 key。

### 2. `put` timeout 後重試，何時有重複副作用？（第 100–108 頁）

**答：**`put(key, same_value)` 若只是設定值，重試多半可視為冪等；但「自增計數」、「建立新訂單」或「每次寫入觸發通知」重試會重複。Timeout 只表示客戶端不知道結果，不能推出原寫入失敗。請求要帶固定 operation ID，伺服器保存已處理結果，或使用 compare-and-set 的預期版本。外部通知還需自己的去重紀錄，鍵值儲存的冪等並不自動涵蓋副作用。

### 3. Tombstone 太早回收，資料怎麼復活？（第 112–120 頁）

**答：**原值在 A、B、C 都是 v1；C 離線後，A、B 寫入刪除標記 v2。若 A、B 在 C 回來前就把 v2 回收，C 帶著 v1 重新加入時，系統可能把它當成沒有衝突的有效資料，再複寫回 A、B。保留 tombstone 的時間至少要覆蓋允許節點離線及完成修復的窗口；超過窗口的節點回來時應重建資料，不可直接以舊磁碟加入。備份也要保留刪除語意，否則還原同樣可能讓舊值復活。
