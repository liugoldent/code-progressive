本章最值得白板推演的是**兩段式 frontier**：先按價值選候選 URL，再按 host 的可抓時間派送。若只增加 Fetcher 數量而不管理 host 間隔，總吞吐可能上升，卻會對單一站點造成不合理負荷。

## 先限定爬蟲的任務

搜尋引擎、價格監測與網站備份的目標不同。先確認要抓多少頁、抓哪些域名、更新頻率、是否執行 JavaScript、是否需要圖片/PDF，以及可接受的索引延遲。若目的是搜尋索引，光下載 HTML 不夠：還要解析、正規化、去重、儲存、建索引與重新抓取。

```text
種子 URL → 正規化與去重 → URL frontier → per-host 排程 → Fetcher
                 ↑                                     ↓
                 └──── 擷取新連結 ← 解析/清洗 ← 回應內容
                                           ├→ 文件儲存
                                           └→ 搜尋索引與重抓時間
```

## Frontier 不是普通 FIFO 佇列

若所有 URL 只按發現時間排隊，某一個大網站可能佔滿 Worker，還會對該站造成過高流量。可以按 host 分佇列，記錄每個 host 下次可抓時間，Scheduler 從可執行的 host 中公平挑選。高價值或久未更新的頁面可有優先級；同時限制全域並行、每 host 並行與流量。

每個 URL 可有 `discovered → scheduled → fetching → fetched → processed` 狀態；失敗進 `retry_at` 或永久失敗。Worker 取任務要有 lease，超時後可由別的 Worker 重試；同一 URL 可能因此同時被抓兩次，所以處理與存檔要能去重。

### 把「優先級」與「對網站有禮貌」拆成兩段排程

一個可行的 frontier 實作有兩組佇列：先把 URL 依重要性放進高、中、低優先級的候選佇列；再由 router 分派到各 host 的佇列。Host scheduler 保存每個 host 的 `next_allowed_at` 與目前抓取數，只從已到期且未超並行限制的 host 選任務。如此高優先級不會讓同一網站瞬間收到數百個請求，而冷門網站也不會永遠被大站壓住。

```text
新 URL → canonicalize / 去重 → priority queues
                                ↓ 依 host 分派
                           host-a queue  next_allowed_at=10:03:02
                           host-b queue  next_allowed_at=10:03:00
                                ↓ host scheduler 選可執行任務
                              Fetcher
```

假設 A 網站有 1,000 個高優先 URL，但每秒只允許 1 個請求；B 網站有 10 個中優先 URL、每秒允許 2 個。排程器在 A 等待下一次抓取期間可抓 B；新增 Worker 會改善跨 host 的總吞吐，卻不應提高 A 的單站速率。優先級也需要 aging 或份額，否則低優先佇列可能永遠排不到。

### Frontier 的持久化與去重邊界

排程狀態不是純快取。若程序重啟後失去「哪些 URL 已抓、哪些正在租約中、下一次可抓時間」，可能重複抓取或對單站造成尖峰。可將 URL 狀態和排程時間持久化，Worker 領取時設定 lease；完成時以 `url_id + crawl_generation` 做條件提交。若 lease 到期後舊 Worker 又回報成功，版本條件可避免過期結果覆蓋較新的抓取。

去重可分三層：URL 身分（是否抓過這個正規化 URL）、內容雜湊（不同 URL 是否完全相同）、近似文件指紋（模板不同但正文高度相似）。不能因為內容重複就刪掉所有 URL 身分：搜尋結果、canonical 關係、來源站與下次重抓時間仍可能不同。

## URL 去重與內容去重分開

URL 正規化可處理相對路徑、fragment、主機名大小寫及預設 port，但不能任意刪 query 參數：`?page=1` 與 `?page=2` 可能是不同內容。相同內容也可能出現在不同 URL；可用內容雜湊辨識完全相同的文件。近似重複需要額外指紋或相似度方法；同一 URL 隨時間變內容則需保留版本或更新索引。

Bloom filter 可在大規模時快速排除明顯已見 URL，代價是有偽陽性。若不能漏抓，不能只用 Bloom filter 作最終判定；應搭配權威已見集合或允許定期重新掃描。

## 禮貌與錯誤分類

抓取前應檢查目標站公開的爬取規則，使用識別清楚的 User-Agent，對同 host 設速率、並行與最短間隔。遇 `429`、`503` 或網路不穩應退避；若有適用的 `Retry-After` 則納入排程。指數退避加抖動可避免所有 Worker 同時重試。

| 情況 | 常見動作 |
| --- | --- |
| DNS/連線暫時失敗 | 有上限的重試與退避 |
| 404 | 記錄並降低重抓頻率，不無限重試 |
| 301/302 | 限制轉址次數，重新檢查目的地是否在允許範圍 |
| 429/503 | 降低該 host 速率，尊重重試提示 |
| 巨大/不支援內容 | 依大小與 Content-Type 拒收或截斷 |
| 惡意 HTML | 隔離解析環境，不在管理後台直接執行 |

爬蟲會收到外部輸入，應防止 SSRF：不要讓外部提供的 URL 指向內部網路、雲端 metadata 服務或環回位址。DNS 解析與轉址後都要檢查目標；限制大小、處理時間與解析 CPU。

## 重新抓取與新鮮度

所有頁面每小時重抓通常太貴。可依歷史變更率、重要性與伺服器回應調整 `next_fetch_at`。若支援 ETag 或 Last-Modified，可用條件請求減少頻寬，但仍要尊重對方規則。新發現的高價值頁面優先抓，久未更新的低價值頁面較少抓。監控文件新鮮度，而不是只看每秒下載量。

## 估算練習與觀測

假設 1 億頁、每頁平均 100 KiB、每週更新一次，原始下載約 10 TB/週，平均約 16.5 MiB/s。這只是下限：重試、轉址、文件大小長尾、解析/索引開銷及 host 限制都未算。即使有足夠總頻寬，若頁面集中在少數網站，禮貌限速仍會決定完成時間。

監控 frontier 待處理量、每 host 抓取速率、成功率、429 率、去重率、文件變更率、索引落後與重抓逾期率。故障時先保留 frontier 與抓取狀態，讓 Worker 可恢復；不能只看抓取程序是否仍在線。

## 自測參考解答與面試追問

### Frontier 為何分「優先級」和「逐站排程」兩層？（對照原書第 154–160 頁）

**答：**優先級回答「哪個 URL 更值得先抓」，逐站排程回答「現在對這個 host 發請求是否合宜」。若只有全域高優先級佇列，熱門站的大量 URL 會壟斷 Fetcher，並可能觸發對方的 429 或封鎖。先依重要性選候選，再放入每 host 佇列，host scheduler 依 `next_allowed_at` 與並行上限取件；這樣能同時維持價值排序與禮貌性。要把排程狀態持久化，重啟後不能瞬間重抓同一站。

### 內容變動慢的頁面多久重抓？（第 160–167 頁）

**答：**不存在固定的「所有頁面每小時一次」。可按頁面重要性、歷史變動率、上次抓取時間和對方給的快取提示決定 `next_fetch_at`；對支援 ETag/Last-Modified 的站點發條件請求，減少傳輸，但仍占用請求配額。若高價值頁面突然常變，縮短間隔；多次未變則逐步拉長。指標要看重要文件的資料新鮮度和重抓成本，不能只看每秒抓了多少頁。

### 1. 同一網站 100 萬頁、最多 2 頁/秒，最快多久？（對照原書第 154–159 頁）

**答：**至少 `1,000,000 ÷ 2 = 500,000 秒 ≈ 5.8 天`，還沒算下載、重試、DNS、解析與站點停機。增加 Worker 不會突破這個網站的 2 頁/秒禮貌上限，只能用來並行抓**其他**網站。若希望縮短時間，得與站方協商更高允許速率、使用官方 API 或減少必抓頁數，而不是讓更多 Worker 一起打同一 host。

### 2. `?sort=price` 與 `?sort=rating` 能視為同一 URL 嗎？（第 149–153、165–167 頁）

**答：**不能只因 path 相同就合併；排序參數可能使頁面順序不同，也可能揭露不同商品。URL 正規化可去掉追蹤參數、排序無關參數的次序、規範大小寫與預設埠，但哪些 query 會改變內容必須依網站或樣本驗證。URL 去重避免重抓同一位址；內容去重則可用內容雜湊辨識不同 URL 的相同文件。兩層都需要，且 canonical 標記只能當線索，不應無條件信任。

### 3. 抓取成功、標記完成前 Worker 當機，如何避免重複索引？（第 160–164 頁）

**答：**Frontier 使用租約；到期後任務可重跑，因此下載與索引應預期至少一次執行。以正規化 URL、內容雜湊和抓取版本建立去重鍵，將索引寫入設為 upsert 或版本條件更新；同一任務重送不能無限新增文件。任務完成狀態應在文件與索引持久化後才確認，否則會產生「已完成但沒索引」的缺口。要監控租約重派數與內容重複率。
