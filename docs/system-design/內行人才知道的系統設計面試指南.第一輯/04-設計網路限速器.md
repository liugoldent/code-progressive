本章的主線是：先定義**誰受到什麼限制**，再選符合突發與平滑需求的演算法，最後處理多副本計數的原子性與故障行為。若先選 Redis 或某一演算法，往往會漏掉配額語意。

## 問題先定義完整

限流器控制一段時間內允許多少請求，用於保護服務容量、公平分配資源與降低濫用。先確認**限制單位**：IP、登入使用者、API key、租戶、端點或它們的組合。匿名 IP 限流可能誤傷同一辦公室或行動網路；只按使用者限制，又可用大量帳號繞過租戶總量。因此通常要多層規則。

示例需求：搜尋 API 每個 API key 每分鐘 600 次、每個租戶每分鐘 3,000 次；允許每秒 30 次短突發；登入 API 更嚴格。超限回 `429 Too Many Requests`，可提供 `Retry-After` 與說明性錯誤碼。要明確定義超限請求是否計入配額、規則更新多久生效，以及限流器失效時放行或拒絕。

## 五種常見演算法

| 演算法 | 狀態 | 優勢 | 主要問題 |
| --- | --- | --- | --- |
| 固定時間窗 | 窗口與計數 | 簡單、省空間 | 邊界可連續通過兩窗額度 |
| 滑動日誌 | 每次請求時間 | 精確 | 熱 key 記憶體多 |
| 滑動計數 | 前後窗計數 | 成本較低 | 近似值會有誤差 |
| Token bucket | token 數與上次補充時間 | 容許有限突發 | 需處理補充速率與原子性 |
| Leaky bucket | 有界佇列與排出速率 | 平滑下游負載 | 排隊延遲、滿桶拒絕 |

固定窗若限制每分鐘 100 次，12:00:59 通過 100 次，12:01:00 又通過 100 次，兩秒內可有 200 次。滑動窗可改善邊界；若真正需求是「長期平均 10 次/秒，允許 30 次突發」，token bucket 更自然。

### 滑動日誌與滑動計數的實際差異

滑動日誌對每個 key 保存最近一個時間窗內的請求時間。以「60 秒內最多 3 次」為例，在 `t=0, 10, 20` 先通過三次；`t=59` 到來時移除早於 `-1` 的紀錄，三次仍在窗內，因此拒絕；`t=61` 時 `t=0` 退出窗口，可以通過。資料結構可用按時間排序的集合，單次檢查包括「清過期 → 計數 → 插入」，也必須原子執行。大量熱 key 的每次請求都存時間戳，記憶體與清理成本明顯。

滑動計數只保存目前及前一個固定窗的計數，依窗口已經過的比例估算。例如前一分鐘 80 次、目前分鐘 20 次，現在已過 25 秒，估計最近 60 秒次數約 `80 × 35/60 + 20 ≈ 66.7`。它是近似值：請求若集中在前一窗口的最後幾秒，真值可能不同。硬性財務配額不應只靠這種估算；保護性限流通常可接受小誤差。

## Token bucket 的狀態更新

令牌桶容量 `capacity=30`、補充率 `rate=10 token/s`。請求到來時先算 `new_tokens = min(capacity, old_tokens + elapsed_seconds × rate)`；若 `new_tokens ≥ cost`，扣除 cost 後放行，否則拒絕。`cost` 可用來給昂貴端點更高權重。

```text
讀取桶狀態 → 根據經過時間補令牌 → 判斷足不足 → 扣令牌 → 寫回
```

上面整段必須在共享狀態中**原子執行**。若兩個 API 副本都先讀到 1 token，再各自扣掉，會超額。Redis 腳本、具條件更新的資料庫或集中式計數器皆可實作；要依 latency 與配額精度選擇。桶狀態需要 TTL，並防止使用不同時鐘造成負 elapsed time。若 Redis 使用單節點時間作依據，也要理解故障切換後的行為。

## 多層配額如何一起檢查

同一請求可能要過「IP + user + tenant + endpoint」四條規則。可由規則引擎產生 key，例如 `tenant:42:search`。若逐條扣額，第三條拒絕時前兩條已扣，要決定是否回補或接受這種計費語意；若要求「全部通過才扣」，需同一原子腳本或一致的預留/提交協定。跨 Redis 分片時全域原子性更難，應簡化規則或接受有界誤差。

## 分散式與跨區

- **集中計數**：精度高但增加每次請求的網路往返，熱租戶可能集中到一個 key。
- **區域子配額**：各區本地檢查快，但一區沒用完的額度不能立即給另一區。
- **租借額度**：區域向中心一次借一批 token，降低中心壓力；借得越多，故障時可能超發越多。

對網路分割，不能同時保證所有區域持續放行與全域硬上限絕不超過。若是昂貴第三方 API，可能寧可限縮；若是一般讀取，可能暫用本地限流並接受小幅超額。把這個產品取捨說清楚。

## 限流器放在哪裡

| 位置 | 能擋住什麼 | 仍要注意 |
| --- | --- | --- |
| CDN / 邊緣 | 大量匿名流量、明顯濫用，降低回源 | 邊緣可能不知道登入者與租戶；各節點計數不完全一致 |
| API gateway | 登入後的通用配額、端點規則 | 所有請求額外查共享狀態的延遲；gateway 也須可擴容 |
| 應用服務 | 按業務成本限制，例如報表匯出 | 太晚拒絕可能已消耗解析與認證資源 |
| 下游工作佇列 | 控制真正執行速率 | API 接受任務不等於任務立刻完成；需回報排隊狀態 |

通常要組合使用：邊緣擋粗粒度濫用，gateway 管通用配額，服務再保護昂貴操作。對真正耗費大量 CPU 的任務，入口限制 QPS 仍不足以保證下游不過載；另需限制**同時執行數**與佇列長度。

## 規則設定、推出與故障演練

規則可建模為 `scope + identity + endpoint + capacity + refill_rate + cost + action + version`。新增規則先 shadow mode：只計算「若啟用會拒絕多少」但不實際拒絕，觀察合法用戶受影響比例，再逐步放量。要有緊急回滾與規則版本，否則某些 gateway 已套新版、某些仍用舊版時，很難解釋配額變動。

故障策略要逐條規則制定，而非整個系統共用一個開關。登入防暴力猜測可暫時拒絕或走額外驗證；一般讀取可使用本機保守桶繼續服務；昂貴匯出可排隊。演練 Redis 不可達、熱 key、規則誤設與時鐘偏移，並監控「被拒絕數」與「下游是否真的較穩定」，避免只把錯誤從 5xx 轉成 429。

## 回應與觀測

客戶端遇 `429` 應依提示退避，避免立即重試形成雪崩。對 `Retry-After`，若是 token bucket，提示可根據缺少 token 的補充時間估算；對多條規則，應取真正限制恢復的時間。監控每條規則拒絕率、限流器 p95、共享狀態錯誤率、熱門 key、下游飽和度與放行後錯誤率。配額過低也會傷害合法用戶，所以需有告警與調整流程。

## 自測

1. 每租戶 3,000 次／分鐘、500 名員工。只用 IP 或 user ID 各有什麼缺陷？
2. 把令牌桶部署在 3 個區域且中央 Redis 中斷，提出兩種降級方式並量化最壞超發。
3. 畫兩台 API 同時讀到最後一個 token 的競爭時間線，指出原子操作邊界。

## 自測參考解答與面試追問

### 為何固定窗邊界會超量，滑動計數如何補救？（對照原書第 65–69 頁）

**答：**若限制每分鐘 100 次，使用者可在 12:00:59 發 100 次，又在 12:01:00 發 100 次；兩秒內共 200 次仍各自符合固定窗。滑動日誌保存每次請求時間，準確但記憶體高。滑動計數保留前後兩個固定窗的計數，按前一窗與目前 60 秒區間的重疊比例加權估算。例如目前窗 20、前窗 100、距目前窗起點 15 秒，估值是 `20 + 100 × 45/60 = 95`；下一次請求後估值約 96。這是近似值，若配額絕對不可超發就不能把近似演算法當精確保證。

### Token bucket 和 leaky bucket 的產品差別？（第 60–64 頁）

**答：**Token bucket 保存可累積的額度，閒置後可容許有限突發，適合希望短時間爆量仍不超長期平均的 API。Leaky bucket 把到來請求放入有界佇列，按固定速率送下游，適合下游只能平穩消化工作的情境；代價是排隊延遲。若登入 API 必須快速拒絕過量嘗試，排隊可能不是好選擇；若是可等候的匯出任務，平滑排出更合理。兩者都要問「桶滿/佇列滿」時回什麼以及客戶端何時重試。

### 限流器本身壞掉，為何不能全部 fail-open 或 fail-closed？（第 70–78 頁）

**答：**全部 fail-open 可能讓登入暴力猜測或昂貴匯出壓垮下游；全部 fail-closed 則讓普通讀取也中斷。可按端點風險定義：安全敏感端點採保守拒絕或額外驗證；一般讀取可用本機小桶暫時放行；昂貴工作可排隊。這些策略要先以故障演練驗證，並讓監控能區分「真正超額」與「限流基礎設施故障」。

### 1. 3,000 次/分鐘的租戶配額，為何不能只用 IP 或 user ID？（第 55–59、70–73 頁）

**答：**500 名員工可能共用公司出口 IP，按 IP 限制會讓正常使用者彼此搶額度；行動網路 NAT 也有同樣問題。只按 user ID 則 500 人各得 3,000 次，租戶總量可達 150 萬次/分鐘，失去控制成本的目的。做法是同一請求同時檢查租戶總桶、個人桶與必要的端點桶，任一不滿足就拒絕。扣額度必須有原子邊界，否則先扣了個人桶又發現租戶桶不足，會白白消耗個人配額。

### 2. 三區的中央 Redis 中斷，怎樣降級？最壞超發多少？（第 74–78 頁）

**答：**一種方法是拒絕高風險寫入，對普通讀取採 fail-open；此時全域配額無法保證，超發上界取決於故障期間的實際請求量，不能假裝仍是 3,000。另一種是預先把每分鐘 3,000 個 token 拆成每區 1,000 個本地桶；正常時可能有配額閒置，但 Redis 中斷時三區合計至多放行 3,000（前提是區域分配與窗口切換事先協調）。若每區都獨立給完整 3,000，最壞可放行 9,000，也就是超發 6,000。選擇取決於可用性與精準配額何者更重要。

### 3. 兩台 API 同時看到最後一個 token，哪裡要原子化？（第 74–75 頁）

**答：**若 A、B 都先讀到 `tokens=1`，各自在本機判斷通過，再各寫回 `0`，一個 token 被消費兩次。原子操作必須包住「依時間補 token → 檢查所有相關桶 → 扣 token → 回傳剩餘量」；可用同一分片上的腳本或交易完成。若跨多個獨立儲存分片檢查，單一腳本不能涵蓋全部，應改設計配額層級或接受有界超發，不能假設多個 Redis 命令天然原子。
