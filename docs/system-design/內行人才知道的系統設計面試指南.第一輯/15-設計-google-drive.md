## 需求比「上傳檔案」多

核心功能：上傳/下載、資料夾、同步多裝置、版本歷史、刪除恢復、分享與權限。先問最大檔案、是否只傳變動區塊、離線多久、同檔多人同改怎麼辦、撤權多久生效、是否要預覽與全文搜尋。若只把整檔放物件儲存，還沒有解決版本、目錄樹與多裝置一致性。

系統可拆三層：**內容區塊**（檔案位元組）、**metadata**（目錄樹、版本與 ACL）、**變更日誌**（裝置要同步的變動）。內容可以在物件儲存，metadata 與 changelog 需要能協調順序和條件更新。

## 一個可工作的資料模型

| 資料 | 例子 | 角色 |
| --- | --- | --- |
| FileEntry | `file_id, parent_id, name, owner_id, current_version, status` | 目錄樹與現況 |
| FileVersion | `file_id, version, manifest_id, created_by, created_at` | 不可變版本 |
| Manifest | 依順序排列的 block hashes/locations | 還原一個版本內容 |
| Block | `hash, size, storage_location` | 分塊內容與校驗 |
| ChangeLog | `cursor, file_id, operation, version` | 多裝置增量同步 |
| ACL/Share | 主體、權限、到期、撤銷版本 | 取得 metadata 與內容前驗權 |

目錄結構需要處理同名檔案、移動資料夾、循環移動、權限繼承與大量子項目。`parent_id` 的更新可以是小交易；移動大資料夾時不要逐檔同步複製內容，只需讓讀取路徑能理解新的樹位置與權限。

## 分塊上傳與提交

```text
裝置計算區塊 hash → 詢問哪些區塊已存在 → 上傳缺少區塊
→ 提交 manifest + expected_version → metadata 交易更新 current_version
→ 寫 ChangeLog → 通知其他裝置 → 其他裝置依游標拉取
```

每塊用內容雜湊驗完整性；上傳中斷後只重傳缺少的塊。跨使用者以雜湊去重可能洩漏某內容是否已存在，還有惡意碰撞/驗證邊界，所以可以先限定在同一使用者或同一信任範圍去重。新 manifest 提交前要確認每塊都可靠存在；否則其他裝置會讀到缺塊的版本。

### 區塊伺服器到底省了哪些位元組

一本 1 GB 的檔案只改了 2 MB，整檔重新上傳會浪費頻寬。客戶端或區塊伺服器可用固定大小或內容定義切塊，找出有變動的區塊，只傳缺少的資料。固定切塊實作簡單，但檔案前面插入少量內容時，後續邊界都可能改變；內容定義切塊較能保留未改動片段，代價是計算與實作複雜度。對每塊先壓縮再加密並上傳，下載時按 manifest 的順序解密、解壓與校驗。已經壓縮的圖片、影片再壓一次，通常收益有限，應依 MIME 與實測選擇。

若相同內容的密文因不同使用者金鑰而不同，伺服器端的跨使用者去重便不會自然成立；為了去重改用收斂加密又可能洩漏內容存在性。面試時應明確說出**去重範圍、金鑰邊界與威脅模型**，而不是同時宣稱全域去重與任意端對端加密。區塊位置可變，manifest 應引用穩定的邏輯 block ID，底層搬遷不必改動每個檔案版本。

先上傳區塊後更新 metadata，可能留下**孤兒區塊**，可由暫存期限與垃圾回收處理。反過來先更新 metadata 再上傳區塊，可能讓使用者看到不可讀版本，風險更高。提交操作要有固定 ID，以便重試時查詢「是否已提交」。

### 把暫存與正式版本分開

上傳可建立 `upload_session`，記錄 `file_id, expected_version, manifest_hash, idempotency_key, expires_at`。Metadata 先有**僅上傳者可見的 pending 記錄**，客戶端拿授權把缺少的區塊送到物件儲存；伺服器收到完成回呼或主動查驗後，核對物件大小與雜湊，再在同一個 metadata 交易中建立 FileVersion、更新 `current_version` 並寫入 ChangeLog。最後通知其他裝置。`pending` 不應被一般下載或同步列表當成已完成版本。

```text
建立 session/pending → 上傳缺塊 → 伺服器驗證所有區塊
→ 條件提交 FileVersion + ChangeLog → 發送變更通知
→ 其他裝置依游標拉取 metadata 與內容
```

物件儲存完成通知可能重複、延遲或遺失。處理回呼時驗證 session 與物件身分，使用 idempotency key 讓重複回呼只產生一個版本；另設掃描器尋找「物件已齊但仍 pending」的 session。若 metadata 提交已成功而 API 回 timeout，客戶端先用同一 idempotency key 查詢結果，不能直接建立下一個版本。若 `expected_version` 已過期，完整區塊仍可短暫保留供衝突處理，不能靜默覆蓋目前版本。

## 多裝置同步與衝突

裝置保存最後套用的 ChangeLog 游標。收到推播只是提示，還要依游標拉取權威變更；推播若遺失，重連仍可補齊。拉取要處理分頁與游標過期：若裝置離線超過日誌保留期，應做完整狀態對帳，而不是從已回收的游標繼續。

兩台離線筆電從 version 7 各自修改。A 上線以 `expected_version=7` 提交 version 8；B 後上線同樣帶 7，條件更新失敗。B 不應默默覆蓋 A，可以取得 8 後嘗試類型特定合併，或建立衝突副本供使用者選。二進位檔通常不能安全自動合併；裝置時間戳不應是唯一裁判。

### 哪些資料一定要同步看見

原書特別區分檔案的位元組儲存與 metadata 的權威版本。對同一檔案，`current_version`、版本清單與變更游標要在同一個一致性邊界內發布，至少保證「看見新版本 metadata 時，內容區塊已可讀」。快取讀到舊 metadata 可以暫時顯示舊版本，但不能拼成「新版本名稱 + 舊版本區塊」。一個做法是所有讀取都攜帶 immutable `version_id`，快取 key 含版本；更新時只切換 `current_version` 指標。若產品承諾強一致的跨裝置列表，權威 metadata 讀路徑或失效機制就不能只靠不定期過期的快取。

通知只說「有變更」，不攜帶完整檔案作為權威。線上的裝置可持續連線或長輪詢取得提示；離線裝置重連後依游標補拉，這樣通知服務故障也不會永遠漏同步。服務端要為每裝置維護最後確認位置或讓客戶端持久化游標，並定義日誌截斷後的全量比對流程。

## 刪除與版本保留

刪除先產生 tombstone/刪除事件，讓所有裝置知道檔案已移除，並在回收期內允許恢復。離線裝置重新上線時應先同步刪除事件，不能把其舊檔案當新版本又上傳。清除內容區塊前，檢查其他版本或使用者是否仍引用它；引用計數與垃圾回收也要能從崩潰中恢復。

版本保留要有明確政策，例如「最近 30 天保留全部版本，之後只留每日或每週快照，超過配額再刪最舊的非釘選版本」。政策要按租戶、法規與產品需求設定，這裡只是設計例子。清理順序是先讓舊版本不可見、等待同步與恢復窗口，再核對區塊引用並垃圾回收；正在上傳、被分享或保留於回收桶的版本也可能仍引用相同區塊。冷資料可移到較便宜的儲存層，但下載可能變慢，恢復時間與取回成本必須反映在產品承諾。

## 分享與撤權

下載前驗 ACL 和分享連結狀態；若使用短期簽名 URL，撤權可能要等 URL 到期，必須把生效窗口告訴產品。metadata 快取、CDN 和裝置本地內容各有不同可撤回性：已下載到別人的裝置的位元組，伺服器無法保證「收回」。可撤銷的是未來的伺服器存取權，不應承諾更強的能力。

## 故障與觀測

監控上傳完成率、分塊校驗失敗、metadata/內容不一致、同步落後、游標過期、衝突率、孤兒區塊、ACL 拒絕、備份恢復時間。多份物件副本能抗硬體故障，版本歷史與備份則用於誤刪或軟體 bug；兩者不能互相取代。

### 逐元件故障時使用者會看到什麼

| 故障點 | 可觀察現象 | 恢復設計 |
| --- | --- | --- |
| 上傳/區塊服務不可用 | 已上傳片段成功、後續片段失敗 | 保留 session 與片段清單，恢復後續傳 |
| 物件儲存短暫不可讀 | Metadata 顯示檔案，但下載失敗 | 不提前發布未驗證版本；已發布檔案靠副本與重試恢復 |
| Metadata 資料庫不可用 | 無法提交新版本或列目錄 | 不以物件存在直接推斷提交成功；恢復後以操作 ID 查詢 |
| Metadata 快取過舊 | 某裝置看不到新版本或舊 ACL | 版本化 key、失效通知；敏感權限在權威路徑驗證 |
| 通知服務不可用 | 其他裝置沒即時收到變更 | 裝置重連/週期輪詢 ChangeLog 游標補齊 |
| 裝置長期離線 | 游標過期、與雲端版本衝突 | 全量對帳並保留衝突副本 |

面試時可追一條「上傳成功但別的裝置看不到」的排查線：先確認 session 是否已提交，再查 ChangeLog 是否寫入、通知是否送達、對方游標是否前進、內容區塊是否可下載。每一段都要有可關聯的操作 ID。

## 自測參考解答與面試追問

### 為何「只傳修改的區塊」與「只存一份相同區塊」不是同一件事？（對照原書第 292–295 頁）

**答：**差異同步節省**網路傳輸**：比較本地舊版與新版，只把變動區塊上傳。去重節省**伺服器儲存**：多個版本或檔案引用同一個已保存的區塊。兩者可以一起使用，但切塊策略、加密方式與信任範圍可能互相牽制。若每次加密都使用不同隨機金鑰，密文不再相同，伺服器不容易跨檔去重；若為了去重透露某塊已存在，又可能產生內容存在性洩漏。回答時應分開算頻寬與容量收益。

### 為何 metadata 先顯示新版、內容晚點上傳很危險？（第 296–300 頁）

**答：**其他裝置可能先看到 `current_version=v8`，隨後依 manifest 下載時發現部分 block 不存在，形成「目錄正確、檔案不能讀」的狀態。比較安全的順序是先讓全部區塊可靠可讀，驗證後再以單一 metadata 交易發布 FileVersion、目前版本指標與變更事件。先上傳造成的孤兒區塊可用到期清理；先發布造成的錯誤則會直接影響讀者。提交中斷時以 session ID 查權威狀態，不能憑客戶端是否看到回應推斷。

### 1. 最後一塊已上傳，但 metadata 提交 timeout，怎麼辦？（對照原書第 286–287、298–299 頁）

**答：**客戶端不能只憑 timeout 判斷提交失敗。它用原本的 `upload_session_id/idempotency_key` 查狀態：若 `committed`，直接顯示既有版本；若仍 `pending`，要求伺服器核對全部區塊並重試同一個條件提交。提交交易要同時更新 FileVersion、`current_version` 與 ChangeLog，不能分別成功一半。若網路中斷時別的裝置已提交更新，`expected_version` 條件失敗，應進入衝突流程，不能覆蓋新版本。

### 2. 兩台離線筆電改同檔，怎樣不靜默覆蓋？（第 290–291、296–300 頁）

**答：**兩端各保存開始編輯時的 base version，例如 v7。A 先提交，服務端以 compare-and-set 把 `current_version` 從 7 改成 8；B 後到，仍帶 `expected_version=7`，提交被拒絕為衝突。B 的內容不能直接丟掉，可建立另一個不可變版本或「衝突副本」，通知使用者比較與選擇。若是可合併的文字檔，可嘗試三方合併；圖片、壓縮檔等二進位內容不要假裝能自動合併。用裝置本地最後修改時間決勝，會因時鐘誤差遺失資料。

### 3. 撤銷分享連結，但 CDN 還有快取，如何保證窗口？（第 282–283、300–303 頁）

**答：**先定義撤權窗口，例如「撤權後 2 分鐘內不再發出新的下載授權」。若 CDN 直接以長效公開 URL 供檔，做不到這個保證；可把內容 URL 設成短效簽名，或在邊緣驗證授權並在撤權時清快取。Metadata/ACL 快取也需要同步失效或短 TTL。已經下載到對方裝置的內容無法追回，因此撤權保證是未來的服務端存取，而非抹除所有已取得副本。

### 4. 通知服務故障，兩天後離線裝置重連會漏同步嗎？（第 300–304 頁）

**答：**不應漏。通知只是提示；裝置保存最後連續套用的 ChangeLog 游標，重連時分頁拉取其後的所有變更。若日誌只保留一天、裝置離線兩天，舊游標已失效，服務端必須回明確錯誤並觸發全量目錄/版本對帳，而不是回空結果讓裝置誤以為已最新。對帳後再換成新的游標；本地未提交修改仍依版本條件處理衝突。
