# 03｜Google 地圖

## 把龐大產品切成可討論的子題

地圖顯示、地點搜尋、路線規劃、交通狀況與導航是不同系統。面試先選定範圍：例如「提供地圖圖磚與從 A 到 B 的駕車路線」，再詢問離線地圖、轉彎提示與即時交通是否包含。不要用一張萬能架構圖跳過資料更新與路線演算法。

## 地圖顯示

地圖資料可依縮放層級與座標切成圖磚。相同區域在不同縮放層級有不同細節，客戶端只請求視窗可見圖磚；CDN 適合快取熱門、更新相對慢的圖磚。道路或店家變動後需增量更新受影響圖磚，並給圖磚版本，避免客戶端混用新舊道路。向量圖磚讓客戶端調整樣式與語言，但提高裝置端繪製成本；點陣圖磚較直接，樣式變動需重新產生。

```text
地理來源 → 清洗/拓撲檢查 → 多層級圖磚生成 → 物件儲存/CDN
搜尋請求 → 地點索引 → 候選與排序
路線請求 → 道路圖與交通權重 → 路徑搜尋 → 幾何線與導航步驟
```

## 路線規劃

道路是帶方向與權重的圖：路口/位置是節點，道路段是邊。權重可代表距離或預估時間，單行道、禁轉與收費路段是約束。基本演算法可從 Dijkstra 與 A* 理解；真實大圖常用預處理、分區或階層化來縮短查詢。預處理能加快常見路線，代價是道路與交通權重更新時要維護索引。

靜態道路圖與即時交通應分層處理。交通觀測可能延遲、稀疏或帶噪聲；路線估時要標明資料時間，不應把單一 GPS 速度當成整條路的真相。重新規劃太頻繁會讓導航路線震盪，可設定改善門檻與冷卻期。

## 面試深入問題

- 圖磚、地點索引與道路圖的更新速度不同，如何分別發版與回滾？
- 跨國路線如何跨分區規劃？可在區域內算細節、在區域間用高階道路圖。
- GPS 偏移到平行道路時如何做 map matching？需考慮連續軌跡，而非只找最近道路。
- 觀測圖磚 CDN 命中率、路線計算 p99、導航偏航率及 ETA 誤差。

**自己練習：** 以「每秒 5 萬圖磚請求、每秒 1 千路線請求」為假設，估 CDN 與路線計算的擴充方式，指出最可能的成本來源。

## 圖磚如何由座標取得

常見地圖顯示會把世界依縮放層級 `z` 分成 `2^z × 2^z` 的格子，客戶端依視窗範圍請求 `(z, x, y)` 圖磚。放大一級後，同一地理區域通常需更細的四塊圖磚。這是理解請求量與快取鍵的模型，不代表所有地圖服務都採相同投影或圖磚尺寸。地圖移動時可預取視窗邊緣的相鄰圖磚；弱網路先顯示較低解析度圖磚，再替換成目標縮放層級。

圖磚版本可放在 URL 中，例如 `/tiles/v42/z/x/y`。新資料上線後舊 URL 仍可由 CDN 快取，客戶端切到新版本時不會混用不同版本。代價是版本切換後短時間可能需要大量重新填充 CDN，最好分區或分層逐步發布。

## 路徑搜尋的逐步例子

假設 A 到 D 有兩條路：`A → B → D` 距離 8 公里但塞車需 25 分鐘，`A → C → D` 距離 11 公里需 15 分鐘。如果需求是最快到達，邊權重就應是預估時間，而非公里數。A* 的啟發函數要低估剩餘成本，否則可能失去最佳路徑保證；交通時間會變動時，先預處理的最短路結果也可能失效。路線回覆應包含使用的交通資料時間與 ETA，不要只給一條幾何線。

每秒 5 萬圖磚請求與 1 千路線請求不能只比 QPS：圖磚多半可由 CDN 命中，路線計算可能需要讀大圖和運算。若 CDN 命中率 95%，回源約 2,500 QPS；若每次路線計算平均耗 20 ms CPU，1,000 QPS 約需 20 個 CPU 核心的純計算量，還要加尖峰、等待與餘裕。這些都是示例假設，需以壓測校正。

## 把路線、導航與 ETA 分開

路線規劃在出發時找一條合適路徑；導航在行進時持續接收 GPS、判斷使用者是否仍在路上、提示下一個轉彎；ETA 則估算剩餘時間。三者更新頻率不同。每秒重新跑完整路徑搜尋通常沒有必要；可以先依當前位置與既有路線計算剩餘距離，只有偏航、封路或新路線有明顯優勢時才重規劃。

ETA 可由道路段的預估通行時間累加，再考慮路口轉向、時段與即時交通。若上午 8 點離開 A，預計 9 點才到較後面的路段，不能把所有路段都用「8 點當下」的速度；理想情況要估使用者**到達該路段時**的交通。交通資料稀疏時，歷史同時段速度可作回退值。回覆可以提供 ETA 與可信區間，並記錄最後更新時間。事後用「預測 ETA 與實際抵達時間差」分地區、時段量測誤差，才能知道模型何時失準。

導航還需要 map matching：GPS 點可能落在道路旁的建築或平行高架下方。單點取最近道路可能選錯；利用連續軌跡、前一位置、行進方向和道路連通性較可靠。若位置長時間缺失，畫面應顯示最後定位時間，避免把舊位置當即時狀態。

## 手算一個最短路徑小圖

假設邊權重是分鐘：`A→B=4`、`A→C=2`、`C→B=1`、`B→D=3`、`C→D=8`。從 A 出發，先得到 B=4、C=2；選目前成本最低的 C，把 B 改成 3、D 設為 10；再選 B，把 D 改成 6。最後路線是 `A→C→B→D`，耗時 6 分鐘。這展示 Dijkstra 為何不能第一次看到 B=4 就直接固定 B：經 C 可能更快。若邊權重隨到達時刻改變，則狀態不只包含節點，還要考慮到達時間或使用可處理時間依賴權重的路徑方法。

一個路線回應可拆成 `route_id, road_graph_version, traffic_snapshot_time, polyline, steps, eta_seconds`。導航客戶端只保留一個路線版本；若新的道路圖或封路事件讓某路段失效，重新規劃並替換整條路線，而不是把新舊步驟混接。對道路版本切換做回歸測試：原路線上橋梁被標為封閉，應無法再輸出穿過該橋的路線；若沒有替代路，回覆「無法規劃」比給錯路安全。

### 兩組容易混淆的資料

**地圖圖磚**是給畫面看的圖片或向量資料；**路線圖塊**是給演算法使用的道路節點、邊與連通關係。兩者都能按空間切分，但查詢、快取與更新方式不同。書中的導航服務還區分「路線規劃」與「預計抵達時間」：最短路可能使用較穩定的道路圖，ETA 必須吸收會變動的交通資料。若只畫一個「地圖資料庫」，就無法解釋圖片 CDN、道路圖搜尋及交通更新的負載差異。

## 自學問答：畫面、路線與即時交通

### 1. 經緯度、投影座標、地址與 Geohash 各做什麼？

**答：** 經緯度標示地球位置；投影把球面位置轉到平面，便於地圖顯示與圖磚切分，但會引入形變；地址是人類可輸入的描述，需要地理編碼轉成位置；Geohash 則把空間位置編成便於近似分區與查找的鍵。導航不能把地址當道路節點，須先地理編碼，再把起終點對應到道路圖。Geohash 可縮小附近候選，仍不能取代精確距離或道路連通性判斷。

### 2. 縮放一級為何圖磚約增四倍？這會真的儲存四倍資料嗎？

**答：** 若一個圖磚向水平與垂直各切成兩半，就會變成 `2 × 2 = 4` 個較細圖磚。全球所有區域、所有縮放級別的理論數量成長很快，但無人區或低需求區不一定預先生成全部圖磚，內容也可壓縮或動態產生。容量估算須分清「理論格數」、「實際保存比例」、「每格大小」和「多版本／副本」，不能直接用最高縮放級別格數乘一個平均大小。

### 3. 圖片圖磚和路線圖塊為何分開？

**答：** 圖片圖磚要讓客戶端快速畫畫面，通常可經 CDN 快取；路線圖塊包含道路節點、方向、轉彎限制與邊權重，供路線服務搜尋。新道路通車會改道路圖並觸發圖塊更新，畫面圖磚也可能重製；某條路暫時塞車則主要改變即時邊權重，不必重畫所有底圖。兩者的查詢量、更新頻率與失效方式都不同。

### 4. 使用者導航時，三條主要資料路徑是什麼？

**答：** 地圖顯示路徑是客戶端按視窗和縮放級別取圖磚，CDN 可承擔多數流量；位置路徑是手機定期或批次上傳 GPS 樣本，供當前位置與交通分析；導航路徑是起終點進地理編碼、道路圖搜尋、ETA 計算後回傳路線。若一段路被封，交通／道路變更進入導航更新流程，找出受影響路線並推送新的 ETA 或整條路線。只更改底圖不能讓使用者避開封路。

### 5. 路線封閉時，何時只更新 ETA，何時重規劃？

**答：** 若道路仍可通行，只是速度下降，原路線可能仍最佳；重新計算 ETA，並與替代路線比較。若道路禁止通行，原路線已無效，須從使用者當前位置重算。系統可維持道路段到活躍路線的反向索引，先找受影響用戶，避免對所有導航者重算。更新訊息要帶路線版本與時間，客戶端忽略較舊結果。
