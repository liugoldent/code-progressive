# 12｜數位錢包

## 帳戶餘額是結果，交易流水是證據

數位錢包要支援查餘額、轉帳、充值與提領。先問是否單幣別、能否透支、同帳戶併發轉帳量、強一致讀取需求，以及錢包內轉帳和外部銀行轉帳是否同範圍。餘額是可快取的衍生狀態；完整、不可隨意修改的流水是稽核與重建依據。

## 雙分錄思考

一筆 A 轉 B 的交易應同時記錄 A 的借方變化和 B 的貸方變化，兩邊金額相等、方向相反。也可加入平台清算帳戶、手續費帳戶。每筆交易有唯一 `transaction_id` 和明確狀態。對同一資料庫內的兩個錢包，可在單筆交易中檢查 A 餘額、寫入兩方分錄並更新餘額；鎖定帳戶時按固定 ID 排序，降低死鎖。金額使用最小貨幣單位整數或精確十進位，不使用浮點數直接代表金額。

```text
轉帳請求 → 驗證/冪等鍵 → 原子檢查餘額與記帳 → 提交 → 回覆交易 ID
                                         └→ Outbox → 通知與分析
```

若帳戶分散於不同分片，單筆資料庫交易可能無法覆蓋兩端。可考慮把轉帳經由專門的記帳服務序列化、讓相關帳戶共置，或用暫記/待結算帳戶配合可恢復的狀態機。方案需維持「任何中間狀態都可解釋資金在哪裡」，不能靠兩個獨立 `UPDATE balance` 加上失敗時祈禱補償。

## 重試、重建、對帳

同一 `transaction_id` 重試應回傳同一結果。事件溯源可以由分錄重建餘額，但重播成本與版本演進要設計；常見做法是保留不可變流水，加定期快照或餘額投影，並持續核對。若餘額投影與流水不符，停止有風險的支出操作並調查差異。外部充值、提領要區分「外部已結算」與「本地已入帳」，用懸帳處理不確定狀態。

## 面試深入問題

- A 帳戶只有 100 元，兩筆 80 元轉出同時到達，如何保證不透支？
- 寫入分錄後回覆丟失，客戶重試時如何查到原交易？
- 跨分片轉帳中一端暫時不可用，如何表達待結算資金並恢復？
- 觀測借貸總額不平衡、餘額/流水差異、待結算交易年齡與重複請求率。

## 100 元轉帳的帳本例子

假設 A 轉 100 元給 B，以「帳戶餘額變動」表示時，同一 `transaction_id` 下寫兩筆不可變分錄：A `-10000` 分、B `+10000` 分，總和為 0。若另收 2 元手續費，可再寫 A `-200` 分、平台手續費帳戶 `+200` 分；整筆交易所有分錄總和仍為 0。資料表可用 `ledger_entries(entry_id, transaction_id, account_id, amount_minor, currency, created_at)`，並以 `transactions(transaction_id, client_key, state)` 控制狀態。不同幣別不能直接相加；換匯需要明確匯率與中間清算帳戶。

若 A 只有 100 元，同時收到兩筆 80 元轉出，兩筆交易不能都先讀到「100」後各自扣款。單資料庫可鎖 A 的餘額列，第一筆扣後剩 20，第二筆檢查失敗；也可使用帶版本號的條件更新，失敗時重新讀取。分錄與餘額投影要同一交易提交，否則記帳成功但餘額未更新會造成短暫或永久差異。

## 失敗時怎麼找到錢

跨分片轉帳可用平台內部的待結算帳戶表達過渡：先從 A 轉入待結算，再從待結算轉給 B。每一步都有平衡分錄與狀態，重試以 transaction ID 去重。這不是免費取得原子性；系統需要保證處理程序可恢復、待結算餘額可被監控與對帳。若第二步長時間失敗，資金仍在可稽核的待結算帳戶，營運人員能查明並處理，而非憑空消失。

定期重算每個帳戶的分錄總和並比較餘額投影，抽樣不足以保證全域正確性。若使用快照縮短重算，快照要記錄最後分錄序號，後續只累加更晚的分錄並檢查序號缺口。

## 三個帳戶的完整資金流

假設使用者 A 的錢包充值 100 元，再轉 30 元給 B，平台收 2 元手續費。若外部充值已完成，帳本可先記平台外部清算帳戶 `-100`、A `+100`；轉帳時 A `-32`、B `+30`、平台手續費帳戶 `+2`。兩筆交易各自的同幣別分錄總和都為 0。A 最終餘額 68、B 增加 30、手續費帳戶增加 2。外部清算帳戶如何與銀行實際入帳對上，還要另做對帳，不能因內部平衡就認定外部錢已到。

入帳前檢查交易是否已存在、金額和幣別是否與原請求一致。再鎖定相關帳戶、確認 A 不透支、寫入所有分錄與餘額投影，最後提交。若任何一步失敗，整筆本地交易回滾。外部充值/提領無法與銀行形成單一交易時，把錢放在待結算狀態，等外部證據確定再轉成可支出餘額。

**故障測試：** 在分錄全部寫完但交易未提交、交易已提交但回覆丟失、外部清算成功但本地回呼丟失三點當機。第一種重試可安全重做；第二種用 transaction ID 查原結果；第三種查外部狀態並對帳，絕不可盲目再次充值。

## 自學問答：轉帳的完整性與可重現性

### 1. A=5、C=2，A 轉 C 1 元，哪些不變量要成立？

**答：** 轉前總額為 7；成功後 A=4、C=3，總額仍為 7。驗證時還要確保 A 有足夠餘額、金額與幣別合法、同一請求不重複執行。若只更新 A=4 而 C 仍是 2，總額暫時變 6；若這個中間狀態對外可見或故障後永久留下，就破壞完整交易要求。單資料庫可用原子交易一次更新兩邊；跨分片需明確協調與恢復。

### 2. 為何把兩個帳戶放不同 Redis 分片會造成問題？

**答：** 轉帳服務要向 A 分片扣款，向 C 分片加款；兩個節點各自成功與否，沒有天然單筆原子提交。扣 A 成功後 C 節點當機，客戶看到的可能是少了 1 元，重試又可能再扣。Redis 按帳戶雜湊可擴充吞吐，卻不能只靠路由解決跨分片交易。需用交易協定、可恢復狀態機或能稽核的轉帳中間帳戶，且每步冪等。

### 3. 2PC、TCC、Saga 怎麼比較？

**答：** 2PC 先讓參與資料庫準備，再由協調者統一提交或放棄，原子性直觀，但準備期間可能鎖住資源，協調者故障會造成阻塞。TCC 把 Try、Confirm、Cancel 交給應用程式設計；Try 通常須預留而不是直接暴露不平衡扣款，還得處理 Cancel 先到及重複呼叫。Saga 依序執行本地交易，失敗時做業務補償；中間狀態可能可見，補償也不是時間倒流。選擇依延遲、參與者能力與能否接受暫時狀態而定。

### 4. 為何「收到轉帳命令」不能立刻記成「已轉帳事件」？

**答：** 命令是意圖，可能因餘額不足、格式錯誤或重複請求被拒絕；事件是已驗證且確實發生的事。狀態機先從目前餘額讀狀態，驗證命令，成功才產生 A 減 1、C 加 1 的事件並更新狀態。若把所有請求都當成功事件，重播會產生錯誤歷史。事件一旦確立應不可任意改寫，修正以新的補償或更正事件表達。

### 5. 如何回答「昨天中午 A 有多少餘額」？

**答：** 找到昨天中午之前最近的狀態快照，確認快照包含的最後事件序號，再依序重播其後、截止時間前的事件；若沒有快照，就從初始狀態重播。事件必須有穩定順序、完整歷史和明確的時間語意；同一程式版本或可兼容的演進規則才能重現相同結果。每次查詢都從頭重播很昂貴，所以 CQRS 可維護不同時間粒度的讀取視圖和稽核快照。

### 6. Raft 複製日誌解決了什麼，沒有解決什麼？

**答：** Raft 讓一組節點對事件順序達成共識，主節點故障後由新的領導者繼續，降低單點資料遺失風險。它沒有讓單一群組的寫入吞吐無限增長；若要每秒百萬轉帳，仍需分片。A、C 落不同 Raft 群組時，又回到跨分片完整交易問題，需要 TCC、Saga 或其他協調。複製保護單片內的日誌，跨片守恆是另一層責任。
