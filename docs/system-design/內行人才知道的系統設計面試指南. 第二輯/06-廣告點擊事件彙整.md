# 06｜廣告點擊事件彙整

## 正確性要求先講清楚

輸入是曝光或點擊事件，輸出是按廣告、活動、地區與時間窗口彙整的數字。先問用途：即時儀表板可以接受幾分鐘延遲，計費則需要更嚴格的去重、稽核與對帳。也要區分「收到點擊請求」、「判定有效點擊」與「可計費點擊」。

## 串流處理流程

```text
點擊 API → 持久化事件日誌 → 去重/驗證 → 依事件時間分窗彙整
                                      ├→ 即時查詢資料庫
                                      └→ 原始事件歸檔與批次核對
```

事件至少包含穩定 `event_id`、`ad_id`、`campaign_id`、事件發生時間、伺服器接收時間與必要的來源資訊。客戶端重試、網路重送、處理器重啟都可能讓同一事件重複。去重表可設 TTL，但要與允許遲到的最長時間一致。跨裝置或惡意點擊的判定屬另一層反作弊，不可只靠 event ID 去重。

## 時間窗口與遲到資料

按事件時間統計比按處理時間更符合業務語意，但手機時鐘可能不準且事件會遲到。需定義窗口時區、邊界、允許遲到多久，以及窗口結算後修正數字的方式。watermark 是「系統認為大部分更早事件已到達」的進度訊號，並非遲到事件絕對不會再來。對財務報表可做版本化修正與每日重算；對即時看板可顯示暫定值。

## 聚合與重播

分區 key 依廣告選擇有助同一廣告聚合，但超熱門廣告會成為熱鍵。可先用 `ad_id + salt` 做局部聚合，再合併結果。消費者重播時，更新結果應具冪等性，或把窗口輸出視為某版本的完整替換；單純 `count += 1` 很容易重算重複。保留原始事件與處理版本，才有條件追查數字差異。

## 面試深入問題

- 儀表板顯示 100 次點擊、隔天結算變成 97，產品如何標示暫定與最終數？
- 時區與夏令時間如何影響「每日」報表？可用 UTC 儲存事件，依報表時區切窗口。
- 處理器故障後如何從 checkpoint 恢復，避免漏算或重算？
- 觀測事件延遲、去重率、窗口修正量、積壓量與即時/批次結果差異。

## 一個遲到事件的完整路徑

假設台北時間 10:58 發生點擊，手機離線後 11:07 才送達。若統計以事件時間切每小時窗口，這筆應計入 10:00–11:00；若按接收時間，會落在 11:00–12:00。假設允許 15 分鐘遲到，10 點窗口可在 11:15 初步結算，之後更晚到的事件進修正流程或另列異常。要把「窗口關閉」、「對外報表發布」和「財務最終結算」分成三個時間點。

彙整表可使用 `(campaign_id, ad_id, window_start, dimension_hash, revision)` 作鍵。處理器輸出某版本窗口完整計數，查詢端選最新 revision；若用增量累加，則每次更新必須帶穩定事件或批次 ID 才能去重。原始事件日誌保留足夠時間以便重播，但保留期限也受到隱私與成本約束。

## 兩種結果如何對帳

即時系統追求低延遲，可能使用近似去重或較短窗口；批次系統讀原始事件可做更完整的反作弊與晚到補算。每日對帳比較「原始有效事件數」、「串流結果」和「帳單結果」，差異超過閾值就暫停結算或標記待調查。不要偷偷覆蓋舊報表數字；保留修正版本及原因，讓廣告主能追溯。

若單一廣告短時間暴增，先確認是否正常活動或機器流量，再看該 key 的處理延遲。分片加鹽能降低處理器熱點，但後續合併還是要處理重複與窗口版本。

## 放回廣告業務流程理解數字

在即時競價場景中，廣告先參與展示機會的競價，得標後才可能產生曝光，使用者看到廣告後才可能點擊。點擊事件彙整位於這條流程的**後段資料管線**；它不等於即時競價本身。若某日 100 萬次有效曝光、1 萬次有效點擊，CTR（點擊率）約為 `10,000 / 1,000,000 = 1%`。若 500 次有效轉換，按點擊計的 CVR 約為 `500 / 10,000 = 5%`。分母必須明講：不同報表可能以曝光、點擊或到站訪問作分母。

由於曝光、點擊、轉換可能由不同系統上報，三種事件的延遲、去重規則與歸因窗口也可能不同。即時看板在 10:00 顯示 1 萬點擊，10:05 補入遲到曝光後，CTR 即使點擊數不變也可能下降。計費若採有效點擊，還需反作弊篩選；不能直接把原始點擊 API 請求數拿去收費。報表應列出事件時間、資料更新時間、是否暫定，以及使用的篩選或歸因版本。

**練習：** 兩次完全相同的 `event_id` 到達，另有兩個不同 `event_id` 來自同一使用者在一秒內點擊同一廣告。前者是傳輸重複，後者可能是有效雙擊或無效流量；只靠事件 ID 去重無法裁決後者，需獨立業務規則與稽核紀錄。

## 狀態、checkpoint 與輸出必須能一起恢復

假設串流工作器把 10:00–10:05 窗口計數從 99 更新為 100，接著當機，來源 offset 卻仍停在那筆事件之前。重啟後會再讀一次同一事件。若輸出是 `count += 1`，結果會變 101。可把窗口狀態和來源進度一起放進一致的 checkpoint，並讓輸出以 `(窗口鍵, revision)` 做完整覆寫；若輸出是外部資料庫，也要在同一交易內記錄處理過的批次 ID。重播時檢查版本或唯一鍵，避免再次累加。

窗口鍵不只包括 `ad_id` 和時間，也可能包括地區、裝置、活動等維度。若所有維度都組合，狀態數會快速增加；要先確定報表真正需要哪些維度與粒度。對大量查詢，可預計算常用聚合；臨時多維分析則讀較細粒度事件或分析儲存。越多預計算，寫入放大和晚到修正成本越大。

**自己驗算：** 原始事件有 A、B、B（重送）三筆，B 的 `event_id` 相同。正確有效計數是 2。若先做局部彙整再去重，可能得到 3；因此去重位置必須在會造成不可逆計數累加之前，或讓後續修正能找回原事件。

## 自學問答：讓點擊數可以被驗證

### 1. 每日 10 億筆點擊，平均 QPS 是多少？

**答：** `1,000,000,000 ÷ 86,400 ≈ 11,574` 次／秒。這只是日平均；廣告曝光會隨時區、活動與熱門事件起伏，應另抓峰值倍數及單一熱門廣告的比例。點擊彙整查詢容許的延遲，與即時競價 RTB 決定出價的毫秒級路徑是不同需求，不能把兩者混成一個延遲目標。

### 2. 為何同時保存原始事件和分鐘聚合結果？

**答：** 分鐘表讓「某廣告最近 30 分鐘點擊數」只需讀少數聚合列；原始事件則保留何時、哪個廣告、哪些維度被計入的證據，支援去重、反作弊調查和程式修正後重算。只存原始事件會讓每次查詢掃大量資料；只存聚合數又無法查明多算或少算的原因。原始資料的儲存期、壓縮、存取權限與個資處理成本也須一併估算。

### 3. 10:01 發生的點擊到 10:06 才抵達，算進哪個視窗？

**答：** 若統計依事件時間，應歸入 10:01 所在的視窗，而非 10:06 的處理時間。系統需要決定容許多晚的資料：watermark 尚未越過該視窗時可正常更新；已越過時要選擇補算、發出修正，或依產品規則記為過晚事件。等待越久，初次答案越準但查詢新鮮度越差。對計費報表，常採暫定值加最終校正；不能把第一次顯示的數字默認為永不改變。

### 4. 輸出成功但 checkpoint／offset 尚未保存，為何會重複計數？

**答：** 工作器重啟後會重新讀到尚未確認的來源事件；若上次已把 `count` 加一，這次再加一就多算。修法是讓輸出以聚合鍵和處理位點做冪等覆寫，或讓狀態更新與來源進度在同一交易語意內提交；亦可對穩定 `event_id` 去重。僅在記憶體記「看過了」不夠，當機後會失去該判斷。此處「恰好一次」指**可觀察結果**恰好計入一次，不是網路只傳一次。

### 5. 爆紅廣告占 30% 點擊，增加分區數有用嗎？

**答：** 若按 `ad_id` 分區，這個廣告始終落同一分區，增加其他分區無法分散它。可將熱門廣告再加鹽切成多個局部計數鍵，例如 `(ad_id, shard)`，每個工作器先局部聚合，查詢或下一級工作器再加總。代價是讀取要合併、去重與快照位點更複雜。使用局部批次也能減少每次事件直接寫全域計數的競爭。

### 6. 如何從一個可疑數字追到重算？

**答：** 先找出廣告、篩選維度和時間窗，再核對聚合值與原始事件中的不同 `event_id` 數。若發現多算，定位從哪個來源位點重送、哪次輸出重試；若少算，檢查晚到、解析失敗與死信資料。修正程式後以原始事件重跑到新聚合表，驗證新舊差異，再切換查詢；保留版本和重算時間，避免新舊結果混雜。
