# 04｜分散式訊息佇列

## 需求先於產品名稱

先問它是工作佇列還是可重播事件日誌：多個消費者是分攤工作，還是每組消費者都要看到同一事件？需要保留多久、單分區是否保序、吞吐量與延遲目標是多少？不同答案會決定是否採用分區追加日誌、訊息確認機制與保留策略。

## 分區日誌的基本模型

以下是**可重播分區日誌**的一種模型：一個 topic 分成多個 partition，生產者依 key 選分區；分區內訊息有遞增 offset。broker 把訊息追加到日誌並複寫給其他節點。消費者群組把分區分派給成員，各成員保存或提交已處理的 offset。分區是平行處理和順序保證的單位：同一訂單用同一 key 可保序，但也可能造成熱點。若題目要求的是傳統工作佇列，確認與刪除語意不同，見下節。

```text
Producer → partition leader → 複本確認 → 回覆 offset
Consumer group → 拉取分區 → 處理副作用 → 提交 offset
```

**確認順序決定失敗語意。** 先提交 offset 再處理，當機可能漏事件；先處理再提交，當機重放可能重複副作用。因此消費端要用事件 ID、冪等寫入或交易邊界處理重複。「恰好一次」通常是特定系統範圍內的保證，不能直接延伸到外部支付或 email 服務。

## 運維與擴充

當 broker 故障，選主與複本落後可能影響可用性或資料耐久性；要說明寫入成功需要多少複本確認，以及是否允許落後複本當選。保留政策可按時間或大小；消費者落後超過保留期限會失去可重播資料。分區增加後，若用 `hash(key) % N`，同一 key 可能搬到別的分區，跨舊新分區的順序要處理。慢消費者以積壓量、最舊訊息年齡和處理失敗率監控，不只看每秒吞吐。

## 面試深入問題

- 大訊息應直接進佇列，還是只傳物件儲存的參照？考慮大小限制、生命週期與權限。
- 毒性訊息每次處理都失敗，如何重試、隔離到死信佇列並重新投遞？
- 消費者重新平衡時如何避免兩個實例同時對外寫入？可用租約、世代編號及冪等副作用。
- 監控寫入確認延遲、複寫落後、分區不均、消費延遲與磁碟使用。

**自己練習：** 若每天 10 億事件、每筆 1 KiB、保留 7 天、三副本，先估原始資料與複本容量，再加索引、餘裕與尖峰流量。

## 消費者當機的時序演練

假設消費者讀到 offset 42，將訂單 7 的狀態寫入資料庫後當機，還沒提交 offset。新消費者接手會重讀 42。若處理是 `UPDATE orders SET status='paid' WHERE id=7`，重做較容易安全；若是 `balance = balance + 100`，就可能多加一次。更穩妥的是在同一筆資料庫交易內，先以事件 ID 寫入 `processed_events` 唯一鍵，再執行副作用。重播時唯一鍵衝突表示該事件已完成。若副作用位於外部系統，還要靠外部冪等鍵或對帳。

偏移量與業務資料若分開提交，仍有兩個真實來源。可把「最後已處理 offset」和業務變更寫入同一資料庫交易，或者接受至少一次投遞並使業務寫入冪等。不要只說「開啟 exactly once」卻不說明跨系統的邊界。

## 分區數與容量估算

每天 10 億筆、每筆 1 KiB，原始事件約 1 TB/天；保留 7 天約 7 TB，三副本約 21 TB，還未計入索引、空間預留、壓縮差異和網路傳輸。平均寫入約 `10^9 / 86,400 ≈ 1.16 萬筆/秒`，若尖峰 10 倍便是 11.6 萬筆/秒。若單分區經壓測可穩定處理 5,000 筆/秒，理論下限約 24 個分區，實際要留擴充餘裕並檢查熱門 key 造成的分布不均。

分區越多，平行度越高，但開檔、複本協調、重新平衡和小批次開銷也增加。因此要用實測吞吐、可接受的重新平衡時間與順序需求一起選分區數。

## 重要修正：工作佇列與可重播日誌不是同一件事

對照原書第四章的需求頁，可以看到它討論訊息是否保留、是否能被不同消費者重複消費、以及至少一次／至多一次等可配置投遞語意。因此不應一開始就把題目等同於 Kafka 式事件日誌。先問「一條訊息被成功處理後還能不能再讀」和「兩組消費者是否都要收到它」。

| 問題 | 工作佇列的常見選擇 | 可重播日誌的常見選擇 |
| --- | --- | --- |
| 訊息處理後 | ACK 後刪除或標記完成 | 依保留期限留下，由 offset 決定讀取位置 |
| 多個工作器 | 一條工作通常只由一位工作器處理 | 同一群組分攤，不同群組可各自讀取 |
| 消費失敗 | 可見性逾時後重送 | 不提交 offset，之後重讀 |
| 重播歷史 | 通常不是核心能力 | 是設計目標之一 |
| 順序 | 可能只保證單一隊列或訊息群組內 | 通常只保證單分區內 |

若實作工作佇列，訊息可有 `READY → IN_FLIGHT → ACKED` 狀態。工作器領取後得到短期租約；租約期間其他工作器不會取到它。工作器成功後 ACK；若當機或租約逾時，訊息回到可領取狀態。租約太短，正常工作尚未結束就被重送；太長，當機後恢復慢。長任務可續租，但續租也可能失敗，因此消費端仍需冪等。毒性訊息多次失敗後進死信佇列，保留失敗原因與人工重試方式。

## 投遞語意要從故障點推導

- **至多一次**：可以在交給消費者時就標記完成。重複風險低，但消費者隨後當機可能漏處理。
- **至少一次**：消費者完成後才 ACK。可避免輕易漏掉，但 ACK 遺失或租約到期會重複投遞。
- **恰好一次效果**：需要限定系統邊界。若訊息處理與業務資料在同一資料庫交易，可用去重 ID 和原子提交達到一次業務效果；跨外部 Email、PSP 或其他資料庫時，必須額外協調、冪等或對帳。單憑 broker 的設定不能保證所有外部副作用恰好一次。

**自己推演：** 訊息 M 被工作器 A 領取，A 已更新資料庫但 ACK 回覆丟失；可見性期限到後工作器 B 再次領取 M。列出兩個工作器可能同時活著的時序，說明業務資料庫的唯一鍵如何避免兩次入帳。

## Broker 當機時哪些訊息可以承諾不丟

假設一個分區有主節點 L 與複本 F1、F2。生產者送訊息 M 到 L，L 寫入本機後立刻回覆成功，還沒複寫就當機；F1 被選為新主，M 可能消失。若服務承諾「確認後不因單節點故障而遺失」，就必須等足夠副本持久化後才確認。等待越多副本，寫入延遲與故障時不可用機率可能越高；不能只說「有三副本」就當作確認已安全。

還要定義新主能從哪些複本選：若允許落後複本當選，可提高切換成功率，但可能丟掉已確認訊息。用每個副本的複寫進度與已提交上限追蹤哪些 offset 能對外讀取。消費者只能讀到已提交資料，避免先看到某筆訊息、主節點故障後它又消失。若系統是工作佇列而非日誌，同樣要讓 READY／IN_FLIGHT／ACKED 狀態持久化並在故障後重建。

**故障測試：** 在「主節點本機寫完」、「第一個複本寫完」、「回覆生產者前後」、「消費者 ACK 前後」分別殺掉節點。逐次記錄訊息是否可讀、是否重送、是否違反已承諾的保證。這比只跑正常吞吐測試更能驗證投遞語意。

### 用一條失敗時序驗證 ACK

假設主副本 L 收到 `M`，落盤後回應成功，但追隨副本尚未存到 `M`；L 隨即故障。若把落後的副本升為新主，生產者以為已成功的 `M` 就可能消失。原書因此把「同步副本集合」與「生產者等待幾個確認」一起討論：只調 ACK 而不看誰可以當新主，無法推導耐久性。練習時先寫下產品承諾，再選副本選舉規則與 ACK 條件。

## 自學問答：日誌、消費進度與故障語意

### 1. 「訊息消費完就刪」與「保留日誌、記 offset」差在哪？

**答：** 工作佇列通常由一位工作者取得任務，完成後該任務不再供其他工作者使用；可重播串流把訊息按保留期限存於分區日誌，每個消費者群組自行記錄讀到的 offset。因此分析群組讀過，不會讓計費群組看不到同一事件；計費群組若程式有錯，也能從較早 offset 重算。代價是保留資料佔空間，且消費進度、過期與重播權限都要管理。

### 2. 為何同一分區有順序，整個 topic 卻未必有全域順序？

**答：** 分區內訊息依追加順序取得單調 offset；兩個分區可由不同主節點同時接受寫入，沒有一個共同的先後決定點。若訂單事件必須依序處理，可用 `order_id` 作分區鍵，讓同一訂單落同一分區。若之後改變分區數，簡單的取模路由可能讓同一鍵的**新**事件落到不同分區，遷移期間要設路由版本或切換策略；舊訊息原本的 offset 不會因此變成另一個 offset。

### 3. 工作完成卻未提交 offset 就當機，會怎樣？

**答：** 新消費者接手時從最後已提交 offset 後讀起，可能再次看到同一訊息，所以通常是「至少一次」。若處理結果已寫入資料庫，重做會造成重複，應以事件 ID 建唯一限制或讓輸出寫入冪等。反過來，若先提交 offset 再處理，當機就可能跳過訊息，形成「至多一次」。offset 的提交時點決定失敗語意，不是 API 名稱決定。

### 4. 生產者收到 ACK，就保證永不遺失嗎？

**答：** 要先問 ACK 等待到哪一步。ACK=0 不知 broker 是否收下；只等主副本時，主機故障且落後副本當選，已回覆的訊息仍可能消失；等待同步副本能提高耐久性，但若選舉允許不在同步集合內的節點當主，也會破壞承諾。還要考慮磁碟持久化、跨故障域佈署與副本數。應把「成功」的持久化條件及故障模型明確寫在設計中。

### 5. 為何拉取比單純推送容易控制背壓？

**答：** 消費者知道自己可處理多少，可決定下一次拉取的批量與頻率；落後時，待處理資料留在 broker 日誌，並可觀測 lag。若 broker 無限制推送給慢消費者，可能把消費者記憶體塞滿，需要另設流控、暫停與重試。拉取也有代價：低流量時可能多一些輪詢延遲，需用長輪詢或適當批量調整。

### 6. 延遲關閉訂單的訊息被重送，怎樣不會關兩次？

**答：** 30 分鐘後觸發的訊息只是一個「檢查」指令。處理器讀訂單權威狀態；若已付款或已關閉，直接結束；若仍待付款，使用條件更新把狀態從 `PENDING` 改為 `CLOSED`，並以訂單 ID／事件 ID 去重。延遲佇列負責到時提醒，資料庫狀態轉移才決定是否關閉。這也涵蓋訊息晚到或重送的情況。
