# 11｜支付系統

## 用狀態機描述交易

「付款成功」可能指本地請求被接受、支付服務商受理、銀行授權、扣款完成或商家完成訂單。先問付款方式、是否需要授權後請款、退款、爭議款、幣別，以及本系統和外部支付服務商各自負責什麼。對外狀態應與真實資金流程對應，不可把 HTTP 200 當成最終成功。

## 一個可追蹤的付款流程

```text
訂單 → 建立 payment intent（冪等鍵）→ 呼叫 PSP
     → 記錄 PSP 請求/回應 → 等待 webhook 或查詢 → 更新付款狀態
     → 交易事件 → 訂單確認/通知/對帳
```

`payment_id`、商家訂單 ID、PSP transaction ID 應分開，並設唯一限制。客戶端逾時後重試要帶相同冪等鍵，避免再扣一次；冪等紀錄需覆蓋整個付款結果，而不是只去重 API 請求。PSP webhook 可能重複、亂序或晚到，處理時須驗證簽章、用事件 ID 去重，並檢查狀態轉移是否合法。回呼遺失時用定期查詢與對帳補足，不能只等 webhook。

## 雙寫與不確定狀態

資料庫更新成功、事件發布失敗會讓訂單和後續處理分裂；可用 transactional outbox，在同一資料庫交易中記錄狀態與待發布事件。對 PSP 的網路呼叫無法與本地資料庫形成單一原子交易；逾時時狀態應是「未知，待查詢」，不是直接視為失敗並重扣。退款是另一筆有自身 ID、狀態與冪等性的交易，不是把原付款資料刪掉。

## 安全與營運

盡量用 PSP 的 token 化介面，避免本系統持有原始卡號；敏感支付資料與日誌要按所用法規及供應商規範處理。金額用最小貨幣單位的整數或精確十進位，幣別與匯率版本不可省略。每日比對本地付款、PSP 報表、銀行清算與訂單狀態，差異需可定位、重試或人工處理。

## 面試深入問題

- PSP 扣款成功、本地在記錄結果前當機，如何恢復而不二次扣款？
- 客戶端同時送兩筆相同訂單付款，唯一約束與冪等鍵放在哪一層？
- 退款成功但通知失敗，何者是真實來源？如何補送通知？
- 觀測未知狀態筆數、重複請求、對帳差異、PSP 逾時率與退款完成時間。

## 一筆付款從建立到對帳

假設訂單 `O-17` 應付新臺幣 500 元。客戶送 `POST /payments`，包含 `order_id=O-17` 與冪等鍵 `K-8`。本地資料庫先建立 `payment_id=P-23, amount_minor=50000, currency=TWD, state=CREATED`，唯一約束保證同一訂單不會同時建立兩筆有效付款。呼叫 PSP 時使用穩定的商家交易 ID。若 PSP 回覆逾時，本地狀態變 `PENDING_RECONCILIATION`，之後用同一交易 ID 查詢 PSP，而不是重建新的付款。

PSP 回呼「已授權」時，要核對金額、幣別、訂單、PSP 交易 ID 與簽章，再做合法狀態轉移。若業務需要後續請款，`AUTHORIZED` 不是 `CAPTURED`；訂單何時確認也要依商業規則決定。儲存每一次狀態轉移與外部事件，保留誰在何時改變了什麼。每天把本地 `CAPTURED`、PSP 結算報表和銀行入帳對照；三者出現時間差時標示暫時差異，超過期限再升級處理。

## 失敗矩陣

| 發生點 | 可能後果 | 恢復方法 |
| --- | --- | --- |
| 建立本地付款後、呼叫 PSP 前當機 | 本地有待付款紀錄 | 由工作器以同一交易 ID 繼續 |
| PSP 成功但回覆逾時 | 扣款狀態未知 | 查詢 PSP 或等已驗證 webhook，禁止盲目再扣 |
| 本地確認成功但訂單事件未發出 | 付款與訂單不一致 | Outbox 重送事件、訂單端冪等處理 |
| 客戶重試同一付款 | 可能重複請求 | 用冪等鍵回傳原 payment 狀態 |

所有表格中的恢復流程都要接受「可能晚到、可能重複」。把不確定狀態持久化，比依賴人記得手動查帳可靠。

## 用狀態轉移表拒絕亂序回呼

假設 PSP 先送 `CAPTURED` 回呼，後送較舊的 `AUTHORIZED` 回呼。如果程式只是把每個回呼狀態直接覆寫本地欄位，付款會從已請款退回已授權。應先驗證回呼與同一 `payment_id`、金額、幣別、PSP 交易 ID 匹配，再用狀態機判斷轉移是否合法。

| 目前狀態 | 事件 | 處理 |
| --- | --- | --- |
| `CREATED` | 已授權 | 轉 `AUTHORIZED`，記錄事件 ID |
| `AUTHORIZED` | 已請款 | 轉 `CAPTURED`，記錄結算待核對 |
| `CAPTURED` | 重複已請款 | 依事件 ID 去重，保持 `CAPTURED` |
| `CAPTURED` | 晚到已授權 | 保存原始事件作稽核，不回退狀態 |
| `UNKNOWN` | 查詢證實失敗 | 轉為明確失敗，才允許後續重試策略 |

退款需要自己的 `refund_id` 和狀態，不應把原付款從 `CAPTURED` 改成「從未付款」。一筆付款可有部分退款，因此原付款、已請款金額、累積退款金額和剩餘可退金額要分開。若 PSP 回呼與主動查詢對同一結果有衝突，標記待對帳並保留兩份證據，不靠最後收到的訊息決定資金真相。

**不變量：** 同一商家訂單的有效請款總額不可超過已授權或業務允許的金額；累積已完成退款不可超過可退款的已請款金額。用重複、亂序、逾時三種事件測試這兩條限制。

## 自學問答：每一筆錢與每一個狀態要對得上

### 1. 收款和付款流程的方向有何不同？

**答：** 收款（pay-in）是買家付錢，商家平台取得可用於後續結算的款項；付款（pay-out）是平台將應付金額交給賣家或其他收款方。兩者可能涉及不同 PSP、銀行、時間與合規步驟，不能把「買家扣款成功」直接等同「賣家已收到錢」。設計中要分開追蹤買家支付訂單、平台帳本與賣家付款訂單。

### 2. `checkout_id`、`payment_order_id`、PSP 的冪等 ID 為何分開？

**答：** 一次結帳可能拆成多筆付款，例如不同賣家、不同支付方式或部分付款，所以 checkout 是業務容器，payment order 是一筆待執行支付。PSP 冪等 ID 則確保同一筆支付因網路重試時，外部不重複扣款。資料模型應讓每個 ID 在自己的範圍內唯一，並保存彼此映射。若全都共用一個 ID，會在部分成功、重試或拆單時失去精確判斷。

### 3. 為何不能用二進位浮點數存金額？

**答：** 許多十進位小數在二進位浮點中不能精確表示；加總和跨系統序列化可能產生捨入差異。用最小貨幣單位整數，或精確十進位／字串傳輸並在邊界解析；同時保存幣別。若支援不同貨幣，不能直接把 100 TWD 和 100 USD 相加，匯率、精度與捨入規則也要有版本。金額精確並不能單獨保證付款正確，仍要對帳。

### 4. 使用者看到 PSP 成功頁，後端就能標記付款成功嗎？

**答：** 瀏覽器重導可能被偽造、關閉或在網路中斷時遺失；它適合改善使用者體驗，不應是唯一財務證據。後端應以驗證過的 PSP webhook、主動查詢 PSP 或結算檔確認外部狀態，並檢查付款 ID、金額、幣別與狀態轉移。若 PSP 顯示成功但本地回呼遺失，先保持待確認狀態，經查詢或對帳再更新。不要因 HTTP 逾時就再建立一筆新付款。

### 5. 重試如何做到「至少嘗試一次」，又不造成二次扣款？

**答：** 可重試錯誤放入具退避的重試隊列，超出次數或不可重試時進待調查／死信隊列。每次重試沿用同一業務付款 ID 與 PSP 冪等 ID；本地以唯一約束擋並發的相同請求。若 PSP 已處理但回覆丟失，先查原交易而非換新 ID 再扣。冪等紀錄需保留足夠久，涵蓋客戶和工作器可能重試的時間。

### 6. 帳本、錢包、PSP 三者資料不一致時怎麼辦？

**答：** 帳本保存交易分錄，錢包保存可快速讀的餘額，PSP／銀行保存外部支付狀態；三者更新不是一筆跨系統的原子交易。每日或更頻繁取得結算資料，按穩定交易 ID、金額、幣別及時間窗比對。能判定的差異用安全的補寫／重試修正；不確定或可能涉及真實資金的差異交人工調查，保留每次證據。系統要監控差異筆數和最老待處理時間，不能只依賴客服發現。
