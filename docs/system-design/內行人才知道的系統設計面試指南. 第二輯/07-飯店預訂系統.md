# 07｜飯店預訂系統

## 讀多寫少，卻不能超賣

搜尋飯店、價格與房況的讀取量通常大；真正的預訂寫入較少，但要保證同一庫存不被重複售出。先問庫存單位是「特定房間」還是「房型在每晚的數量」，是否允許超賣，以及價格在搜尋到付款間可否變動。

## 資料模型與流程

一種模型是 `inventory(hotel_id, room_type, date, total, reserved)`。跨 3 晚預訂要同時占用 3 個日期的庫存，不能只檢查入住日。單筆交易內可依固定順序鎖住每晚庫存列，確認 `reserved < total` 後一起更新；或用條件更新並檢查受影響筆數。固定鎖順序有助降低死鎖。若庫存分散在多個資料庫，交易邊界更複雜，宜先按飯店/房型讓相關庫存共置。

```text
搜尋 → 可快取的候選房況/價格 → 使用者選擇
建立預訂 → 冪等鍵 → 交易占庫存 → 暫留狀態 → 支付
                                      ├→ 成功：確認預訂
                                      └→ 失敗/逾時：釋放或補償
```

搜尋頁看到的是近似即時房況，結帳時必須再以權威庫存檢查。暫留房間需有過期時間及後台清理，但清理工作延遲時不能讓庫存永久鎖住。支付回呼可能重複或晚到，預訂狀態機須限制合法轉移，例如 `PENDING → CONFIRMED` 或 `PENDING → EXPIRED`；若逾時後才收到支付成功，需明確退款或人工處理策略。

## 一致性與營運

價格變動要在建立預訂時固定報價版本、稅費與幣別；取消、改期會跨多晚釋放與再占庫存。分散式交易若不能原子完成，須記錄 saga 的每一步及補償結果，不能假設補償必定成功。第三方飯店供應商的庫存是外部真實來源時，本地快取只是查詢加速，最終確認要以供應商回覆為準。

## 面試深入問題

- 最後一間房被兩位使用者同時預訂，資料庫操作如何證明只有一位成功？
- 多晚預訂中第 2 晚不足，如何避免先占住第 1 晚？
- 支付成功但預訂確認回覆丟失，客戶重試時如何找到同一筆預訂？
- 監控超賣數、預訂失敗率、暫留過期量、支付/預訂對帳差異。

## 最後一間房的併發演練

假設 10 月 1 日某房型只剩一間，使用者 A、B 同時按預訂。兩筆交易都先讀到 `reserved=9, total=10`，若各自寫回 `reserved=10` 並回覆成功，就會超賣。可用資料庫條件更新：`UPDATE inventory SET reserved=reserved+1 WHERE ... AND reserved < total`，並要求受影響列數為 1。第一筆成功後，第二筆條件不再成立，必須回覆無房。若是多晚預訂，所有夜晚的更新應在同一交易內；任一夜失敗，就回滾全部。

預訂表可保存 `booking_id, user_id, hotel_id, room_type, check_in, check_out, quote_id, status, hold_expires_at, payment_id`。`quote_id` 鎖定價格與稅費版本；`booking_id` 與客戶冪等鍵建立唯一映射。暫留過期後釋放庫存也要做條件狀態轉移，例如只允許 `HELD → EXPIRED`；若付款已確認，過期工作不可再次釋放。

## 狀態競賽要有裁決點

最難的情況是付款成功回呼與暫留過期工作同時執行。兩者必須競爭同一筆預訂狀態：誰先在權威資料庫完成合法轉移，誰決定後續流程。若 `HELD → CONFIRMED` 先成功，過期工作無事可做；若 `HELD → EXPIRED` 先成功，晚到的付款成功事件應進退款或人工補救，不能把已釋放的房間再確認。這一段說清楚，比只畫「付款成功／失敗」兩條箭頭更能證明沒有超賣漏洞。

## 一次多晚預訂的原子操作

假設旅客訂 10 月 1 日入住、10 月 4 日退房，必須占用 1、2、3 日三晚，不包含退房當日。把三筆 `(hotel_id, room_type, stay_date)` 庫存列按日期順序鎖定，在同一資料庫交易內逐筆檢查 `available > 0`，全部都足夠才扣庫存、建立 `HELD` 預訂與過期時間。任一晚不足就回滾三筆，不留「只訂到兩晚」的半成品。

```text
BEGIN
  以固定順序鎖定三晚庫存
  若任一晚不足：ROLLBACK，回覆售罄
  三晚各占用一間，寫入 booking(status=HELD, expires_at=...)
COMMIT
```

這只是單資料庫下的概念流程；實際 SQL 的鎖、隔離等級與條件更新要依資料庫驗證。預訂重試必須先用 `(user_id, idempotency_key)` 查原 booking，不能重新占三間。若付款等待時間過長，暫留會降低可售庫存；可量測暫留轉換率、平均占用時間與過期釋放延遲，調整暫留期限。

**不變量：** 每晚每房型的 `已確認 + 未過期暫留 ≤ 可售總量`。取消與過期處理都只能釋放自己先前占用的庫存一次；測試重複取消、過期工作重跑和付款回呼晚到時，此式都要成立。

## 自學問答：最後一間房怎麼賣

### 1. 7/1 入住、7/4 退房，要檢查哪幾晚？

**答：** 檢查 7/1、7/2、7/3 三晚；7/4 是退房日，不占 7/4 晚的房。庫存鍵可用 `(hotel_id, room_type_id, stay_date)`。預訂需在一個原子範圍內確認三晚都足夠，並各扣一間；若其中一晚售罄，整個請求拒絕或請使用者改日期，不能只扣成功的兩晚而留下不完整預訂。房型庫存和實際分房號是不同步驟。

### 2. 同一個人按兩次「預訂」，與兩個人搶最後一間有何不同？

**答：** 前者是重複請求問題，使用穩定的 `reservation_id` 或冪等鍵與唯一約束，重試回原預訂結果。後者是併發庫存問題：兩筆不同預訂都可能讀到「剩一間」，必須用條件更新、列鎖或版本檢查保證只有一筆能扣成功。只設前端按鈕禁用不能擋網路重試，也不能擋其他客人。兩種問題要各自處理。

### 3. 兩筆交易都讀到已訂 99／總量 100，會發生什麼？

**答：** 若各自在應用程式讀 99、算 100、再盲目寫回 100，兩張預訂可能都標成功，庫存表卻只顯示 100，形成遺失更新和實際超賣。正確做法之一是資料庫執行 `UPDATE inventory SET reserved = reserved + 1 WHERE ... AND reserved < capacity`，並檢查受影響列數；或鎖住該日庫存列後再驗證。連續多晚須同一交易提交，否則只扣到部分日期。

### 4. 快取顯示有房，但下單時已售罄，怎麼向使用者解釋？

**答：** 搜尋頁的快取只提供「可能有房」的快速提示；真正可售由下單時資料庫的庫存條件決定。若庫存剛被別人搶走，回覆明確的售罄或替代房型／日期，刷新展示快取。若產品要求搜尋頁顯示「保證有房」，就必須對每次瀏覽保留庫存，成本和浪費非常高，通常不採用。

### 5. 預訂與庫存分屬兩個資料庫，為何變難？

**答：** 可能出現「庫存扣了，預訂紀錄沒建立」或「預訂成功，庫存沒扣」兩種不一致；網路逾時時更不知遠端是否成功。2PC 會讓參與者準備與鎖定資源，故障時可能阻塞；Saga 需要明確的補償與中間狀態。若核心預訂與逐日庫存能在同一資料庫交易內更新，原子性比較容易保證。跨服務的付款仍需狀態機與對帳，不能假設本地交易涵蓋外部支付。

### 6. 業務允許超額預訂 10%，是否可以忽略併發？

**答：** 不可以。10% 是明確的業務上限：若原本 100 間，規則上限是 110 張有效預訂，仍須以資料庫條件更新守住 110。競態造成 111 張以上，與刻意設定的超額預訂不是同一回事。取消後釋出庫存、付款失敗回收預留、調整實際房量，都必須遵守同一上限規則。
