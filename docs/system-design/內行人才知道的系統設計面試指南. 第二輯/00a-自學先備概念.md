# 自學先備概念與解題方法

這篇先解釋後面十三題會反覆用到的語言。若你看到「冪等」、「分區」、「最終一致」只會背名詞，先完成這篇再讀案例。所有例子都是本站設計的練習情境，不是原書數值。

## 1. 系統設計到底要回答什麼

系統設計不是把負載平衡、Redis、Kafka 和資料庫排成一列。它要回答：**哪些操作必須正確、哪些操作必須快、系統承受多少量、故障時要守住什麼，以及付出哪些代價。**

用飯店預訂作例子：搜尋頁顯示房間可以有幾秒延遲，因為最後結帳會重查；同一房間不能賣給兩個人，因為這會直接影響交易。這兩個操作即使在同一產品，也需要不同一致性要求。設計時先寫「不可超賣」和「搜尋 95% 在 300 ms 內回覆」等可驗證條件，再選資料結構。

### 功能需求與非功能需求

功能需求描述使用者要做什麼，如「查附近餐廳」、「送出付款」、「取消委託」。非功能需求描述系統如何提供服務，如延遲、可用性、正確性、容量、隱私、可恢復時間。面試時先確認不做什麼：如果只設計地圖路線，就不必同時完整設計街景、廣告與商家後台。

把每題填進這張表：

| 欄位 | 要寫的內容 | 例子 |
| --- | --- | --- |
| 核心操作 | 最常見的讀與寫 | 建立預訂、查房況 |
| 正確性 | 絕對不能錯的事 | 不得超賣、不重複扣款 |
| 新鮮度 | 資料允許落後多久 | 房況搜尋可落後 5 秒 |
| 延遲 | 對外回應目標 | p95 低於 300 ms |
| 故障 | 元件壞掉時的行為 | PSP 逾時時保留待查詢狀態 |
| 規模 | 平均與尖峰 | 每日 1,000 萬查詢、尖峰 10 倍 |

## 2. 容量估算：先算單位，再談技術

平均 QPS = 每日請求數 ÷ 86,400。假設每天 864 萬次查詢，平均是 100 QPS。若晚間尖峰 8 倍，目標至少要處理約 800 QPS，還要留故障切換餘裕。若每次回應 20 KiB，800 QPS 的純回應流量約 16 MiB/s；網路協定、重試與 CDN 命中率會改變實際數值。

儲存量 = 每日新增筆數 × 每筆大小 × 保留天數 × 副本或編碼開銷。假設每日新增 100 萬筆、每筆 1 KiB、保留 30 天、三副本，原始資料約 30 GB，三副本約 90 GB。索引、日誌、備份和空間預留另計。估算的價值是看出「大約幾個量級」，不要假裝早期假設有精確到小數點的意義。

特別注意**平均與熱點不同**：1,000 QPS 平均分到 100 個分區是每區 10 QPS；若某一廣告佔 50% 點擊，單區可能吃下 500 QPS。凡是以 `user_id`、`ad_id`、`symbol` 分區的系統，都要問 key 是否均勻。

## 3. 先找真實來源，再加衍生資料

真實來源是故障後用來裁定狀態的資料。例如錢包的不可變分錄可重建餘額；排行榜的有效比賽紀錄可重建排序索引；物件儲存的 metadata 告訴我們某版本由哪些資料區塊組成。快取、搜尋索引、排行榜和即時看板通常是**投影**，為了查詢速度而存在。

設計一項投影時，逐一回答：

1. 從哪份權威資料建立？
2. 更新事件若重複或漏掉，怎麼發現？
3. 投影遺失時，要花多久重建？
4. 投影落後時，產品顯示時間戳，還是改查權威資料？

若無法回答，快取再快也可能在故障時顯示錯的金額、錯的房況或錯的排名。

## 4. 一致性要對特定操作說清楚

「強一致」的意思不是整個系統所有資料都立即同步。你可以要求同一房型的庫存更新必須原子完成，同時允許搜尋索引晚 5 秒更新。面試要具體說「哪個讀取在什麼條件下必須看到哪個寫入」。

考慮兩個並行請求都想扣最後 80 元，而帳戶只有 100 元。若它們都先讀到 100，再各寫 20，就可能兩筆都回覆成功。解法是讓「檢查餘額＋扣款」形成一個原子操作：資料庫鎖、條件更新或單一序列化處理器都可以；關鍵不是名詞，而是證明第二筆如何看見第一筆已經改變的狀態。

跨服務時很難把本地資料庫與外部 PSP、SMTP 伺服器放進同一筆交易。這時要允許「結果未知」的中間狀態，保留穩定 ID，之後查詢或對帳。把逾時直接當失敗通常會造成重複扣款或重複寄信。

## 5. 冪等、重試與投遞語意

**冪等**指同一個操作執行多次，業務結果仍與執行一次相同。`SET status='paid'` 比 `balance = balance + 100` 容易冪等，但仍須檢查是同一交易及合法轉移。客戶送出操作時帶穩定冪等鍵；服務端保存鍵對應的請求內容、進度與結果。若同一鍵配上不同金額，應拒絕，而非回傳舊結果或建立新操作。

一個典型當機點：消費者已更新資料庫，但還沒確認佇列事件。恢復後佇列重送，消費者會再處理一次。可在同一資料庫交易中以 `event_id` 建唯一紀錄，已存在就跳過副作用。若副作用在外部，必須問對方是否支援相同冪等鍵；沒有的話承認重複風險，並用狀態查詢與對帳處理。

### Outbox 為什麼需要

若程式先更新資料庫、再發布事件，兩步之間當機會留下「資料已改，事件未發」。Outbox 在**同一筆資料庫交易**內寫業務變更和待發布事件；背景工作器再發布事件。工作器可能重複發布，所以消費端仍要冪等。它解決的是本地資料與待發布事件的雙寫裂縫，並不讓外部系統變成同一筆原子交易。

## 6. 快取、分區和佇列各解什麼問題

| 元件 | 主要用途 | 新問題 |
| --- | --- | --- |
| 快取 | 降低重複讀取延遲與後端負載 | 舊資料、失效、熱鍵、快取擊穿 |
| 分區 | 讓資料和工作量橫向分散 | 跨分區操作、熱點、重新平衡 |
| 佇列/日誌 | 平滑尖峰、非同步處理、重播 | 延遲、重複、順序、積壓、保留期限 |
| 複本 | 提高讀取能力或故障耐受 | 複寫落後、選主、成本 |

不要在每題都放四種元件。例如附近朋友若每人只查 100 位好友，先批次讀最新位置就可能足夠；是否需要全域地理索引，要看查詢目標與實測負載。

## 7. 故障演練比「高可用」四個字有用

對每個箭頭問四個問題：請求可能重複嗎？回覆可能遺失嗎？下游可能先成功後逾時嗎？重啟後從哪裡繼續？再找出「已向客戶承諾成功」的時刻。承諾成功之前，資料必須達到所需耐久性；承諾之後，即使某節點當機，也要能查到或恢復同一結果。

用一張簡單時序表記錄：

| 時刻 | 發生的事 | 系統應保存的證據 |
| --- | --- | --- |
| T1 | 收到請求 | request ID、冪等鍵 |
| T2 | 寫入權威資料 | 交易 ID、版本、狀態 |
| T3 | 呼叫外部系統 | 外部請求 ID、目的地 |
| T4 | 收到或未收到回覆 | 原始回覆、逾時標記 |
| T5 | 通知客戶 | 對外狀態與可查詢 ID |

在 T2、T3、T4 任一處插入「程序當機」，看看能否恢復，這就是有價值的自學練習。

## 8. 如何驗證設計真的達標

「服務正常」至少拆成延遲、錯誤、資料正確性與資源成本。p95 是 95% 請求的延遲不超過該值，p99 更能看出尾端卡頓；只看平均值可能掩蓋慢請求。佇列看最舊訊息年齡比只看訊息數更有意義。財務系統要看對帳差異、待確認交易年齡；地理系統看位置過期比例；物件儲存看不可讀物件與修復積壓。

壓測時逐步增加負載，找第一個飽和資源。故障注入時移除單節點、區域、快取或外部供應商，測量服務退化與恢復，而非只看正常路徑的吞吐。

## 自我檢查：先答再展開

1. 每日 864 萬請求、尖峰 8 倍，尖峰約多少 QPS？**答案：約 800 QPS。**
2. 佇列事件更新資料庫後、提交 offset 前當機，會漏處理還是重複處理？**答案：可能重複；需冪等。**
3. PSP 呼叫逾時，能否立即宣告支付失敗並重扣？**答案：不能；遠端可能已成功，需保留未知狀態並查證。**
4. 搜尋索引遺失，要從哪裡重建？**答案：先指出權威資料與完整更新日誌，才能推導重建。**

若這四題能解釋「為什麼」，再進入第一章。
