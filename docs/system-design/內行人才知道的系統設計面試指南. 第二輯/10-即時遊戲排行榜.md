# 10｜即時遊戲排行榜

## 四種讀取，不是一個 Top 10

常見需求包括全服前 N 名、某玩家名次、玩家周圍名次、好友排行榜。還要釐清分數是最高分、累積分還是最近一場；同分如何排序；排行榜按天、週、賽季重置；作弊判定是否先於上榜。

## 寫入與查詢模型

一種實作是以排序集合維護 `player_id → score`，讀前 N 名與玩家名次很方便。但要先有持久化的權威分數與事件來源，避免排行榜記憶體遺失後無法恢復。提交成績 API 帶穩定比賽 ID；若是取最高分，更新應是「只在新分數較高時覆寫」，同一場重試不可重複加分。若是累積分，需先對比賽 ID 去重，再原子增加分數。

```text
比賽結果 → 驗證/防作弊 → 權威成績紀錄 → 排行榜更新事件
查排名 → 排序索引 → 加上玩家資料 → 回傳排名與更新時間
```

## 熱點與一致性

單一全服排行榜若承受極高更新量，可能成為單節點瓶頸。可依賽季/地區/遊戲模式分榜；更大規模可分片儲存分數、批次合併 Top N，但精確的全域名次與「我附近」查詢會更難。若產品可接受數秒落後，可以非同步更新讀取索引；若獎金發放依名次，結算時應在固定截止點使用可稽核快照，而不是讀當下暫定榜單。

同分名次要明確定義：分數相同按達成時間、玩家 ID，或共享名次；不同定義會改變資料結構與分頁。玩家改名不應重建分數索引，可在讀取時補玩家資料。刪除作弊成績需可追溯原始比賽與重新計算影響範圍。

## 面試深入問題

- 100 萬玩家在賽季最後 10 秒大量更新，如何保護寫入與結算？
- 好友排行榜是先取好友再批量查分數，還是為每個玩家預建一張榜？比較好友數與更新成本。
- 週榜何時重置？建新版本榜單並切換讀取，比清空正在使用的榜單安全。
- 觀測更新延遲、排名新鮮度、熱榜寫入量、作弊回滾數與結算差異。

## 先把排序規則定死

假設週榜以最高分排序，同分者以較早達成時間優先。排序鍵需包含 `score DESC, achieved_at ASC, player_id ASC`；最後的玩家 ID 用來讓排序完全確定。若只存分數，平分時的順序可能在不同節點或重建後改變。玩家查看自己附近五名時，可先查到自己的順位，再按順位範圍取前後玩家；若要求「所有同分都共用名次」，資料模型與位次計算就不同，要在需求階段決定。

可以保存 `score_events(match_id, player_id, season_id, score, verdict)` 作權威資料，再把有效最佳成績投影到排序索引。索引遺失時，從事件或權威成績表重建；重建期間可提供較舊快照，並顯示更新時間。若作弊審核將一場成績撤銷，不能只把目前分數設為 0：應重新找該玩家其他有效比賽中的最高分。

## 賽季切換與結算

新賽季開始前建立新的 `season_id`，寫入按比賽完成時間或伺服器接受時間歸屬賽季，避免午夜邊界模糊。舊賽季在截止時封存一份具版本的最終榜單；晚到的比賽結果如何處理要事先公布。發獎流程使用最終榜單版本和冪等獎勵 ID，同一份榜單重跑不能重複發獎。榜單讀取流量和結算工作分開，避免最後幾秒大量查榜拖慢分數寫入。

## 為什麼精確名次難以任意分片

假設全服 1,000 萬玩家分成 10 個分片，每片各自能很快算出前 100 名。合併這十份前 100 名，可以得到全域前 100 名；但若問「玩家 P 排第幾」，只查 P 所在分片的名次不夠，因為其他九片有多少人分數更高仍未知。若要精確全域名次，必須能計算所有分片中分數高於 P 的人數，或維持集中/分層的全域排序索引。前者提高讀取成本，後者增加寫入與同步成本。

若產品只需前 100 名和玩家附近名次，可以把熱門讀取拆成不同索引或查詢路徑；若容許名次延遲幾秒，批次合併比分數每變一次就全域同步便宜。若最終名次決定獎金，結算仍須從權威成績在截止點產生可重現的快照，而不能用暫時落後的近似排名。

**手算：** P 得 900 分，本片有 3 人高於 900，其他九片各有 2 人高於 900，則全域高於 P 的人數是 `3 + 9×2 = 21`，在不考慮同分規則時 P 排第 22。只讀本片會錯報第 4。

## 自學問答：Top 10 容易，任意名次較難

### 1. 排行榜需要支援哪些不同的讀取？

**答：** 至少有全域前十、指定玩家的名次、該玩家附近幾名，以及玩家資料的顯示。前十只需最高分的一小段；指定玩家名次需要知道**有多少人排在他前面**；附近排名需先求他的位次，再取一段有序範圍。若只有一張依使用者 ID 存分數的表，這些查詢成本完全不同。面試時先問清楚榜單是全服、月榜、好友榜或賽季榜，以及同分規則。

### 2. SQL `ORDER BY score DESC LIMIT 10` 為何不能順便解決所有名次？

**答：** 分數索引可很快取最高的少量資料，但問任意玩家 P 排第幾，要知道所有比分 P 高的人數，可能掃大量索引項；若每次查詢重新排序，成本更高。讀取越頻繁，這越不划算。Redis sorted set 維持可更新的有序結構，能直接做分數增量、查名次和依名次取範圍；代價是記憶體容量、持久化與節點擴充要另行設計。

### 3. 四種操作如何對應到排序集合？

**答：** 玩家獲得一分可用 `ZINCRBY leaderboard 1 player_id`；取前十用由高到低的範圍查詢；查 P 的名次用 `ZREVRANK`（回傳通常從 0 起算，畫面名次再加 1）；取得附近玩家先求 rank，再依 rank 前後取範圍。若想同時顯示暱稱與照片，不宜每次改名都重建排序索引，可取出玩家 ID 後批量讀使用者資料。實務上還要處理同分順序與查詢期間分數變動。

### 4. 每個分片只保存前十，能求全域前十嗎？能求任意玩家名次嗎？

**答：** 各分片前十合併後再取前十，可以得到全域前十：某人若連自己分片前十都進不了，就不可能進全域前十。但這些資料不足以知道中段玩家 P 的精確名次，因為其他分片可能各有大量比分 P 高的人。精確名次需對每個分片求高於 P 的數量並加總，或維持額外的全域排序／分數分布索引。分片降低寫入壓力，卻讓全域名次讀取更貴。

### 5. 固定分數範圍與按玩家雜湊分片的主要差別？

**答：** 按分數範圍切分，查某個分數落在哪段容易，但玩家得分跨過邊界時要搬分片，熱門分數區間也可能成熱點。按玩家 ID 雜湊，寫入分布較均勻且同玩家操作落同一片；但全域前十須向各片收集候選，精確名次更須跨片統計。選法取決於最重要的是高吞吐更新、全域名次延遲，還是資料維運簡單。

### 6. Redis 故障或月底切榜時，怎樣不丟榜？

**答：** Redis 可作快速排行索引，但需保有可重建的分數資料和更新紀錄。故障時從持久來源重建排序集合，並確認重播位點，避免漏加或重複加分。切月榜可用不同榜單鍵／版本，讓新舊榜並行一段時間，讀取入口明確選版；若名次涉及獎勵，應以截止點的權威紀錄產生可重現的最終榜。這些是把原書的持久化與快取討論轉成實作檢查點。
