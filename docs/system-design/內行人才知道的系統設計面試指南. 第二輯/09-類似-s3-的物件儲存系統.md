# 09｜類似 S3 的物件儲存系統

## API 語意比磁碟種類重要

物件儲存提供以 bucket/key 存取資料的介面。先確認物件大小、上傳/下載 QPS、是否需要版本控制、覆寫後讀取的一致性、列舉語意、跨區複寫與耐久性目標。API 可能包含 PUT、GET、HEAD、DELETE、LIST 與多段上傳；它不是一般檔案系統，通常不提供任意位置原地修改。

## 分開中繼資料與位元組

```text
Client → API/授權 → 中繼資料服務（bucket、key、版本、狀態、位置）
               └→ 資料節點/區塊 → 複本或抹除碼 → 背景校驗與修復
```

資料可切成區塊，以複本或抹除碼分散到不同故障域；中繼資料記錄每個版本的區塊位置、大小、雜湊和生命週期。寫入應有暫存與提交階段：先可靠存放資料，再把該版本發布為可讀，避免讀者看到半套物件。多段上傳的未完成區塊需要定期清理。資料區塊不可只依單台機器的「寫入成功」就向客戶確認；需按耐久性目標等待足夠副本或編碼片段落盤。

## 耐久性、一致性、可用性

複本簡單、讀取快，但儲存開銷高；抹除碼節省容量，修復與小讀取可能需要更多網路和計算。定期做 checksum 驗證與反熵修復，處理靜默資料毀損。跨區複寫若非同步，區域災難可能失去尚未複寫的近期版本；應明講 RPO。覆寫與刪除要定義版本語意，尤其是舊快取、LIST 結果與 GET 之間可能短暫不同步。

## 成本與安全

熱門下載走 CDN，但私有物件需要簽名 URL、短有效期和存取權限檢查。容量不是唯一成本：請求數、出站流量、跨區複寫、資料修復都可能更貴。分層儲存可把冷資料移至低成本層，但要告知讀取延遲與恢復費用。加密金鑰管理與稽核日誌要和物件版本、租戶隔離相容。

## 面試深入問題

- 物件寫入成功後立即 GET 卻找不到，根因可能在資料、metadata、路由或快取的哪一層？
- 某資料節點故障，如何判定修復優先級與避免修復流量壓垮線上讀取？
- 超大物件上傳到 80% 斷線，如何續傳並驗證完整性？
- 觀測資料不可讀率、校驗錯誤、修復積壓、跨區複寫落後與每 GiB 成本。

## PUT 與 GET 的具體時序

PUT 可先由 API 驗證權限、配額與物件大小，產生上傳 ID；資料切塊後寫入足夠的資料節點並驗證 checksum；最後中繼資料服務原子發布 `(bucket, key, version)` 指向那些區塊。若資料已落盤但中繼資料提交失敗，區塊成為孤兒，由背景清理；若中繼資料先發布而區塊還沒可靠存好，讀者可能得到不可讀物件，因此提交順序很重要。GET 先驗權限並取得版本與區塊位置，再讀取資料、校驗 checksum，失敗時可嘗試其他副本或重建。

中繼資料表可有 `bucket_id, object_key, version_id, size, checksum, storage_class, state, created_at`；區塊位置可獨立儲存，避免物件列表查詢讀取大量節點資訊。LIST 需要按 bucket/key 有序索引；若 namespace 很大，前綴分片與游標分頁比一次掃完整個 bucket 更重要。對象名稱可包含斜線，但那通常只是 key 的字元，不能直接當成本機目錄階層。

## 複本與抹除碼的算例

假設 1 PB 原始資料，三副本需要約 3 PB 原始儲存空間；若使用 10 個資料片加 4 個同位片的抹除碼，理論資料開銷約 `14/10 = 1.4`，約 1.4 PB。這未包含索引、空間碎片、暫存和故障修復餘裕。抹除碼在冷資料上有吸引力，但讀取或修復缺失片段可能需要跨節點傳輸更多資料。可把近期熱物件先複寫，後續轉冷時再編碼；轉換期要同時記錄兩種布局與確認清理時機。

最重要的驗證是故障注入：拔掉一台節點、整個機櫃或一個區域，測量有多少物件仍可讀、修復需多久，以及故障期間新寫入是否仍達到耐久性要求。

## 版本、覆寫與刪除標記的手推流程

假設 `photos/a.jpg` 現有版本 V1。使用者覆寫新照片時，不直接原地改 V1 的區塊；先把 V2 區塊可靠存好，再把目前版本指標切到 V2。讀者若在切換前開始讀 V1，應拿到完整 V1；切換後開始讀則拿到完整 V2，不能混到兩個版本的區塊。若開啟版本控制，V1 仍可按版本 ID 讀取；若未保留舊版，背景清理要等確認無讀者、無複寫或恢復需求後才刪。

刪除可寫入新的刪除標記，而不是立即抹掉所有舊區塊。這讓 LIST 與不指定版本的 GET 看起來已刪，但有權限的版本讀取仍可能拿到舊版；是否允許由產品語意決定。生命週期政策、保留鎖定與跨區複寫也要理解版本，否則一個區域的刪除可能在另一區晚到並覆蓋較新的寫入。每個變更需有版本 ID 或可比較的序號。

**故障測試：** V2 只寫好一半時當機，GET 應仍拿完整 V1；V2 區塊寫完但指標切換失敗時，GET 也拿 V1，孤兒區塊由清理程序回收。若指標已切 V2、某資料節點隨後故障，應能從剩餘複本或編碼片段讀 V2。

## 自學問答：從 PUT 到安全的 GET

### 1. 為何不能只拿「總容量 ÷ 平均物件大小」當流量估算？

**答：** 這最多粗估物件數，不能推得每秒 PUT／GET。相同 100 PB 可以是大量幾 KB 小檔，也可以是較少的大檔，詮釋資料量與讀寫型態完全不同；存取熱度、保留期限、版本數與副本也會改變負載。容量估算至少分開：物件數、平均與尾端大小、每天新增／覆寫／刪除數、讀取 QPS、尖峰流量及耐久冗餘。

### 2. `GET bucket/key` 怎樣找到真正的 bytes？

**答：** API 先驗證權限，再以 bucket/key 查詮釋資料，得到目前版本的內部 object ID；放置資訊將 object ID 對應到副本或糾刪碼區塊所在節點。若小物件被打包，還需 object ID → 資料檔、位移與長度的映射，最後取 bytes、核對校驗和並回傳。這三層名稱不能混成同一鍵，因為覆寫名稱時可指向新 object ID，而舊版本 bytes 仍保留。

### 3. bytes 已上傳但詮釋資料尚未提交，GET 能看到嗎？

**答：** 一般不應看到半成品。上傳過程先把 bytes 放到暫存或尚未公開的位置，待副本／區塊達到持久化條件，再原子發布詮釋資料中「目前版本指向新 object ID」的映射。若發布前當機，舊版仍可讀，新 bytes 成為待清理的孤兒；若發布後當機，GET 應能定位到已保存的 bytes。此順序決定了 PUT 成功與 GET 可見的契約。

### 4. 小物件為何要打包？打包後怎麼避免指錯位移？

**答：** 每個幾 KB 物件若各佔一個檔案，檔案系統 inode、開檔和碎片成本可能遠超內容本身。可把小物件附加到大資料檔，另保存 `(object ID, file ID, offset, length, checksum)`。寫入時先確保資料段完整，再提交映射；讀取映射時取得同一版本的檔案與位移，核對長度及 checksum。清理和重新打包後要原子切換新映射，舊資料等沒有讀者使用時再回收。

### 5. 分段上傳 8 段只到 7 段，正式 GET 應看到什麼？

**答：** 不應看到新的部分物件；若原本有舊版，仍讀舊版。每段以 upload ID 和 part number 暫存，完成請求要核對所有指定片段、順序、長度及校驗資訊，組合成功後才發布正式 object ID。未完成片段設到期清理；完成請求重試時須能辨識同一次 upload，避免重複生成不可見垃圾或錯誤覆寫。

### 6. 複本與糾刪碼要怎麼選？

**答：** 三副本讀寫和修復直觀，空間大約需原資料三倍；糾刪碼用資料片加校驗片，常節省空間，但小寫入、讀取與故障修復可能需更多計算或跨節點傳輸。應依物件大小、熱度、延遲與故障域選擇；常見做法是熱或小物件先用副本，較冷且較大的資料再轉成糾刪碼。無論哪種，還要定期校驗與巡檢，冗餘本身不能防止靜默損壞。
