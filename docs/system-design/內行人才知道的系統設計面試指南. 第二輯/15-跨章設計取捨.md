# 跨章設計取捨與故障對照

讀完十三章後，不要只記住「某題用某技術」。更有用的能力是看到新題目時辨認它屬於哪一類正確性問題。以下比較是本站自行整理的學習工具，不是原書原表。

## 十三題的真實來源與最危險錯誤

| 案例 | 用來裁決的資料 | 最容易被忽略的錯誤 | 優先驗證 |
| --- | --- | --- | --- |
| 附近的場所 | 場所主資料與索引版本 | 格子邊界漏結果、搬遷後重複 | 精確距離與索引更新延遲 |
| 人在附近的朋友 | 最新分享權限與有效位置 | 撤銷分享後仍顯示舊位置 | 權限生效時間與 TTL |
| Google 地圖 | 版本化道路圖與交通觀測 | 舊圖磚混新路網、ETA 偏差 | 路線可達性與 ETA 誤差 |
| 分散式訊息佇列 | 持久訊息、ACK/offset 狀態 | ACK 遺失造成重送、過早 ACK 造成漏訊 | 投遞語意與復原測試 |
| 指標監控 | 原始或保留期內的時序樣本 | 缺資料被看作健康、標籤爆炸 | 收集落後與活躍序列數 |
| 廣告點擊 | 原始事件及有效性裁決 | 遲到、重複、計費數與看板數混淆 | 對帳差異與修正版本 |
| 飯店預訂 | 權威庫存與預訂狀態 | 最後一間超賣、付款晚到 | 條件更新與狀態競賽 |
| Email | 原始信件與每收件者投遞狀態 | 遠端已收卻被當成失敗重送 | 不確定投遞與退信率 |
| 物件儲存 | 版本 metadata 與資料區塊 | metadata 已發布但區塊不可讀 | checksum、修復與發布順序 |
| 遊戲排行榜 | 有效比賽成績 | 作弊成績撤銷後無法回到次高分 | 排序索引可重建性 |
| 支付 | 本地交易紀錄與 PSP 結算資料 | 逾時後二次扣款 | 冪等鍵與對帳差異 |
| 數位錢包 | 不可變分錄與交易狀態 | 雙邊帳不平、併發透支 | 分錄平衡與餘額重算 |
| 證券交易所 | 有序命令日誌與成交事件 | 雙主撮合、撤單超越先到委託 | 序號連續與重播一致 |

## 容易混淆的五組概念

### 1. 快取命中與資料正確

快取命中率高，只能說減少了回源，不能證明顯示正確。附近場所可容忍短暫的舊名稱；飯店最後一間房和錢包餘額的裁決不能依舊快取。每次加快取前問：**使用者會拿這個值做什麼決定？** 若涉及付款、權限或不可逆操作，提交前要回到權威資料核對。

### 2. 訊息已送達與業務已完成

broker 回覆生產者，表示訊息達到該 broker 的確認條件；消費者 ACK，表示它宣稱處理完成；業務資料庫提交，才代表業務效果已保存。三個事件可能在不同時刻發生。畫時序時逐個標記，不要用一個「成功」覆蓋全部。

### 3. 冪等與不會重複收到

冪等允許重複請求，但讓重複不再產生新的業務效果。它不代表網路、佇列或 webhook 絕對不會重複。付款、錢包與訂房都需要穩定操作 ID、請求內容比對、唯一約束和可查詢的原結果；只在前端把按鈕停用，不是完整冪等設計。

### 4. 耐久性與可用性

物件有三份副本不代表目前一定可讀：路由、metadata 或權限服務失效仍會使 GET 失敗。反過來，快取能在資料庫故障時回覆舊資料，也不代表新寫入具有耐久性。要分別測「資料會不會永久失去」與「現在能不能服務請求」。

### 5. 全域順序與局部順序

訊息佇列通常只需某個 key 或分區內順序；聊天室常要求單一會話內順序；交易所則要對**同一商品**的送單與撤單建立確定順序。全世界所有事件用一個序列化點，會造成巨大瓶頸。先指出需要比較先後的操作集合，再選合適的序列化邊界。

## 對陌生題目套用的推導順序

假設題目變成「設計演唱會售票」。你可以不用背另一張架構圖，而依序問：票是指定座位還是一般區？超賣可否接受？暫留多久？付款逾時怎麼辦？若票務庫存與付款分屬不同系統，兩者之間如何以狀態機處理？這些問題分別借用飯店預訂、支付系統與訊息佇列的模型。

再假設題目變成「附近朋友一起玩的即時遊戲」。位置分享權限與 TTL 借用第二章，排行榜的可重建排序索引借用第十章，即時事件投遞借用第四章。每個子系統可以容忍不同落後時間；不需要把整個產品設成同一種一致性等級。

## 最終自測

任選一個沒在本書出現的產品，例如線上排隊、外送配送或共享單車。寫出：

1. 哪項資料是權威來源，哪些只是快取或投影？
2. 哪兩個操作可能並行競爭同一資源？
3. 哪個外部呼叫可能「已成功但本地逾時」？
4. 哪種資料允許落後，哪種權限或資金狀態不能落後？
5. 插入一次當機與一次重複事件後，如何恢復到可解釋狀態？

若能用具體資料列、事件 ID 和時序回答，而不只是說「加 Redis／Kafka」，就已能把十三章的方法轉到新題目。
