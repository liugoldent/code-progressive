# 05｜指標監控警報系統

## 先定義監控對象

指標是帶時間戳、名稱與標籤的數值樣本，例如 `http_requests_total{service="api",status="500"}`。面試需問收集間隔、保留期限、查詢粒度、警報延遲與多租戶隔離。監控系統本身在故障時仍需可用，否則最需要警報時反而失明。

## 收集到查詢

```text
應用/主機 → Agent 或拉取器 → 驗證與緩衝 → 時序資料庫
                                            ├→ 規則評估 → 警報路由
                                            └→ 查詢 API → 圖表
```

拉取模式讓中心控制目標與間隔，但短生命週期工作需服務發現；推送模式適合無法被中心連入的環境，但要節流與身分驗證。時序資料庫通常按時間切塊、壓縮，並用標籤索引找序列。舊資料可降採樣，例如近期保留 10 秒粒度，長期保留每分鐘摘要；但最大值、分位數不能任意由平均值再推回。

## 高基數是成本陷阱

把 `user_id` 或 `request_id` 放進指標標籤，會產生大量獨立時序，記憶體與索引成本可能暴增。高基數細節較適合追蹤或日誌，指標標籤應限制在可控集合。counter 可能因程序重啟而歸零，計算速率要處理 reset；gauge 表示某時刻值；histogram 可彙總延遲分布，單看平均會掩蓋尾端延遲。

## 警報設計

警報應對使用者影響或可操作的症狀負責，例如錯誤率與延遲 SLO；對每個 CPU 小波動都通知會造成疲勞。規則評估要考慮資料延遲與缺失：沒有樣本不等於健康。使用持續時間門檻、防抖、同類去重、維護時段與升級路由。警報狀態與通知副作用分離，避免規則重算時反覆發送。

## 面試深入問題

- 每台主機每 10 秒上報 1,000 條序列，10 萬台主機的寫入速率是多少？如何分片？
- 某分片當機，如何讓查詢回覆「部分資料缺失」而非看似正常的 0？
- 監控系統自己的監控如何建立？可用外部探針與不同故障域的檢查。
- 觀測收集成功率、樣本延遲、活躍序列數、查詢 p99 與警報誤報率。

## 指標量級怎麼算

假設 10 萬台主機，每台每 10 秒產生 1,000 個樣本，則平均寫入約 `100,000 × 1,000 / 10 = 1,000 萬樣本/秒`。若每個壓縮後樣本粗估 16 bytes，僅樣本本身約 160 MB/秒、每天約 13.8 TB；標籤索引、副本和查詢暫存還會增加成本。這個估算先幫助判斷需要水平分片，再透過實際壓縮率和活躍序列數修正。

時序數量不等於樣本數。若某指標有 `region=3`、`service=100`、`status=5` 三種標籤，最多可能形成 1,500 條序列；再加 `user_id=100萬` 會讓數量爆炸。標籤的組合乘法比單一標籤數更值得檢查。新指標上線時可設 cardinality 預算及拒收或降採樣策略。

## 警報規則範例

假設 API 的五分鐘錯誤率高於 5%，且每分鐘至少 100 次請求，連續 10 分鐘才警報。請求量門檻避免低流量服務「1 次失敗／1 次請求」被當成大故障；持續門檻避免瞬間尖峰造成噪音。另一方面，若服務完全沒有流量，錯誤率可能無法計算，應有獨立的心跳或外部可用性探針。警報解除也可用不同門檻，例如錯誤率低於 2% 持續 10 分鐘，防止狀態反覆跳動。

警報事件應保存規則版本、判斷時間、樣本範圍與通知紀錄，讓事後能解釋「為何當時通知」或「為何漏報」。

## 時序儲存的寫入與查詢路徑

收集器拿到一批樣本後，可先把資料寫入預寫日誌（WAL），再放入記憶體中的活躍時序；背景程序把較舊樣本整理成按時間切塊的壓縮檔。若程序在資料仍只在記憶體時當機，可由 WAL 重播。查詢過去一小時，先依標籤索引找到序列，再讀需要的時間區間；查詢一年趨勢則優先讀降採樣資料，避免掃所有原始樣本。WAL、壓縮區塊與長期儲存都有保留與故障恢復成本。

用 counter `requests_total` 計算每秒請求數時，應取一段時間內的增加量除以秒數，並處理程序重啟歸零。若 10:00 是 100、10:01 是 160，該分鐘平均約 1 次/秒；若 10:02 變成 5，不應算出負速率，而要辨認 reset。若要估 p99 延遲，不能拿各節點 p99 簡單平均；不同節點的請求量不同，應使用可合併的分布資料或在原始層彙整。這是分散式監控常見的數學錯誤。

**故障測試：** 停掉一台收集器、重啟一台應用、讓一個分片落後 10 分鐘。圖表與警報應明確呈現資料缺失，不能把空值補成 0 後宣稱服務健康。

## 自學問答：從樣本到可採取行動的警報

### 1. 指標名稱為何不等於一條時間序列？

**答：** 一條序列由指標名稱與一組標籤值共同識別。`cpu_usage{service="api", host="a"}` 與 host=b 是兩條序列。若有 100 個服務、每個 20 台主機、每台 8 核，單一指標若加上服務、主機、核心標籤，就可能有 `100 × 20 × 8 = 16,000` 條序列。再把使用者 ID 或請求 ID 放進標籤，基數會急劇膨脹，影響索引、記憶體與查詢時間；這類高基數資訊通常放日誌或 trace 更合適。

### 2. 拉取與推送收集各會漏掉什麼？

**答：** 拉取由收集器按固定間隔向端點取樣，易掌握目標和失敗率；短於收集間隔就結束的工作可能完全沒被抓到，收集器故障也會留下空洞。推送讓工作負載自行送樣本，短命任務較容易被記錄，但出口堵塞時必須有本地緩衝、限流與重試，否則資料會丟或拖慢業務。服務發現解決「該抓誰」，不能解決資料缺口；儀表板應能辨識缺資料與真實數值為零。

### 3. 10 秒樣本降成 1 分鐘，會失去什麼？

**答：** 若只存一分鐘平均，某 10 秒內 CPU 達 100%、其餘 50 秒為 0%，會顯示約 16.7%，尖峰被掩蓋。降採樣時可保留平均、最大值、樣本數等摘要，仍不等同保留完整原始序列。容量估算須分層：高解析度保留短期供排障，低解析度保留長期趨勢。警報若依短暫尖峰觸發，應在原始資料尚在時評估，不能只看長期降採樣資料。

### 4. 監控資料進入佇列後，警報為何不能直接由佇列訊息觸發？

**答：** 多數警報是時間窗條件，如「過去 5 分鐘錯誤率持續大於門檻」，需聚合多條序列、處理缺樣本與延遲。資料先寫入時序庫或流式狀態，規則引擎定期評估並記錄警報狀態；通知服務再負責抑制、去重、升級和重試。把規則判斷與通知發送綁在一起，簡訊供應商故障就可能拖慢樣本處理；兩者拆開才能分別擴充和恢復。

### 5. 通知發送失敗後，如何避免既漏報又狂重送？

**答：** 警報事件要有穩定 ID 和狀態，例如待發送、已送出、已確認。通知工作器以該 ID 重試，對提供冪等 API 的通道傳相同鍵；若外部通道不支援，就要接受極少量重複並在本地限制重送。相同根因的警報可分組，維護中的服務可抑制，長時間未恢復再升級。還應監控「規則觸發到通知送達」的延遲，不只看規則引擎是否運行。
