# 02｜人在附近的朋友

## 先界定「朋友」和「附近」

需求通常是展示同意分享位置、目前在線且距離使用者一定範圍內的朋友。位置比場所資料變動快，也涉及隱私。需要確認雙向好友或單向追蹤、隱身模式、位置分享期限、位置更新頻率，以及「附近」是否接受數秒至數分鐘的延遲。

## 一條可行的資料流

```text
手機定位 → 位置寫入 API → 驗證授權與節流 → 最新位置儲存（TTL）
                                             └→ 位置變化事件
開啟頁面 → 好友清單 → 批次讀好友最新位置 → 過濾分享權限/TTL/距離
```

如果好友數很少，**先取好友再算距離**通常比對全世界活躍使用者做地理搜尋便宜。若每人有幾十萬追蹤者、或產品要找附近所有公開使用者，才更需要地理索引。這是依查詢集合大小選架構，不是看到地理位置就先建全域空間索引。

位置資料可存 `user_id, lat, lon, accuracy, observed_at, expires_at, visibility_version`。位置寫入與心跳要區分：使用者不移動時，不必每幾秒覆寫相同座標。可設定最短時間或最小移動距離上傳門檻，降低電池和網路消耗。伺服器仍需拒絕過舊位置，避免手機離線後把舊座標覆蓋新座標。

## 隱私與一致性

關閉分享、解除好友或封鎖後，讀取路徑應以最新權限為準；不要只依快取中的舊好友關係顯示精確位置。對方的位置精度可降至「約 1 公里內」，並限制查詢頻率，降低追蹤風險。TTL 到期應視為未知，不應把最後位置永久呈現為目前位置。推播「某朋友靠近」需要防抖與冷卻時間，避免人在距離邊界來回移動時大量通知。

## 面試深入問題

- 如何在多裝置定位衝突時選較新的可信座標？比較事件時間與伺服器接收時間。
- 使用者突然撤銷分享權限時，WebSocket 已推送到別人的資料如何處理？可停止後續推送並縮短資料有效期，但無法收回已看到的內容。
- 若每秒有大量位置更新，是否每次都需要更新好友的畫面？可按可見頁面與距離變化合併更新。
- 監控過期位置比例、每人上傳頻率、權限拒絕率與附近查詢延遲。

**自己練習：** 對「平均 100 位好友」及「平均 10 萬位好友」各畫一種查詢策略，說明何時由批次讀取改成地理索引或預計算。

## 用數字決定查詢方式

假設 1,000 萬活躍使用者，每人平均 100 位好友，每人每分鐘送一次定位，平均位置寫入是 `10,000,000 / 60 ≈ 16.7 萬次/秒`，這比每秒幾千次的附近查詢更可能先成為瓶頸。因此先做手機端節流、變化門檻及伺服器合併寫入，再討論複雜地理索引。若每次附近查詢只需批量讀 100 個好友的位置，即使其中大多數已過期，計算仍相對可控。只有當好友數或附近查詢量成長到不可承受時，再轉向格子索引或預先計算。

可把好友集合與位置版本分開快取。關係變更需立即讓讀取路徑重新檢查權限；位置落後可以容忍數秒。這說明同一個 API 內的兩類資料，一類要求較強一致性，另一類重視低延遲與省電。不要把兩者統一設成「最終一致」而忽略封鎖後的位置曝光。

## 走一遍撤銷分享的故障情境

1. A 正在向好友 B 分享位置，B 的畫面每 10 秒刷新。
2. A 取消分享，權限資料庫提交新版本；清除權限快取並發布失效事件。
3. B 再查詢時，伺服器先檢查權限版本，再讀位置。即使舊位置仍在 TTL 快取，也不得回傳。
4. 若快取失效事件延遲，系統仍須靠短 TTL 或權威權限查詢限制暴露窗口；應量測撤銷生效延遲。

推播模式下，伺服器還要從 B 的訂閱集合移除 A。若 B 斷線後重連，重新建立訂閱時必須重新檢查權限，不能沿用舊連線狀態。

## 為什麼這題與附近場所不一樣

場所位置通常變動慢，朋友位置可能數十秒更新一次。若照第一章的方法把每次定位都寫入永久地理索引，寫入、索引搬格與快取失效成本會很高。可把「最新位置」放在具 TTL 的快速儲存，把較少用的歷史軌跡放在另一條受控資料管線。是否真的需要歷史資料，應先由產品需求與隱私設定決定；只做附近好友列表時，長期保存每個人的精確軌跡沒有必要。

即時推送也應按**可見性**節流。使用者 B 沒有開啟附近頁時，A 每次移動不一定要立即送到 B；B 開啟頁面可先拉一次最新狀態，再訂閱變化。伺服器端可只在「跨過距離門檻」、「移動超過一定距離」或「更新間隔已到」時發送變化。這不只節省網路，也降低手機背景耗電。

對 5 公里半徑的篩選，手機 GPS 精度若是 100 公尺，顯示「4.98 公里」會給人不必要的精確感。距離邊界可設遲滯區間：例如進入 4.9 公里內才出現、離開 5.1 公里外才消失，避免定位噪聲讓好友反覆跳進跳出。這是產品穩定性與精確性的取捨，練習時要把定位誤差納入需求。

## 位置更新要有時間與版本語意

手機可能離線後補送舊定位。例如 A 在 10:01 位於甲地、10:02 位於乙地，但乙地資料先到，甲地資料因重試在 10:03 才到。若伺服器無條件採最後**收到**的一筆，A 會瞬間「移回」甲地。可為定位附 `observed_at`、裝置 ID、遞增 sequence 與精度，並建立接受規則：同一裝置只接受較新的 sequence；跨裝置時用伺服器時間與可信觀測時間的界限選擇。過舊或未來時間過遠的樣本應拒收或隔離。

```text
收到定位
→ 驗證是否仍允許分享
→ 檢查時間戳與裝置 sequence
→ 只在版本較新時覆寫最新位置
→ 若距離或可見性有實質變化，發布更新事件
```

若 A 撤銷分享，伺服器應先提高權限版本，再處理任何晚到定位；否則舊裝置的重試可能把位置重新寫回可見集合。設計不變量是：**任何查詢只要看到撤銷後的權限版本，就不會回傳 A 的座標**。用測試同時送「撤銷分享」與「舊定位重試」，確認結果不依抵達順序洩漏位置。

### 書中估算的使用方式

上述人口、好友數與更新頻率都是架構推導的**情境假設**，不是服務現況。計算更新量時先釐清「每日使用者」和「同時在線使用者」的差別：若同時有 1,000 萬人、每 30 秒各上傳一次，才是約 `10,000,000 / 30 ≈ 333,333` 次／秒；若同時在線數改成 1 億，結果就是約 333 萬次／秒。書中還藉好友通知扇出討論更高的發送量。實際面試應先問有多少人真正開啟即時頁面、上傳是否因移動而節流、平均與熱門帳號的好友分布，否則直接把每次更新乘以全部好友數會高估網路推送，卻可能低估熱門帳號的局部熱點。

## 自學問答：從位置更新到朋友看到結果

### 1. 更新量和通知量如何分開估？

**答：** 更新量看同時啟用定位的人數除以上傳間隔。例如同時 1,000 萬人、30 秒一傳，約 33.3 萬次更新／秒；改成 60 秒，更新量約減半。通知量還要乘「真正訂閱且在線的朋友數」，不能直接乘總好友數。若平均 400 位好友、其中 5% 正在看附近列表，理想化上界約為每次更新推給 20 人；實際還受距離過濾、位置未變、上傳節流影響。熱門帳號須另估極端扇出。

### 2. WebSocket、Redis 最新位置、Pub/Sub 各負責什麼？

**答：** WebSocket 保留瀏覽器／手機與連線服務之間的雙向通道；最新位置快取保存每人的座標、時間與到期時間，讓重連者能重新載入狀態；Pub/Sub 把「某人位置變了」傳給正在服務其朋友的節點。好友關係及隱私設定仍需要可持久查詢的權威資料。Pub/Sub 訊息通常是瞬時通知，訂閱者斷線時可能漏掉，所以不能把它當成位置歷史或可靠事件日誌。

### 3. A 移動後，B 如何收到附近通知？

**答：** A 上傳位置 → 連線服務檢查時間與格式 → 寫入最新位置並設 TTL → 發布 A 的更新 → B 所在節點因訂閱 A 而收到通知 → 用 A、B 的最新位置算距離 → 只有落在設定範圍且符合可見性時推給 B。若每次都把 A 的全部好友從資料庫讀出並逐個送信，寫入扇出會很高；訂閱關係能把工作移到在線連線，但也要負擔訂閱管理與節點故障後重建。

### 4. B 斷線一分鐘後重連，漏掉的 Pub/Sub 訊息怎麼補？

**答：** 不必逐條補瞬時位置通知；B 重連時讀好友清單與每位好友的**最新**位置，重新計算附近集合，再建立新訂閱。這是一種「通知促使即時更新，快照保證最終收斂」的設計。若產品還要求歷史軌跡，才需要持久事件或位置歷史儲存，不能指望 Pub/Sub。重新訂閱和讀快照的先後要小心：可先訂閱，再讀快照，用時間戳或版本忽略較舊通知。

### 5. 為何「附近朋友」不能直接改成「附近所有陌生人」？

**答：** 前者從有限好友清單判斷距離，訂閱通道可依人建立；後者不知道附近有哪些人，必須先依地理格找候選，還要面對熱門區域的大量發布與隱私限制。可改用 Geohash 區域通道，但格內有人離自己超過 5 公里，所以接收後仍需精確距離過濾；格邊的鄰格也要訂閱或查詢，否則會漏掉近鄰。
