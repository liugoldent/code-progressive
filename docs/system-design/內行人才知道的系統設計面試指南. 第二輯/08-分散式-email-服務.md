# 08｜分散式 Email 服務

## 先問是寄信平台還是完整信箱

若題目是提供 Email 收發服務，範圍可能含寄送、接收、儲存、搜尋、附件、垃圾信與多裝置同步。面試要先選定主要流程，例如「寄信並確保可追蹤的投遞狀態」。完整信箱還要討論收件端 SMTP、IMAP/網頁讀取與索引，不能把第三方寄信 API 視為整個 Email 系統。

## 寄送流程

```text
寄信 API → 驗證與配額 → 郵件/附件持久化 → Outbox/佇列
      → 分網域投遞工作器 → DNS/MX → 對方郵件伺服器
      → 狀態事件、退信、重試、監控
```

API 接受信件只代表本系統收妥，不代表收件人已收到。可設 `ACCEPTED, QUEUED, DELIVERING, DELIVERED_TO_REMOTE, BOUNCED, FAILED` 等狀態；`DELIVERED_TO_REMOTE` 也不等於收件人已閱讀。SMTP 回應分暫時與永久錯誤，暫時錯誤可指數退避並設總期限，永久錯誤不應無限重試。對方系統可能在接受郵件後連線中斷，使本方不知道是否送達；重試可能重複，因此應在語意上承認這種不確定性。

## 收件、搜尋與附件

若包含收件，MX 接入伺服器要先完成協定與垃圾信檢查，再把原始郵件持久化，之後非同步解析標頭、正文、附件與建立搜尋索引。信件主資料與搜尋索引可短暫不一致；搜尋結果需檢查郵件權限。大附件放物件儲存，郵件紀錄保存參照和雜湊；附件掃毒與下載授權需與信件生命週期一致。

## 信譽與防濫用

多租戶服務需要按帳戶、網域、目的網域與 IP 控制寄送速率。退信率與投訴率高的租戶可能拖累共享 IP 信譽。寄件網域驗證、SPF/DKIM/DMARC、退訂與濫用處置都是可投遞性的一部分。記錄投遞事件時要保護郵件內容及收件者隱私。

## 面試深入問題

- 工作器已把信送出，但在記錄成功前當機，恢復時怎麼處理不確定狀態？
- 大型寄信活動如何不擠掉密碼重設信？可分優先級與隔離佇列。
- 郵件已刪除但搜尋索引仍可查到，如何避免內容洩漏？
- 觀測各網域退信率、佇列年齡、寄送成功率、重試與投訴率。

## 寄送狀態如何落在資料表

可分 `messages(message_id, tenant_id, sender, subject_ref, body_ref, created_at)`、`recipients(message_id, recipient, state, last_attempt_at)` 和 `delivery_attempts(attempt_id, recipient_id, mx_host, smtp_code, error, started_at)`。同一封信寄給多位收件人，各人的投遞狀態可能不同，因此不要只給整封信一個 `sent=true`。正文與附件可存在物件儲存，資料庫只放參照；下載或重試投遞時還需驗證租戶權限和物件是否仍在保留期限內。

假設每日 1 億封、每封平均 100 KiB 的正文與附件，每日原始內容約 10 TB。若大多數信件沒有附件，平均值可能被少數大附件拉高；應把信件大小分布和附件上限分開估算。投遞工作器要依目的網域與來源租戶限速：即使總吞吐足夠，單一目的網域也可能因短時間過量寄送而回覆暫時錯誤。

## SMTP 不確定性的例子

工作器把信件內容送給收件端，對方已接受，但本地在收到最後回覆前網路斷線。此時不能證明信件未送達；狀態應記為「結果未知」並有受控重試或人工調查策略。若重試可能產生重複郵件，可維持穩定 Message-ID 方便下游判斷，但不能假設所有收件端都會去重。寄信平台的承諾應以可驗證的狀態為界，不宣稱端到端恰好一次。

收件端若同時收到寄給多個本地帳戶的同一封信，可讓原始內容只存一份、每個收件者各有信箱索引與讀取狀態；刪除某人信箱中的信，不應把其他人的資料一併刪掉。

## 補全「信箱」的使用者流程

原書第八章的開頭把 Gmail 類型服務視為題目，需求不只有 SMTP 寄送，也包括身分驗證、接收郵件、投遞回報，以及依已讀／未讀等狀態篩選。因此可先畫三條獨立流程：

```text
寄信：使用者認證 → 儲存寄件匣 → 佇列 → 對外 SMTP 投遞 → 狀態更新
收信：對外 SMTP 接入 → 驗證與防濫用 → 儲存原文 → 建立收件匣索引
看信：使用者認證 → 列表/搜尋 → 取正文與附件 → 更新已讀狀態
```

信件正文與「某使用者在某信箱中的狀態」應分開。可設 `mailbox_items(user_id, message_id, folder, read_at, starred, deleted_at, received_at)`；同一封群發信讓多個收件者各有自己的已讀狀態。收件匣列表按 `received_at, message_id` 游標分頁；全文搜尋索引可能落後，點開搜尋結果時仍須查使用者權限和刪除狀態。若使用者把郵件標為已讀後立刻刷新，應對該使用者提供「讀到自己的寫入」語意，即使全文搜尋仍是最終一致。

寄出郵件時，先存好原文、收件者與投遞任務，再回覆 `ACCEPTED`。若寄給本系統使用者，可走內部投遞；寄給外部網域則查 MX 並透過 SMTP 投遞。兩條路徑都要產生可稽核狀態，避免「寄件匣有信但收件者永遠收不到」。已讀回執與遠端 SMTP 接受是不同概念，也不能因為遠端收下信就把它標為已讀。

**自己練習：** 同一郵件寄給 A、B，A 刪除、B 尚未閱讀。設計原始內容和兩筆 `mailbox_items` 的狀態；再說明原始內容何時可以真正從物件儲存刪除。

## 寄件者、收件者與搜尋索引的三種狀態

假設使用者寄出訊息 M 給本系統使用者 A，API 已回覆 `ACCEPTED`。此時寄件匣必須能查到 M，投遞工作器還可能尚未把它放進 A 的收件匣。當內部投遞成功後，A 的 `mailbox_items` 出現 M；全文索引可能再晚幾秒才加入。這三件事有不同完成時間，不能只用一個全域 `sent=true` 表示。可保存投遞狀態事件並顯示時間，讓使用者知道是在排隊、已投遞還是失敗。

若 A 在搜尋索引更新前就點開收件匣，列表應依權威信箱索引顯示 M；搜尋暫時找不到 M 可以接受，但產品要決定可容忍延遲。若 A 刪除 M，讀取搜尋結果時仍需檢查 `deleted_at`，避免搜尋索引落後而露出已刪的信。若有法律保留或復原需求，刪除可先變成邏輯刪除；真正移除正文前需確認所有收件者的參照與保留政策。

**故障測試：** 原文已儲存但寄件匣寫入失敗、收件匣寫入成功但投遞事件回覆丟失、搜尋索引停擺。對每個故障點寫出權威資料、重試 ID 與使用者可見狀態，避免重複投遞或信件憑空消失。

## 自學問答：一封信從按下寄送到被讀取

### 1. SMTP、IMAP／POP、Webmail 各在哪段流程？

**答：** SMTP 負責郵件伺服器間的收發與提交；寄往外部網域時，發信端依 DNS MX 找接收伺服器並用 SMTP 投遞。IMAP／POP 是使用者從信箱讀信的協定；Webmail 是透過網站 API 讀寫信箱。外站 SMTP 回覆接受，通常只能說郵件交到對方系統，不能保證收件者已閱讀，也不一定保證對方已把信顯示在收件匣。

### 2. 為何正文、附件和信箱清單資料要分層？

**答：** 清單頁頻繁讀寄件者、主旨、時間、已讀狀態，適合在詮釋資料庫依使用者與資料夾建立索引；大型附件不宜每次列信時一起讀，應存物件儲存並用 ID／位置連結。正文也可與清單欄位分開，避免熱查詢搬動大資料。信件一對多收件者時，可共享不可變內容，但每人自己的資料夾、已讀、標記與刪除狀態必須分開。

### 3. 寄件 API 回成功，信是否已寄到外站？

**答：** 不一定。API 先驗證與持久入佇列，回覆通常表示**本站已接受責任**；SMTP 工作器之後才和外站對話。狀態要區分已接受、投遞中、外站接受、暫時失敗、永久退信等。若入佇列之前就回成功，工作器當機可能丟信；若外站已接受但最後回覆丟失，重試可能重複寄送，所以需穩定郵件 ID、合理重試與投遞紀錄。

### 4. 外站回暫時錯誤和永久錯誤，處理有何不同？

**答：** 暫時錯誤可在較長間隔後重試，逐步退避並限制最長期限；立即密集重送會加重對方負擔，還可能降低寄件聲譽。永久錯誤如地址不存在則不應無限重試，需產生退信狀態與通知。逾時不一定等於外站未收，查投遞紀錄時要保留「結果不確定」。

### 5. 已刪除的信仍被搜尋命中，要修哪裡？

**答：** 搜尋索引可能非同步落後。搜尋結果回傳前應用目前權威信箱狀態過濾，避免向使用者顯示已刪或無權查看的信；同時重新投遞索引刪除事件、監控索引延遲並支援重建。搜尋索引是查找加速結構，不應成為權限與刪除狀態的唯一來源。

### 6. 送達率為什麼是架構問題，不只是 SMTP 問題？

**答：** 若大量新 IP 突然寄信、忽略退信與投訴、缺少寄件身分驗證，外部服務可能拒收或歸入垃圾郵件。投遞工作器需要按目的網域節流、管理重試、追蹤退信與投訴，並支援發信 IP 暖機。架構也要隔離濫發帳號，避免單一壞流量拖累所有人的信件。這些步驟是提高被接收機率，不能保證每封必達。
