# AI 時代的軟體工程師學習策略

## 先回答最讓人焦慮的問題

「未來還需不需要軟體工程師？」沒有人能保證答案，也不需要用過度樂觀的口號壓掉這個擔心。

比較能採取行動的問法是：

> 當寫出一段可運行的程式愈來愈便宜，企業還願意為哪些能力付費？

答案不會只剩下「會不會手寫某個 API」。真正的工作還包含：

- 從模糊需求中找出真正問題，辨認互相衝突的限制。
- 在既有系統中做改動，理解相依關係、歷史包袱與風險。
- 對正確性、安全性、效能、可維護性與上線結果負責。
- 發現 AI 產出中「看起來合理、實際上不成立」的部分。
- 與產品、設計、後端、QA 和其他工程師形成共同決策。

AI 會參與上述每一項，也會讓一部分工作所需的人力下降。因此，合理的策略不是假設職業永遠不變，而是把自己從「程式碼產生者」升級成**能藉由程式碼與 AI 解決問題、並為結果負責的人**。

## 校正幾個常見建議

Gemini 提到的方向大致合理，但學習時需要再排優先順序。

| 常見建議 | 更適合實行的版本 |
| --- | --- |
| AI 不會取代工程思考 | 不把任何能力當成永久護城河；持續把工作往需求判斷、系統整合、驗證與責任移動。 |
| 練好 Prompt 能力 | Prompt 只是介面。更重要的是提供正確 context、拆出可驗收任務、訂定限制、檢查假設與判讀結果。 |
| 深挖 Virtual DOM、Reconciliation、Fiber | 先掌握 render snapshot、state ownership、identity、effect 邊界與並行更新等公開行為；Fiber 實作細節放在需要解釋機制時再深入。 |
| 擴展成 Full-Stack | 補齊一條可交付的垂直切片，不是收集更多框架名稱。至少理解 API、認證、資料庫、cache、部署與 observability 的邊界。 |
| 不必再記語法 | 不必背低頻 API，但核心語言、非同步、資料結構、框架心智模型仍要熟到能閱讀、debug 與判斷 AI 是否寫錯。 |

## 建立「一深、兩寬、一槓桿」能力組合

### 一深：保留 Vue 的 production 深度

學 React 不代表 Vue 經驗歸零。既有優勢應該繼續變深：

- 大型元件如何拆分，狀態與副作用如何治理。
- TypeScript、測試、效能、瀏覽器行為與工程工具。
- 曾處理過的 production bug、跨團隊協作與取捨。
- 從需求到上線、監控與回復的完整交付經驗。

履歷不要把自己描述成「正在從 Vue 重學前端」，而是「已有 Vue 交付經驗，並能把同一套工程判斷轉移到 React」。

### 第一個寬度：把 React 練成第二套原生思考

React 的學習目標不是把 Vue API 翻譯成 Hook，而是看到需求時能自然判斷：

- 哪個資料才是 source of truth？
- 這是 render 時可推導的值，還是真的 state？
- 這段邏輯屬於 event，還是與外部系統同步的 effect？
- effect 是否會遇到 stale closure、race、重複訂閱或漏 cleanup？
- state 應 colocate、提升、放進 Context，還是交給 external store？
- 問題是 render 次數，還是單次工作太重？有沒有 Profiler 證據？

學習順序應是：**公開心智模型 → 常見錯誤 → 測試與除錯 → 效能量測 → 底層實作**。能解釋 Fiber 是加分，但不能取代正確處理 effect、identity 和非同步資料。

### 第二個寬度：補齊前端以外的交付邊界

選一個小產品，完整走過以下路徑：

```text
需求
  → UI 與互動狀態
  → API contract
  → 認證與授權
  → 資料儲存與 cache
  → 測試
  → 部署
  → log、metric 與錯誤追蹤
```

不需要立刻把自己定位成資深後端。目標是當問題跨出瀏覽器時，不會失去判斷力，並且知道哪一層應該負責什麼。

### 一個槓桿：AI 協作與驗證

AI 能加快閱讀陌生程式、建立測試骨架、產生候選方案、補 edge case 與整理文件。但最終價值不是「一天產生多少行」，而是**更快得到可信的結果**。

每次讓 AI 參與工作，都要保留四個責任：

1. **定義**：問題、限制、完成條件是什麼？
2. **取捨**：為什麼選這個方案？代價與替代方案是什麼？
3. **驗證**：哪些測試、文件、量測或實際操作能證明它成立？
4. **所有權**：如果上線失敗，自己是否能定位、修正與解釋？

## 用四種模式練習 AI 協作

同一種 AI 使用方式不適合所有階段。可以依目的切換：

| 模式 | AI 可以做什麼 | 你要練什麼 |
| --- | --- | --- |
| 閉卷模式 | 先不使用 | 建立基本反射，確認自己能從空白開始 |
| 面試官模式 | 只出題、追問、給測試案例，不直接給答案 | 需求釐清、口述、臨場推導 |
| Reviewer 模式 | 找 bug、反例、風險與遺漏 | Code review、邊界條件、取捨判斷 |
| Pair 模式 | 產生候選實作、測試骨架與重構方案 | 快速整合、查證、測試與交付 |

如果所有練習都直接進入 Pair 模式，容易得到能跑的作品，卻無法形成面試與 debug 所需的心智模型；如果完全拒絕 AI，又會錯過工作方式正在改變的現實。兩者都要練。

## 一個不會被 AI 偷走學習效果的循環

每個 React 或系統題都使用同一套流程：

### 1. 先自行建立問題模型

用 10～25 分鐘寫出：

- 已知條件與未知條件。
- state、事件、外部系統與失敗路徑。
- 最小實作，以及自己最不確定的地方。

### 2. 讓 AI 攻擊答案

不要只問「請優化」。可以要求：

- 找出三個會在 production 發生的反例。
- 設計會讓這段程式失敗的測試。
- 標示每一項假設，指出哪些沒有證據。
- 提供兩個替代方案，說明何時不應採用目前方案。
- 以面試官方式連續追問，先不要透露答案。

### 3. 用工具與第一手證據驗證

依問題選擇真正能驗證的手段：

- 型別檢查、unit / integration / e2e test。
- React DevTools、Profiler、瀏覽器 Network / Performance / Memory。
- 官方文件、API contract、實際 response 與 log。
- build 結果、bundle 分析、錯誤監控與部署環境行為。

AI 的第二個回答不是第一個回答的證據。能執行的測試、量測結果與公開 contract 才是。

### 4. 關掉答案重做與口述

隔天從空白重做關鍵部分，並用 3 分鐘回答：

- 問題根因是什麼？
- 為什麼這個解法成立？
- 哪個 edge case 最容易漏掉？
- 還有什麼方案，為什麼這次沒選？

能重新推導，才代表 AI 幫你加速學習，而不是暫時代替思考。

## 針對轉職的時間分配

目前已有 Vue 經驗、正在補 React，建議先用以下比例連續執行六週：

| 比例 | 學習內容 | 每週可見產出 |
| --- | --- | --- |
| 45% | React 核心、debug 與面試實作 | 2 題閉卷實作、1 題 bug 修復、1 次口述 |
| 25% | JavaScript、瀏覽器、非同步、效能與安全 | 1 個可重現 lab，附 DevTools 或測試證據 |
| 20% | 一個垂直切片作品 | 每週交付一段真的可操作、可測試的功能 |
| 10% | 履歷、職缺校準與模擬面試 | 追蹤目標 JD 缺口，改善一段專案敘述 |

這不是永遠不變的比例。React 達到可獨立交付後，把部分時間移到系統設計、全端邊界與目標產業知識。

### 不要同時開太多武器線

React、Next.js、Node.js、資料庫、雲端、LLM application 全部同時從零開始，通常只會得到很多入門進度。每一階段只保留：

1. 一個主要缺口，例如 React 原生思考。
2. 一個整合型作品，例如 realtime dashboard。
3. 一個求職輸出，例如限時 coding 或 system design 口述。

新技術只有在能補目標職缺缺口，或能讓作品多出一個可證明的能力時，才加入計畫。

## 把作品從「功能展示」升級成「工程證據」

AI 已能快速生成常見 CRUD 與漂亮 UI，因此作品集只展示畫面會愈來愈難證明能力。每個作品至少回答：

- **需求**：解決什麼情境？成功指標與限制是什麼？
- **架構**：狀態、資料流、模組和信任邊界如何劃分？
- **失敗**：loading、empty、error、timeout、race、重連如何處理？
- **品質**：用哪些測試保護主要使用流程？
- **效能**：哪裡真的慢？修改前後的數據是什麼？
- **安全**：輸入、認證、secret、第三方依賴有哪些風險？
- **決策**：刻意沒有使用哪個熱門方案？原因是什麼？
- **AI 使用**：AI 幫了哪些部分？你如何驗證、改寫與承擔結果？

一個能展示 snapshot + delta、一致性恢復、測試、Profiler 證據與架構決策的 dashboard，通常比五個由教學拼出的待辦清單更有說服力。

## 每週檢查：能力是否真的在增加

不要用「讀了幾篇、問了幾次 AI、寫了幾行 code」衡量進度。改用以下檢查：

- [ ] 能在沒有 AI 的情況下完成本週的核心小題。
- [ ] 能讀懂並拒絕一個看似合理但有 bug 的 AI 解法。
- [ ] 至少有一個測試、量測或 log 能證明結論。
- [ ] 能說明方案限制，而不只描述程式如何運作。
- [ ] 能把新能力連到目標職缺的一項要求。
- [ ] 能把本週成果寫成履歷或面試中可講的工程故事。

## 最後的職涯定位

短期目標不是追上所有新技術，而是形成一個清楚、可信的定位：

> 我是一位有 Vue production 經驗的前端工程師，能用 React 獨立交付，理解瀏覽器、非同步資料與系統邊界；我會使用 AI 加速實作與探索，也能用測試、量測和 code review 對產出負責。

這個定位比「我會 Vue、React、Next.js、Node.js 和很多 AI 工具」更能抵抗技術清單快速折舊。工具會繼續改變，但能定義問題、建立證據、做取捨並交付結果，才是接下來每一輪學習都應該累積的核心。
